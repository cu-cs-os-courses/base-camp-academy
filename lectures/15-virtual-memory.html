Memory as a cache of the disk

In Lecture 14, every page of a process is mapped to a frame. However, most pages are not used most of the time. If RAM holds only the pages that a process is actually using, and the OS fetches the other pages from disk when they are first touched, the address space can be far larger than physical memory. In this lecture, we discuss how a missing page is fetched, what it costs, how fork avoids copying at all, and what happens when memory fills up.

Chapter 0

Demand paging

Load only what you need, when you need it.

0.1Not every page needs to be in RAM

  • Processes and their page tables can be large. Keeping all of them in memory costs a lot of RAM. The key observation is that not all pages of a logical address space need to be in memory at once.
  • At the extreme, the OS keeps only the page that the PC is executing in, and it fetches every other page from disk just before the page is used. This approach works. However, it is far too slow, because it needs a disk read every time execution moves to another page.
  • Therefore, the OS keeps a subset of the pages of the process in memory. Specifically, it treats memory as a cache of the most frequently or most recently used pages, and it loads a page only when the page is needed.

0.2Locality of reference

A cache works only if the program cooperates. Most programs exhibit locality of reference. In other words, a page referenced recently is likely to be referenced again soon.

  • Loops run through the same instructions again and again.
  • Branches keep returning to the same code.
  • Execution is mostly linear. The next instruction is usually right after the last one, not a random jump.

As a result, execution mostly revisits pages that are already in memory. The program does not go to disk every time the PC crosses into another page.

0.3Paging in on demand

  • With demand paging, a page is brought from disk into RAM only when it is referenced. A process can even start with zero pages in memory. The first instruction fetch faults in the first page, and later pages come in as execution reaches them.
  • The valid–invalid bit from Lecture 14 now has a second meaning. Invalid can mean "not in this address space" or "legal, but not in memory right now".

0.4What virtual memory buys

Bigger than RAMA virtual address space can exceed physical memory. Only the most demanded subset of pages lives in RAM. As such, virtual memory is decoupled from physical memory.
More processesEach process occupies only its active pages. Therefore, many more processes fit in memory, and the CPU stays busier.
Less to swapMoving a process out means moving only its resident pages, not its whole image.
Sparse address spacesA large heap and stack that are mostly empty take no RAM until they are actually touched.

That raises two questions, answered below and in Lecture 16. How is a needed page loaded from disk? When no frame is free, which page is replaced?

Chapter 1

The page fault

What happens when the MMU finds an invalid bit, and why it must be rare.

1.1Six steps

Step throughHandling a page fault

We describe each step in more detail below.

  1. The MMU finds the page-table entry invalid and raises a page-fault trap to the OS.
  2. The OS saves the registers and process state, determines that the trap is a page fault, and jumps to the page-fault handler.
  3. The handler checks the reference. If the address is not in the logical address space of the process at all, the access is illegal, namely a segmentation fault. If the address is legal but the page is not in RAM, the OS loads the page.
  4. The OS finds a free frame and schedules a disk read. Other processes run meanwhile, because the faulting process is blocked, as in any I/O wait.
  5. The disk interrupts when the read is done. The page is now in the frame. The OS updates the page table. Specifically, it sets the valid bit and the frame number.
  6. The OS restarts the instruction that caused the fault. This time, the instruction finds the page and runs as if nothing had happened.

1.2Where the page comes from

  • The page can come from the file system, for example the executable file, or from swap space, which is a disk area reserved as backing store. Swap is faster, because it needs no file-system lookup and can be laid out contiguously.
  • Pages end up in swap in two ways. First, some systems copy the whole executable into swap when the program starts. Second, when pages are evicted from RAM, they are written to swap rather than back to the file system. As such, the next fault on them is quick.
  • Linux and Windows take an approach in between. Code pages are paged in directly from the executable file. Since code pages are never modified, they are simply dropped when evicted. Only anonymous pages go to swap. These pages, such as the heap and stack, have no file behind them.

1.3What it costs

If p is the probability that a memory reference faults, the effective access time is

EAT = (1 − p) × memory access + p × page-fault service time

The slides use a 10 ns memory read and a 10 ms disk read. With these numbers, p = 0.001 gives about 10 µs, which is 1000× slower than memory. Keeping EAT within 10% of 10 ns requires p below 10−7, namely one fault in ten million references.

Chapter 2

Copy-on-write

fork() without copying, until one of the processes writes.

2.1Share, then copy on the first write

  • Copy-on-write (COW) lets the parent and the child share the same frames after fork(). The shared pages are marked read-only in both page tables.
  • When either process writes to a shared page, the write traps. The OS copies only that page into a new frame, maps the copy as writable into the page table of the writer, and restarts the write.
  • Only modified pages are ever copied. Therefore, process creation is fast. In the common pattern, in which the child calls exec() right away, almost nothing is copied at all.
Try itParent and child after fork()

2.2vfork()

vfork() goes further. The parent is suspended, and the child runs directly in the address space of the parent, with no copy-on-write, no page-table copy at all. It is designed for a child that immediately calls exec(), and it is very efficient. However, any page that the child modifies before exec() is modified for the parent too. Therefore, the child must do almost nothing but exec().

Chapter 3

When memory is full

To page in, the OS first pages something else out.

3.1The replacement mechanism

As processes run and demand-page more pages in, the system eventually runs out of free frames. A page fault then needs page replacement.

  1. Find the location of the desired page on disk.
  2. Find a free frame. (a) If there is one, use it. (b) If not, use a page-replacement algorithm to pick a victim frame. (c) Write the victim to disk if it is dirty, and update its page-table entry to invalid.
  3. Read the desired page into the newly freed frame, and update the page and frame tables.
  4. Restart the instruction that caused the trap.

Step 2(c) is new compared with plain demand paging. It can double the cost, because a fault may need two disk operations, namely a write and then a read.

3.2The dirty bit

  • The dirty (modify) bit in each page-table entry starts at 0, and the hardware sets it to 1 when the page is written.
  • A clean victim (dirty = 0) need not be written out, because an identical copy is already on disk. In this case, the fault costs only one disk operation, namely the read.
  • Therefore, other things being equal, the OS prefers a clean victim over a dirty one.
Try itThree frames, dashed = write

Run both choices. On this string, preferring clean pages saves a write-back. However, it evicts a page that is needed again sooner, which costs an extra fault. As a result, both choices take 11 disk operations. In other words, clean-first is a tiebreaker, not a policy by itself. Lecture 16 discusses how to choose the victim well.

Epilogue

Summary and glossary

∎What to take away

  • Only a small fraction of a logical address space needs to be in RAM. Pages are brought in on demand. This works because programs show locality.
  • The virtual address space can be much larger than physical memory, many more processes fit in memory, and sparse regions cost nothing.
  • A page fault traps to the OS, which checks legality, finds a frame, reads the page (other processes run meanwhile), fixes the page table, and restarts the instruction.
  • Faults are very expensive. Therefore, the fault rate must be tiny, on the order of 10−7 for under 10% overhead with the numbers from the slides.
  • Copy-on-write shares pages after fork() and copies only on write. vfork() shares the address space outright.
  • When no frame is free, the OS picks a victim and writes it back if it is dirty. A clean victim saves a disk write.

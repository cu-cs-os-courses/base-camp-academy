Let the language hold the lock

Lecture 09 showed how one misplaced P or V breaks a program. A monitor moves the locking into the language. Shared data is reachable only through the monitor's functions, and only one thread runs them at a time. For waiting, it adds condition variables. They look like semaphores but have no memory, and that difference decides how you must use them.

Chapter 0

Monitors

Let the compiler insert the P and V for you.

0.1Why a higher-level tool

  • Semaphores can deadlock or break mutual exclusion through simple programming errors, such as a missing P or V, a misordered pair, or a duplicated call (Lecture 09, §2.3).
  • A monitor is a higher-level synchronization construct that essentially automates the insertion of P and V.
  • Underneath, the compiler or runtime may implement monitors using semaphores and mutex locks.

0.2What a monitor is

  • A monitor is declared somewhat like a C++ class, with shared variables, functions, and initialization code.
  • It guarantees that only one thread at a time is active inside the monitor. You never write the locking yourself.
  • Implicitly it defines a lock, semaphore mutex = 1, and wraps each function body in P(mutex) … V(mutex).
  • The monitor's variables can be accessed only by its own functions, and each function uses only those variables and its parameters. No one can reach the shared data without the lock.
monitor monitor_name { // shared local variables function f1(…) {…} function f2(…) {…} … initialization code(…) {…}} // what the compiler makes of each fjfunction fj(…) { P(mutex); // critical code V(mutex);}

0.3What got lost

So far a monitor gives mutual exclusion and hides P and V. But a semaphore could do one more thing, namely enforce order. One process can sleep in P until another calls V. A plain monitor has no way for a process to sleep waiting for a signal. Yet processes often need to wait until some condition holds, such as data being ready or a queue having space. So monitors are extended with condition variables.

Chapter 1

Condition variables

A named queue inside the monitor for "wait until something is true".

1.1wait, signal, queue

A condition variable adds an ordering mechanism to the monitor's mutual exclusion. One task waits until a condition is true. A second task makes it true and signals the waiter to proceed. A condition variable y has the three operations below.

  • y.wait() blocks the caller and releases the monitor so others can enter. Many processes can be suspended on one condition, typically released in FIFO order.
  • y.signal() resumes exactly one suspended process. If no process is waiting, it has no effect.
  • y.queue() returns true if at least one process is blocked on y.

1.2Making S1 happen before S2

P1 must run statement S1 before P2 runs S2. Put them in a monitor with functions F1, called by P1, and F2, called by P2, a condition variable x, and a boolean done = FALSE.

Why the flag? A condition variable has no value to initialize. If F1 runs first, its signal finds no waiter and is lost. The flag records that S1 already happened, so F2 does not wait at all. The check and the wait are both inside the monitor, so nothing can slip in between them.

monitor Order { boolean done = FALSE; condition x; F1() { // P1 S1; done = TRUE; x.signal(); } F2() { // P2 if (!done) x.wait(); S2; }}

1.3Who runs after a signal?

When P signals and Q was waiting, both could continue, but only one may be active in the monitor. There are two classic answers.

  • Signal-and-wait (Hoare). Q runs immediately, and P waits until Q leaves or waits. Q is guaranteed that the condition still holds.
  • Signal-and-continue (Mesa). P keeps running, and Q goes back to the entry queue and competes to re-enter. By the time Q runs, another thread may have changed the condition. Java, C# and POSIX threads use this rule.

Under Mesa semantics a woken thread must re-check its condition, so waits belong in a while loop, not an if. See it happen with two consumers and one producer on a monitor that counts items.

Try itA monitor with one condition, x = "an item is available"

1.4Condition variable vs. semaphore

signal

C.signal has no effect if no thread is waiting. A condition variable is not really a variable. It has no value. S.signal (V) has an effect whether or not anyone waits, because the semaphore keeps a memory in its count.

wait

S.wait (P) checks its condition and blocks only if necessary. The condition is built in, but it is limited to a counter, and the caller need not re-check after P returns. C.wait checks nothing, ever. It always blocks. The condition is defined outside, by the programmer, and protected by the monitor's lock.

Chapter 2

Inside and beyond

How monitors are built from semaphores, and how to pick which waiter wakes.

2.1Condition variables from semaphores

A Hoare-style monitor can be built from semaphores. Each monitor has mutex, for entry, and next, where signalers wait while the thread they woke runs, plus a count next_count of those signalers. Each condition x gets its own semaphore and count.

semaphore mutex = 1; // monitor entrysemaphore next = 0; // suspended signalersint next_count = 0; // each monitor function F:wait(mutex); // body of Fif (next_count > 0) signal(next); // let a signaler resumeelse signal(mutex); // or admit a new entrant
semaphore x_sem = 0; int x_count = 0; // x.wait()x_count++;if (next_count > 0) signal(next);else signal(mutex);wait(x_sem);x_count--; // x.signal()if (x_count > 0) { next_count++; signal(x_sem); // hand over to the waiter wait(next); // and step aside next_count--;}

Note the if (x_count > 0) in x.signal(). With no waiter, signal does nothing. That is the "no memory" property, built on top of semaphores that do have memory.

2.2Priority waits

If several processes wait on x, which does x.signal() resume? With the conditional-wait construct x.wait(c), the integer c is a priority number, and the waiter with the lowest number resumes first.

For example, allocate one resource, where each process passes the maximum time it plans to use it. The shortest request is served first. This is SJF from Lecture 06, with the same risk of starving long requests.

This code uses if, which is correct under the Hoare semantics these textbook monitors assume. Under Mesa it must be while.

monitor ResourceAllocator { boolean busy; condition x; void acquire(int time) { if (busy) x.wait(time); busy = TRUE; } void release() { busy = FALSE; x.signal(); } initialization_code() { busy = FALSE; }}

Chapter 3

Complex conditions and POSIX

Outside a monitor, the lock is yours to manage, and pthread_cond_wait exists because of one tiny window.

3.1Waiting on a compound condition

Task 1 waits while f != 7.0 && count <= 0. That is, it proceeds once Task 2 has set f to 7.0 or made count positive. Task 2 does both, then signals. With plain threads there is no monitor, so the test must be protected by a mutex that you manage. There are four versions to compare.

  • no lock leaves a race between testing the shared variables and setting them.
  • wait holding the lock surrounds the test with a mutex, as on the slide, but x.wait() does not release it.
  • release, then wait releases the mutex by hand just before waiting.
  • pthread_cond_wait hands the mutex to the wait, which releases it and sleeps in one atomic step, then re-acquires it before returning.
Try itFour versions, every interleaving

Each line is one atomic step. "Every interleaving" means all orders in which Task 1 and Task 2 can take their steps, from the start to the end or to a point where nobody can move.

3.2POSIX condition variables

pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;pthread_cond_t x = PTHREAD_COND_INITIALIZER;int count = 0; float f = 0.0; // Task 1pthread_mutex_lock(&m);while (f != 7.0 && count <= 0) pthread_cond_wait(&x, &m);pthread_mutex_unlock(&m);// … proceed
// Task 2pthread_mutex_lock(&m);f = 7.0;count++;pthread_cond_signal(&x);pthread_mutex_unlock(&m);
callmeaning
pthread_cond_init(&c, NULL)Initialize (or use PTHREAD_COND_INITIALIZER).
pthread_cond_wait(&c, &m)Caller must hold m. Atomically releases m and sleeps on c. It re-acquires m before returning.
pthread_cond_signal(&c)Wake at least one waiter (Mesa semantics). It has no effect if there is none.
pthread_cond_broadcast(&c)Wake all waiters. Each re-checks its own condition.
pthread_cond_destroy(&c)Done with it.
The three rules

1. Keep the condition in shared variables, and read and write them only while holding the mutex. 2. Always wait in a while loop that re-tests the condition, because of Mesa semantics, and because POSIX permits spurious wakeups. 3. Signal after changing the state. Signaling while still holding the mutex, as above, is always safe.

Epilogue

Summary and glossary

∎What to take away

  • A monitor bundles shared data with the only functions that may touch it. One thread at a time is active inside, and the P and V are implicit.
  • Condition variables add waiting. wait always blocks and releases the monitor, and signal wakes one waiter or does nothing.
  • Condition variables have no memory, so pair each wait with a state variable that you check first.
  • Hoare semantics run the woken thread immediately. Mesa semantics (POSIX, Java) let the signaler continue, so waiters must re-check in a while loop.
  • Monitors can be built from semaphores (mutex, next, one semaphore per condition). x.wait(c) resumes the lowest c first.
  • In POSIX, pthread_cond_wait(&c, &m) atomically releases the mutex and sleeps, closing the lost-wakeup window.
TermMeaning
monitorA module of shared data plus functions, with implicit mutual exclusion.

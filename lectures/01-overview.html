Chapter 0

What an operating system is

There is no universally accepted definition. Therefore, we start with where the OS sits.

0.1Four components of a computer system

  • Users are people, machines, and other computers.
  • Application programs define how system resources are used to solve users' problems. Examples are word processors, compilers, web browsers, database systems, and games.
  • The operating system controls and coordinates the use of the hardware among the applications and users.
  • Hardware provides the basic computing resources, namely the CPU, memory, and I/O devices.

0.2What operating systems do

An OS is a program that acts as an intermediary between a user of a computer and the hardware. It has three goals. First, it executes user programs and makes solving problems easier. Second, it makes the computer convenient to use. Third, it uses the hardware efficiently.

What these goals mean depends on the point of view.

  • A user at a laptop wants convenience, ease of use, and good performance, and does not care about resource utilization.
  • A shared computer (mainframe, minicomputer, server) must keep all its users happy. Therefore, the OS is a resource allocator and a control program that uses the hardware efficiently and manages the execution of user programs.
  • Workstation users have dedicated resources but often use shared ones from servers.
  • Mobile devices are resource poor and optimized for usability and battery life, with touch and voice interfaces.
  • Embedded computers in devices and cars have little or no user interface and run mostly without user intervention.

0.3Defining the operating system

  • "Everything a vendor ships when you order an operating system" is a good approximation. However, what vendors ship varies widely.
  • "The one program running at all times on the computer" is the kernel, part of the OS. Everything else is either a system program (ships with the OS, not part of the kernel) or an application program.
  • General-purpose and mobile OSes today also include middleware, namely frameworks that give application developers extra services such as databases, multimedia and graphics.
In this course

"The OS" mostly means the kernel, namely the code that runs in the privileged mode of Chapter 4 and that every other program has to ask.

0.4What an OS is written in

  • Early OSes were written in assembly, then in system programming languages like Algol and PL/1, and now in C, C++, and increasingly Rust.
  • Usually, an OS is written in a mix of languages. The lowest levels are in assembly, and the main body is in C. System programs are in C, C++, and scripting languages (Perl, Python, shell).
  • A higher-level language is easier to port to other hardware. However, it is slower. Note that emulation can let an OS run on non-native hardware.

Chapter 1

Review of computer organization

The hardware the OS manages, and the one mechanism it depends on above all, namely the interrupt.

1.1Computer-system organization

  • One or more CPUs and device controllers connect through a common bus that gives access to shared memory.
  • CPUs and devices execute concurrently, competing for memory cycles.
  • Each device controller is in charge of one device type and has a local buffer. Each controller type has an OS device driver to manage it.
  • The CPU moves data between main memory and the controllers' buffers. I/O itself moves data between the device and its controller's buffer. The controller tells the CPU that it has finished by causing an interrupt.

1.2Interrupts

  • An interrupt transfers control to an interrupt service routine, generally through the interrupt vector, a table with the addresses of all the service routines.
  • The interrupt architecture must save the address of the interrupted instruction. The OS preserves the rest of the CPU state by storing the registers and the program counter.
  • It determines which kind of interrupt occurred. Separate code handles each kind.
  • A trap or exception is a software-generated interrupt, caused by an error or by a user request.
Key idea

An operating system is interrupt driven. After booting, the kernel mostly waits. It runs when a device interrupts, a program traps, or the timer fires.

1.4Two ways to wait for I/O

Return only when I/O completesA wait instruction idles the CPU until the next interrupt, or a wait loop spins (contending for memory). At most one I/O request is outstanding at a time. Therefore, there is no simultaneous I/O.
Return without waitingThe program continues, and a system call lets it wait for completion when it chooses. A device-status table has an entry per device with its type, address, and state. The OS updates the entry when the device interrupts.

Chapter 2

Storage

Fast storage is small, expensive, and volatile. Large storage is slow and non-volatile. The OS manages both.

2.1Main memory and secondary storage

  • Main memory is the only large storage the CPU can access directly. It is random access and typically volatile, and it is usually dynamic RAM (DRAM).
  • Secondary storage extends main memory with large non-volatile capacity.
  • Hard disk drives (HDDs) use rigid platters coated with magnetic material, divided into tracks and sectors. The disk controller manages the interaction with the computer. Non-volatile memory (NVM) devices, such as flash SSDs, are faster. They are becoming more popular as capacity and performance rise and prices fall (Lecture 19).

2.2The storage hierarchy

Storage is organized in a hierarchy by speed, cost, and volatility. Caching copies information into faster storage. Note that main memory can be viewed as a cache for secondary storage. Click a level in the widget below.

2.3Caching

  • Caching is an important principle. It is applied at many levels, namely hardware, OS, and software.
  • Information in use is copied temporarily from slower to faster storage. The cache is checked first. If the information is there, it is used directly (fast). Otherwise, it is copied into the cache and used there.
  • The cache is smaller than the storage it caches. Therefore, cache management (its size and its replacement policy) is an important design problem. You will see it again as the TLB (L14), page replacement (L16), and the buffer cache (L20).

2.4How a modern computer works

In a von Neumann architecture, instructions and data share memory. The CPU fetches an instruction, executes it, and moves data between memory and its registers.

Devices move data in one of two ways. First, a device moves one word at a time through the CPU (after an interrupt). Second, a device moves data in bulk by DMA, directly into memory, with a single interrupt at the end.

Chapter 3

Running many programs

This chapter goes from boot to multiprogramming to timesharing, and it explains why the OS switches between programs at all.

3.1From boot to running

  1. A small bootstrap program initializes the system and loads the kernel.
  2. The kernel loads and starts system daemons, which are services provided outside the kernel.
  3. From then on, the kernel is interrupt driven. It is driven by hardware interrupts from devices and by software interrupts (exceptions or traps). Software interrupts come from software errors such as division by zero, requests for OS service (system calls), and other process problems such as infinite loops or processes modifying each other or the OS.

3.2Multiprogramming and timesharing

  • A single user cannot keep the CPU and I/O devices busy all the time.
  • Multiprogramming (batch systems) keeps several jobs (code and data) in memory, so that the CPU always has one to run. Job scheduling selects one of them. When that job has to wait, for example for I/O, the OS switches to another job.
  • Multitasking (timesharing) is the logical extension of multiprogramming. The CPU switches jobs so frequently that users can interact with each job while it runs. Response time should be under a second. Each user has at least one program in memory, namely a process. Choosing among ready processes is CPU scheduling. Swapping and virtual memory handle processes that do not fit in memory.

Chapter 4

Dual mode and the timer

When many programs share one machine, the OS must protect itself and the programs from each other. Two hardware features make this protection possible.

4.1User mode and kernel mode

  • Dual-mode operation lets the OS protect itself and other components. It has two modes, user mode and kernel mode.
  • A mode bit, provided by hardware, says whether user code or kernel code is running.
  • Some instructions are privileged. In other words, they are executable only in kernel mode.
  • Note that a user program cannot set the mode bit to "kernel" itself. A user program can enter kernel mode only through a system call (a trap), and the trap jumps to kernel code that the OS chose. Returning from the call sets user mode again.

4.2The timer

  • A timer prevents an infinite loop, or a process hogging resources, from keeping the CPU forever.
  • The OS sets a counter (a privileged instruction), which the physical clock decrements. When the counter reaches zero, the hardware raises an interrupt.
  • The OS sets the timer before it schedules a process. As such, the OS can regain control, or terminate a program that exceeds its allotted time.

Chapter 5

What the OS manages

This chapter maps the rest of the semester.

5.1Process management

  • A process is a program in execution, a unit of work. A program is a passive entity. In contrast, a process is active.
  • A process needs resources (CPU, memory, I/O, files, initialization data). When it terminates, the reusable resources must be reclaimed.
  • A single-threaded process has one program counter and executes instructions one at a time. A multi-threaded process has one program counter per thread. Many processes, user and OS, run concurrently by multiplexing the CPUs.
  • The OS creates and deletes processes, suspends and resumes them, and provides mechanisms for synchronization, communication, and deadlock handling. (Lectures 3–12.)

5.2Memory management

  • To execute a program, all or part of its instructions and data must be in memory. Memory management decides what is in memory and when. Its goal is to optimize CPU utilization and response time.
  • Specifically, it keeps track of which parts of memory are in use and by whom, decides which processes and data move in and out, and allocates and frees memory. (Lectures 13–16.)

5.3Storage, files and I/O

File systemsThe file system gives a uniform, logical view of storage, in which the file abstracts the physical medium. It covers directories, access control, creating and deleting files and directories, mapping them onto secondary storage, and backups. (L20)
Mass storageThe speed of the whole computer can depend on the disk subsystem. This subsystem handles mounting, free-space management, allocation, disk scheduling, partitioning, and protection. (L19)
I/O subsystemThe I/O subsystem hides the peculiarities of devices. It uses buffering, caching, spooling (overlapping one job's output with another's input), a general driver interface, and specific drivers. (L17–18)

5.4Structuring an operating system

A general-purpose OS is a very large program. There are several ways to structure it.

  • Monolithic (UNIX, Linux). The whole kernel is one program in one address space.
  • Microkernel (Mach). The small kernel provides only communication, basic memory management, and CPU scheduling. File systems and drivers run as user-level servers that communicate through messages.
  • This course focuses on monolithic plus modular design, namely Linux, with loadable kernel modules, such as the driver you write in Basecamp 5.

5.5Policy and mechanism

  • Policy defines what needs to be done. For example, interrupt every 100 seconds.
  • Mechanism defines how to do it. For example, the timer.
  • The two should be kept separate. As such, a policy decision can change later (100 becomes 200) without changing the mechanism. This separation gives maximum flexibility.
Watch for it

This split recurs throughout the semester, for example, in the timer vs. the scheduling policy (L6), paging vs. the replacement policy (L16), and the access matrix vs. who may use what (L22).

Epilogue

Summary and glossary

∎What to take away

  • The OS sits between applications and hardware, as a resource allocator and control program. Its core, the kernel, is the one program always running.
  • CPUs and device controllers run concurrently on a shared bus. Devices report through interrupts. As such, the OS is interrupt driven.
  • Storage forms a hierarchy of speed, cost, and volatility. Caching makes the hierarchy look fast.
  • Multiprogramming keeps the CPU busy while jobs wait for I/O. Timesharing switches often enough for interaction.
  • Dual-mode operation and the timer let the OS protect itself and keep control.
  • The OS manages processes, memory, files, storage, and I/O. It is structured monolithically, as a microkernel, or modularly. Policy is kept separate from mechanism.

Chapter 0

The readers–writers problem

Readers may share; writers may not. Four attempts, each fixing one flaw.

0.1The problem

A data object, such as a file, a database or a shared document, is used by many concurrent processes. Readers only read it. Writers can read and write.

  • Goal 1: a writer must have exclusive access.
  • Goal 2: readers can share access with other readers.

Two further requirements pull in opposite directions:

  • Requirement 1: no reader is kept waiting unless a writer has already seized the object.
  • Requirement 2: a pending writer is not kept waiting indefinitely by readers that arrived after it. A pending writer cannot starve.

0.2Four solutions

In all four, the writer is the same: wait(wrt); // writing; signal(wrt);. Only the fourth adds to it. The readers change:

1st: every reader takes wrt
wait(wrt);// readingsignal(wrt);

Goal 2 fails. The first reader grabs the lock and shuts out the other readers. Only the first reader needs to take the lock, and only the last should release it.

2nd: count readers
readcount++;if (readcount == 1) wait(wrt);// readingreadcount--;if (readcount == 0) signal(wrt);

Race conditions on readcount++ and readcount-- (Lecture 08, §2.2). They need a second mutex around them.

3rd: protect readcount (readers-preference)
wait(mutex);readcount++;if (readcount == 1) wait(wrt);signal(mutex);// readingwait(mutex);readcount--;if (readcount == 0) signal(wrt);signal(mutex);

Correct, and it meets requirement 1. But writers can starve: as long as readers keep overlapping, readcount never reaches 0 and wrt is never released.

4th: add readBlock (starvation-free)
// writerwait(readBlock);wait(wrt); // writing; signal(wrt);signal(readBlock);// readerwait(readBlock);wait(mutex); readcount++;if (readcount == 1) wait(wrt);signal(mutex);signal(readBlock);// reading… exit as in the 3rd

A waiting writer holds readBlock, so readers arriving after it queue behind it. Readers already reading finish, then the writer gets wrt. It is a small variant of the 3rd solution. It meets requirement 2 by giving up requirement 1: a new reader now waits for a writer that is only pending.

All semaphores here start at 1; readcount starts at 0. "Starvation-free" assumes the semaphore queues are FIFO (Lecture 09, §2.2).

0.3Run them

Try itThree readers, two writers

Each line is one atomic step. In the 2nd solution, readcount++ and readcount-- are shown as their separate load and store. "Overlapping readers" is an adversarial scheduler: writers step whenever they can, and a reader leaves only while another reader is still reading, so reading never pauses unless it has to.

Chapter 1

The dining philosophers

Five philosophers, five chopsticks, and a deadlock waiting to happen.

1.1The problem

  • N philosophers sit at a round table with a bowl of rice in the middle. They spend their lives alternating between thinking and eating, and they do not interact with their neighbors.
  • Occasionally one gets hungry and picks up two chopsticks, the ones to its immediate left and right, one at a time. It needs both to eat, and releases both when done.
  • With 5 philosophers, the shared data is the bowl plus semaphore chopstick[5], all initialized to 1. Philosopher i grabs chopstick i with P(chopstick[i]) and releases it with V(chopstick[i]).
while (1) { // think P(chopstick[i]); // left P(chopstick[(i + 1) % N]); // right // eat V(chopstick[(i + 1) % N]); V(chopstick[i]);}

Problem: if every philosopher picks up the left chopstick, every one waits forever for the right. That is a deadlock, a cycle of waiting (Lecture 12).

1.2Three ways out

At most 4 at the tableWith 5 chopsticks and at most 4 seated philosophers, at least one of them can get two chopsticks (pigeonhole). Implement it with a counting semaphore room = 4.
AsymmetryOdd philosophers pick up left then right; even ones pick up right then left. The circular wait can no longer close.
Both or nothingPick up chopsticks only if both are free. Testing both must itself be a critical section. That is the monitor solution in §1.3.
Deadlock-free ≠ starvation-free

A solution in which no one is ever stuck all together can still let one philosopher go hungry forever while the others keep eating. The monitor solution below is an example (§1.4).

1.3The monitor solution

  • Insight 1: pick up two chopsticks only if both are free. Equivalently, a philosopher begins eating only if neither neighbor is eating. That needs a state per philosopher.
  • Insight 2: if I am hungry and a neighbor is eating, ask the neighbor to signal() me when done. The states are thinking, hungry and eating, with a condition variable self[i] per philosopher.
monitor DP { enum {THINKING, HUNGRY, EATING} state[5]; condition self[5]; void pickup(int i) { state[i] = HUNGRY; test(i); if (state[i] != EATING) self[i].wait(); } void putdown(int i) { state[i] = THINKING; test((i + 4) % 5); // left neighbor test((i + 1) % 5); // right neighbor }
void test(int i) { if (state[(i + 4) % 5] != EATING && state[(i + 1) % 5] != EATING && state[i] == HUNGRY) { state[i] = EATING; self[i].signal(); } } init() { for (i = 0; i < 5; i++) state[i] = THINKING; }} // philosopher iwhile (1) { think; DP.pickup(i); eat; DP.putdown(i); }
  • In pickup, the signal() inside test(i) finds no waiter and has no effect. That is harmless, because the state is already EATING and pickup skips the wait. A signal before the wait does not matter here.
  • The real wakeup comes from a neighbor's putdown. Philosophers who finish eating turn hungry neighbors into eating ones.
  • Why (i + 4) % 5 rather than (i − 1) % 5? In C, -1 % 5 is -1, so philosopher 0's left neighbor would index state[-1].
  • The if is safe even under Mesa semantics: only a neighbor's test sets state[i] = EATING, and nothing can undo that before philosopher i runs.

1.4Run the table

Try itFive philosophers, four strategies

Chopstick i lies between philosopher P(i) and P(i+1), counting from P0. A held chopstick is drawn next to its holder. In "monitor" each call to pickup or putdown is one step, because monitor functions run atomically.

Starvation in the monitor solution (the script button above, in "monitor" mode): P0 and P2 start eating, so P1, between them, is hungry and waits. When P0 puts down, it tests P1, but P2 is still eating, so nothing happens. P0 thinks, gets hungry, and eats again. Then P2 does the same. If P0 and P2 always overlap, P1 never eats, although the system as a whole never deadlocks.

Epilogue

Summary and glossary

∎What to take away

  • The classic problems are the bounded buffer, readers–writers and the dining philosophers.
  • Readers–writers: the first reader in takes wrt and the last reader out releases it, with readcount protected by a mutex. That version prefers readers, so writers can starve. Adding readBlock lets a pending writer hold back new readers.
  • Dining philosophers: grabbing left then right can deadlock. The fixes are at most N−1 seated, asymmetric order, or both-or-nothing in a monitor.
  • The monitor solution uses states (thinking, hungry, eating) and one condition per philosopher. It is deadlock-free but not starvation-free.

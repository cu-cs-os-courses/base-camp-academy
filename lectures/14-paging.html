Chapter 0

Recall: where Lecture 13 left us

Contiguous allocation and segmentation both hand out variable-size chunks, and variable-size chunks fragment.

0.1External fragmentation

Over time, repeated allocation and deallocation leave many small, non-contiguous holes of free memory between processes.

The result is external fragmentation: enough free memory in total, but no single hole big enough. In Fig. 0.1, 130 KB is free, and a 100 KB process still doesn't fit.

The OS must then swap processes out to open a large enough hole, or compact memory by moving processes, which is very costly.

0.2What if every chunk were the same size?

Segmentation avoids one huge chunk per process and eases external fragmentation somewhat. But segments still come in every size, so the holes they leave do too.

Now cut the logical address space into pages of one fixed size, and physical memory into frames of the same size.

Any page can go in any free frame. A free frame is never too small, so external fragmentation is gone.

Chapter 1

Pages, frames, and the page table

Once pages can land in any frame, something has to remember where each one went. That is the page table, and the MMU reads it on every memory reference.

1.1The page table

The OS keeps a page tableA per-process array indexed by logical page number. Entry l holds the frame number f where page l lives, plus status bits. for each process. Entry l says which frame holds logical page l.

Given a logical address, the MMUMemory-management unit: hardware in the CPU that translates every logical address to a physical one at run time (Lecture 13). finds its logical page, then looks up the physical frame in the page table.

Frames 2, 5 and 6 are free. They can go to a new process P2, whatever its size.

Hover or tab to a row of the page table to follow it into RAM.

1.2The program still sees one contiguous block

The program sees one contiguous logical address space, 0 to 5119 in Fig. 1.2: code, data, heap, stack.

Physically, its five 1 KB pages sit in frames scattered across RAM.

The MMU performs this translation at run time, for every logical address, using the page table.

1.3Splitting a logical address

Every logical address now has two parts:

  • The most significant bits are the logical page l. It equals the address divided by the page size, and it indexes the page table to find the frame f.
  • The least significant bits are the page offset d: the position inside the page. It is copied into the physical address unchanged.
l = ⌊A ÷ page size⌋  ·  d = A mod page size
Key idea

Page sizes are powers of two, so the split is a cut between two bit positions. The hardware never divides.

Chapter 2

How big is a page table?

One entry per page, one table per process. Multiply it out.

2.1A 32-bit example

  • A typical page is 4 KB. Larger "huge pages" (2 MB, 1 GB) also exist.
  • Take a 32-bit (4 GB) address space with 4 KB pages. The offset within a page takes 12 bits, which leaves 20 bits for the page number.
  • 232 / 212 = 220: about one million entries in the page table.
  • If each entry is 20 bits, that is 220 × 20 bits ≈ 2.62 MB (2.5 MiB) per process, just for its page table.

2.2The general formula

Let the logical address space be 2m bytes, so addresses have m bits, and let pages be 2n bytes, so the offset has n bits.

The page number gets the remaining m − n bits, so the table has 2m−n entries.

table size = 2m−n × (bits per entry) ÷ 8  bytes

Check against §2.1: m = 32, n = 12, 20-bit entries → 220 × 20 ÷ 8 = 2,621,440 bytes.

2.3Size a flat page table

Try itWhat one flat page table costs
How do real 64-bit systems avoid this?

A flat table for a 48-bit address space would be hundreds of gigabytes per process, and almost all of it would say "not mapped". Real CPUs use hierarchical page tables instead: a small top-level table points to lower-level tables, and lower levels exist only for regions the process actually uses. x86-64 walks four levels (five on newer CPUs). See Silberschatz §9.4, "Structure of the Page Table".

Chapter 3

Where the page table lives

Three options. Each fixes the previous one's weakness and brings its own cost.

3.1Option 1: dedicated hardware registers

Keep the whole page table in a bank of registers or dedicated memory inside the MMU.

Good
  • Fast translation on every instruction: the table is right inside the MMU.
Bad
  • Slow context switch: the whole page table must be reloaded for the new process.
  • Expensive hardware, and some tables are very large (one million entries).

3.2Option 2: main memory, plus one register

Store the page table in RAM. Keep a pointer to the current one in a special CPU register, the page-table base register (PTBR)Holds the physical address of the running process's page table. On x86 this register is CR3..

Good
  • Page tables can be large.
  • Fast context switch: reload only the PTBR.

3.3The price: two memory accesses

Option 2 makes translation slow on every instruction. Each instruction fetch needs two memory accesses:

  1. Find the page table in memory (via the PTBR) and index to entry l to get the physical frame number f.
  2. Fetch the instruction itself from frame f at offset d.
Key idea

With the page table in RAM, every memory reference costs two. The next option caches translations so that most references go back to costing one.

3.4Option 3: cache translations in a TLB

Cache a subset of page-table entries in a small set of CPU buffers: the translation look-aside buffer (TLB)A small, fully associative cache of recent page → frame translations inside the MMU. Typically tens to a few thousand entries.. It is a fast fix for option 2's two-step memory access.

Which entries to keep? Several caching policies work:

  • cache the most popular, most frequently referenced pages;
  • cache the most recently used pages.

The TLB

4.1Paging with PTBR and TLB

4.2Hits, misses, and what they cost

The MMU first looks in the TLB for the logical page.

  • TLB hit: go straight to memory with frame f plus offset d. The TLB compares the page against all its entries in parallel, in hardware.
  • TLB miss: do the regular two-step lookup (page table, then data), then update the TLB with the new entry. If the TLB is full, evict one using a replacement policy such as least recently used (LRU; more in Lecture 16).
  • The goal: maximize hits, minimize misses. The effective access time shows why.

Chapter 5

Paging and the L1/L2 caches

A data cache can be looked up by virtual address or by physical address. Each choice has its own problem.

5.1Virtually or physically indexed?

How does the MMU interact with the L1 or L2 data and instruction caches? It depends on whether the cache is indexed by virtual or physical address.

Physically indexed: the MMU must translate before the cache can be consulted. Slower, but every entry is uniquely identified by its physical address.

Virtually indexed: the cache can be checked right away, without the MMU. On a miss, the MMU still has to translate.

5.2The homonym problem

A virtually indexed cache has a problem. After a context switch, the new process may use the same virtual address V as the previous one, and a cache indexed only by V hands back the previous process's data. Pick a fix and see what P2 gets:

Try itSame address, different process
All three fixes, with their costs
  • Flush the cache on each context switch. The process gets the whole cache to itself, but has to rebuild it from cold.
  • Add an address-space ID (process ID) to each cache entry. Only the right process's data comes back for V. Needs hardware support and an extra comparison, and the processes now share the cache space.
  • Give every process non-overlapping virtual addresses. Unlikely: it breaks the model that each process is compiled and runs independently in its own address space [0, MAX].

5.3In practice: L1 virtual, L2 physical

  • Most L1 caches are virtually indexed, which is fast.
  • Most L2 caches are physically indexed. Each entry is unique, so there are no collisions. That suits shared library code and data: if several processes share the same code, the cache stores it once.
  • So the virtually indexed cache is a small, fast L1, and the physically indexed cache is a much larger L2.
Going further: "virtually indexed, physically tagged"

Many modern L1 caches are VIPT. They pick the cache set using only the page-offset bits, which are the same in the virtual and the physical address, so the lookup starts in parallel with the TLB. They then compare the physical frame number from the TLB against the stored tag. That keeps L1 fast and avoids homonyms without flushing. The trick works only while the set index fits inside the offset bits, which is one reason L1 caches stay small.

Chapter 6

Shared pages

Two page tables can point at the same frame. That one fact gives shared libraries, shared memory, and a cheap fork().

6.1Shared code and shared memory

Page tables of different processes can point to the same physical frames.

  • Shared code. Apps A and B run as processes P1 and P2 and share C library functions in two pages of code, lib1 and lib2. Each process keeps its own data. Both page tables map lib1 and lib2 to the same frames, so RAM holds one copy.
  • Shared-memory IPC. Two or more processes that want to share memory can point their page tables at the same data frames. That is how shared-memory IPC works (Lecture 4).

6.3Shared pages and fork()

  • fork() gives the child a copy of the parent's entire address space, code included.
  • Rather than duplicating those pages, map the child's pages to the same frames as the parent's, and mark them read-only.
  • When either process writes to a shared page, the write faults. The kernel copies that one page into a free frame and points the writer's entry at the copy. This is copy-on-writeCOW: share pages read-only after fork(), and copy a page only when someone first writes to it. Most children call exec() soon, so most pages are never copied.. Lecture 3 introduced it; Lecture 15 covers it in depth.

Chapter 7

Persistent internal fragmentation

Paging trades external fragmentation for a smaller, bounded kind.

7.1The last page is rarely full

  • Paging has no external fragmentation: any free frame fits any page.
  • It does have internal fragmentation. A 4097-byte process with 4 KB (4096-byte) pages needs two pages (8 KB), and 4095 bytes of the second page are wasted inside it.
  • The OS also keeps a frame table (free-frame pool) to track which physical frames are free.

Epilogue

Summary and glossary

∎What to take away

  • Paging cuts logical memory into pages and RAM into frames of the same size. No external fragmentation; at most one page of internal fragmentation per process.
  • Address = page l | offset d. The per-process page table maps l → f; d passes through.
  • A flat page table is big: 2m−n entries. Keeping it in RAM behind the PTBR makes context switches cheap, but doubles memory accesses.
  • The TLB caches translations, so most references need one memory access. Context switches force a flush unless entries carry an ASID.
  • Pointing two page tables at one frame gives shared libraries, shared-memory IPC, and copy-on-write fork().

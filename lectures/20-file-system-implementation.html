Chapter 0

What a file system stores

Some of it lives on disk and survives power loss. Some lives in RAM and makes it fast.

0.1Tree-structured directories

Files are organized in a tree of directories. The fully qualified name of foo.txt is /users/carl/SeniorProject/foo.txt, and everything before the file name is its path.

  • hierarchical organization that each user can customize,
  • unique naming, so carl's mail does not conflict with alice's mail, and
  • users can share and reach files in other directories.

0.2On disk

The whole file system is stored on disk or flash, in the five main elements below.

  1. the entire directory tree,
  2. each file's attributes, in a file control block (FCB),
  3. each file's data,
  4. a boot block, typically the first block of a volume, with what is needed to boot an OS from it (empty if there is none), and
  5. a volume control block with the volume's details, such as which blocks are free, how many blocks, and the block size.

0.3In memory

The kernel keeps the four structures below in RAM.

  1. recently used parts of the directory tree, for fast lookup,
  2. a system-wide open-file table (OFT) with process-independent information about each open file, namely its FCB and an open count of the processes that have it open,
  3. a per-process OFT with every file that process opened, holding access rights and a current file position pointer, where the process is reading or writing, and
  4. a mount table of the devices whose file systems are mounted as volumes.

Chapter 1

Open, read, close

The three calls that move a file's information from disk into those tables and back.

1.1What open("foo.txt") does

  1. Search the directory structure for foo.txt. Fast if the directory entries are in memory. Otherwise, read them from disk and cache them.
  2. The directory entry points to the file's FCB on disk. Read the FCB, copy it into the system OFT, which caches it for later opens, and increment the file's open count.
  3. Add an entry to the per-process OFT pointing to the FCB in the system OFT.
  4. Return a file descriptor (handle), which is the index of that per-process entry.

1.2read and close

read(fd, buffer, size). The descriptor indexes the per-process OFT, which points to the FCB in the system OFT. The FCB says where the data blocks are on disk. The data is copied into the user's buffer, and the file position advances.

close(fd) takes the three steps below.

  1. Remove the entry from the per-process OFT.
  2. Decrement the file's open count in the system OFT.
  3. If the count is now 0, write any metadata changes in the FCB (its modification date, for instance) back to disk.
Watch out

Until that write-back, the FCB in memory and the FCB on disk disagree. File system designers must keep this temporary inconsistency in mind. Chapter 5 is about what happens if the machine crashes during it.

Advisory (optional) locksProcesses may take locks, but the OS does not force anyone to check. It is up to the users to synchronize access. UNIX policy.

Chapter 2

File allocation

Which disk blocks hold a file, and how the file system remembers. Five approaches follow. The running example is one 4-block file, foo, on a 25-block disk shared with other files (hatched).

2.1Approach 1, contiguous allocation

A file of n blocks gets a start block b and blocks b, b+1, …, b+n−1. The header stores only start and length. It is fast, because the blocks are next to each other, so seeks are short.

  • External fragmentation, the same problem as fitting processes into RAM contiguously, with the same choices of first fit, best fit, or compaction (defragmenting the disk, late at night).
  • The file's size may not be known in advance. Allocate more than estimated. If it still outgrows its space, copy it to a larger free hole.
  • Slow-growing files waste space. A file that will one day need 1 MB, growing 1 byte a second, wastes most of a 1 MB allocation for most of its life.

2.2Borrowing from paging

Page tables solved external fragmentation for processes (Lecture 14). Apply the same idea to files, as follows.

  • Divide the disk into fixed-size blocks, as RAM was divided into frames.
  • Let a file's blocks sit anywhere on the disk, not necessarily together.
  • Keep a data structure that says which file block is on which disk block, such as a linked list or an index, and their variants.

2.3Approach 2, linked allocation

Each file is a linked list of disk blocks, and every block holds a pointer to the next. The header needs only the start (and, conveniently, the end).

Good
  • no external fragmentation, no need to know the size in advance,
  • minimal header, good for sequential access, easy to insert in the middle.
Bad
  • random access is very slow, because you follow the list to the block you want,
  • every block spends space on a pointer,
  • fragile, because one corrupted pointer loses the rest of the file.

2.4Approach 3, the file allocation table (FAT)

An important variation of linked allocation is to take the pointers out of the data blocks and put them in one table at the beginning of the volume. Entry k of the FAT holds the number of the block after block k. A special EOF value ends the list, and unused blocks are 0.

  • Allocating a block is simple. Find the first 0 entry.
  • Random access is faster than a pure linked list, because all pointers sit together near the start of the disk, so little seeking (and the FAT is often cached in RAM).
  • But finding block j still means walking j links.

FAT came from MS-DOS and Windows 95/98 (Bill Gates wrote the original). FAT16 and FAT32 name the size of a FAT entry. NTFS replaced it from Windows NT on, but FAT lives on in USB sticks and SD cards.

2.5Approach 4, indexed allocation

Collect all of a file's pointers into one list, the index block. Entry j points to the file's j-th block on disk. It looks like a page table, except that it can grow.

  • Unlike the FAT, the index block can live anywhere on the disk, and it is just a linear list for one file.
  • No external fragmentation, no size needed in advance, and no list to walk, since you index straight into the block.
  • But how big should the index block be? Too small limits file size, and too big wastes space on small files. The fixes are to link index blocks together, or use a multilevel index (§2.7).

2.7Approach 5, multilevel indexed allocation

It works like hierarchical page tables. A first-level index block lists the second-level index blocks, and each second-level block lists the data blocks for its section of the file.

The problem is that small files pay the same as large ones. Every access walks the same number of levels, so even the data of a 100-byte file takes at least 4 block reads, namely header, first level, second level, and data.

2.8The UNIX inode

UNIX mixes the approaches in one small index of 15 pointers inside the inode, listed below.

  • 12 direct pointers to data blocks, so small files need nothing else and little space is wasted,
  • a single indirect pointer to an index block,
  • a double indirect pointer, an index of index blocks, and
  • a triple indirect pointer, one more level.

Small files stay cheap, large files can span a huge number of blocks, and a small file that grows into a large one just starts using the indirect pointers.

2.9Files vs. processes

Both problems map an entity onto storage. A process's address space maps onto RAM frames through page tables, and a file's data maps onto disk or flash. The differences are below.

  • An address space has a fixed size known in advance. Files grow and shrink, so they need a more flexible map than a page table, which cannot grow.
  • An address space can be sparse and mostly unused, while a file's data is all in use.

Chapter 3

Free-space management

To allocate blocks, the file system must know which ones are free. Four ways to keep that "list".

3.1Four representations

1 · Bit vector (bitmap)One bit per block, concatenated into an array. Bit j tells whether block j is allocated. Here bit = 1 means free, 0 allocated.
2 · Linked listLink all free blocks together. It tracks only the free blocks (a bitmap also spends bits on allocated ones), and the first free block is found immediately. But allocating many blocks at once means traversing the list, which is slow.
3 · GroupingA linked list whose list blocks each store n−1 pointers to free blocks, plus a pointer to the next list block. Many free blocks can be allocated at once.
4 · CountingGrouping, plus a count on each entry of how many free blocks follow the one it points to. Even faster allocation of large numbers of free blocks.

Chapter 4

Performance

Most tricks either keep something in memory or put things on disk where the head will be.

4.1In memory and on disk

In memory
  • cache the FCBs of open files,
  • cache directory entries, and hash the directory tree to find an entry and check whether it is in memory quickly,
  • cache file data.
On disk
  • for file data, indexed allocation is generally faster than walking a linked list,
  • for free blocks, counting or grouping allocates many blocks quickly,
  • for a smarter layout, keep the inode near the file's data, and the file's blocks near each other (Lecture 19),
  • the disk controller can have its own cache of data and FCBs.

4.2Read-ahead and asynchronous writes

  • Read-ahead. If the OS knows the access is sequential, it reads the requested page and several following ones into the cache, before they are asked for.
  • Asynchronous writes. Delay writing file data until later. write() returns without waiting for the disk, taking disk I/O off the program's critical path. The disk can schedule and group nearby writes. And if the data changes again soon, one write may be skipped entirely.
  • Sometimes synchronous writes are preferable, for example for FCB metadata changed during open(). Chapter 5 explains why.

Chapter 5

Reliability and fault recovery

Part of the file system lives in RAM, and a power loss erases it. The OS must recover gracefully anyway.

5.1A fragile file system

Directories, file metadata and file data may all be cached in memory, and all be modified there. On a power loss, every modification not yet saved to disk is gone, and the copy on disk may be inconsistent.

  1. Asynchronous writes create inconsistency between memory and disk. Promised writes of file data may be lost, and directory information in RAM can be newer than on disk. UNIX's answer is to cache directory entries for reads, but write any change to metadata or free-space allocation synchronously, before the data blocks.
  2. Even synchronous writes can fail halfway, leaving a half-written directory entry, FCB, or data block.
  3. Complex operations can be interrupted in the middle. create() updates the directory, the FCB, data blocks, and free-space structures. Crash after the FCB is created, and the directory points to an FCB whose index block was never fully allocated.

5.2Consistency checkers

Run a checker such as fsck (UNIX) or chkdsk (MS-DOS) after a crash. With linked allocation it checks every list and every FCB against the directory structure (similar checks for indexed allocation), and verifies each allocated block's checksum.

But it is computationally intensive and takes a long time on a whole file system, and it can detect an error without being able to correct it.

5.3Log-based recovery

  • The OS keeps a log (journal) on disk of every operation on the file system. After a failure, it consults the log to reconstruct the file system.
  • Write-ahead logging. Each operation is written to the log before it is performed on the data, such as "I'm about to write this directory entry / file header / data block", then "I just finished".
  • Operations are grouped into transactions. A create() has many steps, and you want the whole file created or nothing at all. Transactions are atomic, meaning they succeed in their entirety or not at all.
  • A transaction Ti is logged as <Ti start>, then records like write(X, old, new), then <Ti commit>. Each record keeps the transaction, the data item, and both the old and the new value, so recovery can go either way.
  • Once <commit> is in the log, the log alone can finish the transaction after a crash, so the system call may return. The actual write of X to disk may come much later, and transactions may overlap in the log.

5.4Checkpoints, redo, undo

A checkpoint record confirms that every full transaction before it has been both committed to the log and executed on disk. Relative to the latest checkpoint, transactions fall into three groups.

  • completed means full transactions before the checkpoint. Nothing to do, and they can be removed from the log, or overwritten if it is circular.
  • committed means full transactions after the checkpoint, possibly not yet on disk. After a crash, redo() them.
  • partial means a start without a commit. After a crash, undo() them, rolling back to the old values. These are aborted transactions.

In normal operation the file system periodically replays committed transactions onto disk and appends a new checkpoint, turning them into completed ones.

journalingthe log is a separate structure next to the normal file system. NTFS logs only metadata changes (file headers, directory entries), not file datasafe metadata, but data written twice if it is journaled too

5.7ext4's three journal modes

journalBoth metadata and file data are logged. The safest mode, at the cost of two disk writes for every write.
ordered (default)Only metadata is logged, and file contents are guaranteed to reach disk before the metadata is committed in the journal. The default on many Linux distributions.
writebackOnly metadata is logged, with no ordering guarantee, so a crash can leave a file whose metadata is new but whose contents are garbage. Fastest, least reliable.

Epilogue

Summary and glossary

∎What to take away

  • On disk are the directory tree, FCBs (inodes), data, boot block, and volume control block. In memory are cached directories, the system OFT with open counts, per-process OFTs with file positions, the mount table.
  • open finds the FCB and caches it. read follows descriptor → FCB → blocks. close writes metadata back when the last user closes.
  • Allocation methods are contiguous (fast, fragments), linked (flexible, slow random access, fragile), FAT (links in a table), indexed (direct access), multilevel and the UNIX inode (small files cheap, large files possible).
  • Free space is tracked by bitmap, linked list, grouping, or counting.
  • Crashes are handled by synchronous metadata writes, fsck, and write-ahead logging with transactions, checkpoints, redo and undo. Journaling, log-structured and copy-on-write file systems build on these ideas.
In the lab

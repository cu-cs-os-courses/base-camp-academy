A program on disk does nothing. The OS turns it into a process. A process has memory for its code, data, heap, and stack, a program counter, and a record that the kernel keeps about it. In this lecture, we follow a process from its creation by fork() through exec(), wait(), and exit(). We also discuss the states it passes through, the queues it waits in, and the context switch that lets many processes share one CPU.

Chapter 0

From program to process

How source code becomes an executable, and an executable becomes something running.

0.1Linkers and loaders

  • Source code is compiled into relocatable object files, which are designed to be loaded at any physical memory location.
  • The linker combines these object files and libraries into one binary executable. The executable lives on secondary storage.
  • The loader brings the executable into memory to run. Relocation assigns final addresses to the program's parts and adjusts code and data to match.
  • Modern systems do not link libraries into every executable. Instead, dynamically linked libraries (DLLs, .so files) are loaded as needed and shared by all programs that use the same version. Note that object and executable files use standard formats (ELF on Linux), so that the OS knows how to load them.

0.2The process concept

  • A process is a program in execution. Its execution progresses sequentially, one instruction at a time (for a single-threaded process).
  • A program is passive, namely an executable file on disk. In contrast, a process is active. A program becomes a process when it is loaded into memory through a mouse click or a command line. One program can become several processes. For example, several users can run the same editor.
  • A process consists of several parts.
    • the program code, or text section, loaded from the binary,
    • the data section with global variables, also from the binary,
    • its current activity, namely the program counter and processor registers, and
    • a stack of temporary data (function parameters, return addresses, local variables) and a heap of memory allocated at run time, both set up by the OS.

Chapter 1

Creating processes

On a UNIX system, every process was created by another process.

1.1Parents, children, and the process tree

  • A parent process creates children, and these children create other processes. As such, the processes form a tree, and each process is identified by a process identifier (pid).
  • Resource sharing. Parent and children share all resources, a subset of them, or none.
  • Execution. Parent and children run concurrently, or the parent waits for the children to terminate.
  • Address space. The child is a duplicate of the parent, or the child has a new program loaded into it.

1.2fork()

  • fork() creates a new process, which is an exact copy of the parent. All code and data are the same, and all addresses are mapped to match.
  • The child starts executing at the same point as the parent, namely just after returning from fork().
  • fork() returns an int, which is 0 in the child and the child's pid in the parent (−1 on failure). The code tells the two processes apart by this value.
  • Copying the whole address space is expensive. Therefore, the kernel copies lazily. Specifically, pages are shared until one side writes to them (copy-on-write, Lectures 14–15).
int main(void) { pid_t pid = fork(); if (pid < 0) { /* error */ perror("fork"); return 1; } else if (pid == 0) { /* child */ execlp("/bin/ls", "ls", NULL); } else { /* parent */ wait(NULL); printf("Child Complete\n"); } return 0;}

1.4exec() and wait()

  • The execlp() / exec*() library calls invoke the execve() system call, which loads a new program into the calling process's memory. The calling code is erased, and exec returns only if it fails.
  • UNIX creates a new process that runs a new program in a new address space by calling fork() and then execve(). The shell does exactly this for every command you type.
  • The parent calls wait() to wait for the child to terminate.
  • In contrast, Windows creates a process and loads its program in one call, CreateProcess(), which takes ten parameters.

1.6Why applications are OS specific

  • An application compiled on one system usually does not run on another, because each OS has its own system calls, file formats, and so on.
  • An application can run on multiple OSes if it is written in an interpreted language (Python, Ruby) whose interpreter exists everywhere, in a language with its own VM (Java), or in a standard language (C) that is compiled separately for each OS.
  • The application binary interface (ABI) is the architecture-level equivalent of an API. It defines how compiled code interfaces on a given OS and CPU (register use, calling convention, system-call numbers).

Chapter 2

Process termination

Ending a process properly requires both the child and the parent.

2.1exit and wait

  • A process executes its last statement and asks the OS to delete it with exit(). Its status goes to the parent through wait(). The OS frees its resources, such as memory.
  • A parent can also terminate a child. On UNIX, the parent does so with kill(). Note that the slides' abort() is what a process calls to end itself abnormally. A parent terminates a child in three cases. First, the child has exceeded its resources. Second, the child's task is no longer needed. Third, the parent is exiting, and the OS does not let children outlive their parent.
  • Some OSes enforce exactly this rule. In such an OS, the OS terminates all children, grandchildren, and so on, which is called cascading termination.
  • pid = wait(&status) returns the status and pid of a terminated child. waitpid() waits for a particular child.

2.2Zombies and orphans

ZombieA child that has terminated but whose parent has not yet called wait(). Its memory is freed. However, its PCB entry stays, so that the exit status can be collected. ps shows it as Z or <defunct>.
OrphanA child whose parent terminated without waiting for it. On Linux, it is re-parented to init/systemd (pid 1), which calls wait() for it when it ends. Therefore, orphans do not stay zombies forever.

You can step through both cases in §1.5 by choosing "parent never waits" or "parent exits first".

Chapter 3

Process state and the PCB

In this chapter, we discuss what the process manager keeps track of for every process.

3.1Five states

  • new means being created.
  • ready means waiting to be assigned a processor.
  • running means instructions are being executed.
  • waiting means waiting for some event, such as I/O completion.
  • terminated means finished execution.

Only one process per core is running at a time. However, many processes can be ready or waiting.

3.2The process control block

The kernel keeps a process control block (PCB), also called a task control block or process descriptor, for every process. The PCB holds the items below.

  • process state. Running, waiting, …
  • program counter. The next instruction to execute.
  • CPU registers. The contents of all process-centric registers.
  • scheduling information. Priority, scheduling-queue pointers.
  • memory-management information. The memory allocated to the process.
  • accounting information. CPU used, time since start, limits.
  • I/O status. Devices allocated, list of open files.

PCBs live in kernel memory and are managed by the process manager. Note that they are kept next to (not inside) each process's own code, data, heap, and stack.

With threads (Lecture 05), a process has several program counters. Therefore, the PCB needs room for each thread's details.

Chapter 4

Scheduling and context switches

With many ready processes and one core, queues determine which process waits where. A context switch then hands the core over to another process.

4.1Scheduling queues

  • The process scheduler selects one of the available processes to run next on a CPU core. Its goal is to maximize CPU use and to switch quickly.
  • To implement this, the kernel keeps scheduling queues. The ready queue holds processes in memory, ready to run. Wait queues hold processes waiting for an event, such as I/O. Processes migrate among the queues.
  • The policy, namely which ready process runs next, is the subject of Lectures 06–07.

4.3The context switch

  • When the CPU switches to another process, the kernel saves the state of the old process in its PCB and loads the saved state of the new one. This is a context switch.
  • Context-switch time is pure overhead, because no useful work is done while switching. The more complex the OS and the PCB are, the longer a context switch takes (typically a few microseconds).
  • Context-switch time also depends on hardware support. For example, some CPUs have several register sets, so several contexts can be loaded at once.

4.4Chrome, a multiprocess application

  • Many web browsers ran as a single process. In such a browser, if one site causes trouble, the whole browser hangs or crashes.
  • In contrast, Chrome is multiprocess. A browser process manages the UI as well as disk and network I/O. Each site has a renderer process, which renders HTML and runs JavaScript. The renderer is sandboxed away from disk and network (Lecture 22). There is also one process per plug-in type.
  • As such, the OS's process isolation becomes the application's fault isolation and security boundary.

Epilogue

Summary and glossary

∎What to take away

  • Compilers and linkers turn source code into an executable. Loaders turn an executable into a process with text, data, heap, and stack.
  • fork() copies the caller, and it returns 0 in the child and the child's pid in the parent. exec() replaces the program, and wait() collects a child's exit status.
  • A terminated child that has not yet been waited for is a zombie. A child whose parent died is an orphan, and pid 1 adopts it.
  • Processes move among the new, ready, running, waiting, and terminated states. The kernel records everything about each process in its PCB (task_struct).
  • The scheduler moves processes between the ready queue, the CPU, and wait queues. A context switch saves one PCB's worth of state and loads another's. This switch is pure overhead.

Many program counters,
one address space

A process gives each program its own memory and one program counter. A thread keeps the memory and adds more program counters. As such, a process can have several streams of execution that share code, data, and heap, and each stream has its own stack and registers. Communication between them is as cheap as a memory write. However, so is a mistake. This lecture ends with a first look at what happens when two threads access the same variable.

Chapter 0

Threads and processes

What a thread shares with its siblings, and what it keeps for itself.

0.1Multiple threads in one process

  • All threads of a process share its code, data, heap, and open files.
  • Each thread has its own program counter, register state, and stack.
  • The kernel keeps the PCB for the process and control data for each thread. On Linux, every thread is in fact a separate task_struct, which shares the memory (mm) and files with its siblings.

0.2Applications, processes, threads

  • An application can consist of several processes, and each process is dedicated to a task (UI, computation, communication). Chrome is an example.
  • Each process can consist of several threads. Therefore, an application may consist of many processes and many threads.
  • A classic example is a multithreaded server. One thread listens for requests. For each request, it creates a new thread (or takes one from a pool) to service the request. Then, it goes back to listening.

0.3Why threads?

EconomyThreads are cheaper to create than processes. They are also cheaper to switch, because there are no MMU registers to reload and no TLB to flush (Lecture 14). In Solaris, switching between processes was about 5× slower than switching between threads.
Shared resourcesThreads do not duplicate code, data, heap, or PCBs. As such, they scale better, for example in a web server with thousands of connections.
Easy communicationThreads share memory. Therefore, communication is a read or write of the same memory. In contrast, message-passing IPC is slow. Shared-memory IPC (Lecture 04) comes closest to threads.

Chapter 1

Where threads live, user space or kernel

A thread library can manage threads entirely in user space, or let the kernel manage them.

1.1User-space threads

  • A thread library gives the programmer an API to create and manage threads. The library is implemented either entirely in user space or by the kernel.
  • User-space threads are usually cooperatively multitasked. In other words, they voluntarily give the CPU to each other through the library. They are also called fibers (or green threads, coroutines).
  • The OS is unaware of them and sees only the process. Therefore, if one user thread blocks in a system call, the whole process blocks (the many-to-one case).

1.2Kernel threads and mappings

  • Kernel threads are supported by the OS. The kernel sees each thread and schedules it. Linux, macOS, and Windows all support them.
  • User threads map onto kernel threads one-to-one (Linux, Windows), many-to-one, or many-to-many.

1.3Three main libraries

POSIX pthreadsA POSIX standard (IEEE 1003.1c) API for creating and synchronizing threads. It specifies behavior, not implementation. As such, the implementation may be user-level or kernel-level. On Linux, it is kernel-level and one-to-one.
Win32A kernel-level thread library on Windows.
JavaThreads managed by the JVM, typically on top of the threads of the underlying OS.

Chapter 2

The pthreads API

This chapter covers thread management. Semaphores, mutexes, and condition variables come in Lectures 08–10.

2.1Create, exit, join

  • pthread_create(&tid, attr, start_routine, arg) returns the ID of the new thread in tid. attr sets attributes (NULL for defaults). start_routine is the C function the thread runs, and arg is its single argument, passed as a void *.
  • pthread_exit(value) terminates the calling thread and returns value as a pointer. Returning from start_routine has the same effect.
  • pthread_join(tid, &value) blocks until thread tid terminates, and then it collects the return value of that thread (NULL if you do not need it). It returns 0 on success and an error number otherwise. In other words, it is to threads what wait() is to processes.

2.3Why are processes still used?

  • Some applications are sequential by nature and not easily parallelized.
  • Threads have no fault isolation between them. One crashing thread brings down the whole process. In contrast, a crashed process leaves the other processes running in their own address spaces.
  • Writing thread-safe and reentrant code is hard (Chapters 3–4). Processes avoid this problem with separate copies of data and heap, except when they use shared-memory IPC. Note that the OS kernel is itself a concurrent program, and it has the same problem.

Chapter 3

When threads collide

Shared memory means shared variables, and the scheduler chooses the order.

3.1Concurrency and parallelism

  • Concurrency on a single core means that the instructions of the threads are interleaved over time, as the scheduler switches among them.
  • Parallelism on multiple cores means that instructions actually run at the same time.
  • In both cases, the program cannot assume any particular order between the instructions of two threads.

3.3Data race vs. race condition

Data raceTwo threads access the same memory location without synchronization, and at least one access is a write. It is a low-level memory behavior, and it is not necessarily a bug.
Race conditionThe execution order of the threads causes incorrect behavior. It is a high-level logic flaw.

The two terms overlap, but neither implies the other. A statistics counter that two threads increment with stats_counter++ has a data race. However, if missing a few increments is acceptable, it is not a race condition. Conversely, a race condition without a data race requires synchronization in the first place, for example two properly locked steps that execute in the wrong order (Lecture 08).

Careful in C

Since C11, a data race on a plain (non-atomic) variable is undefined behavior. Therefore, the compiler may assume that it never happens. Code for a variable that is "only a counter" should use atomic_ulong with relaxed operations. This choice states the intent and keeps the program well-defined.

Chapter 4

Thread-safe and reentrant code

A piece of code can make two different promises.

4.1Definitions

Thread-safeThe code behaves correctly during simultaneous or concurrent execution by multiple threads. The kernel itself is a concurrent program, with user threads in kernel mode, kernel threads, and interrupt handlers.
ReentrantA single thread can be interrupted in the middle of the code and re-enter it without breaking anything. Re-entry comes from recursion, another thread, or a signal handler. In the kernel, it comes from recursive calls, system calls from several threads, and interrupt handlers.

In both cases, "correct" means what the programmer intended.

Epilogue

Summary and glossary

∎What to take away

  • Threads of a process share code, data, heap, and files, and each thread has its own PC, registers, and stack. Threads are cheaper to create and switch, and they communicate through memory.
  • User-space threads are invisible to the kernel. Therefore, one blocking call blocks them all (many-to-one). Kernel threads, usually one-to-one, are scheduled individually.
  • pthreads provides pthread_create, pthread_exit, and pthread_join.
  • Processes remain useful for fault isolation and for avoiding shared-state bugs.
  • Interleaved load, compute, and store steps can lose updates. A data race is an unsynchronized access that includes a write. A race condition is incorrect behavior caused by ordering.
  • Thread-safe means correct under several threads. Reentrant means correct when one thread re-enters the code, for example from a signal handler. Neither implies the other.

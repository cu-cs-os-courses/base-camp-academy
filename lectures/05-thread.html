Chapter 0

Threads and processes

What a thread shares with its siblings, and what it keeps for itself.

0.1Multiple threads in one process

  • All threads of a process share its code, data and heap, and its open files.
  • Each thread has its own program counter, register state and stack.
  • The kernel keeps the PCB for the process plus control data for each thread. On Linux, every thread is in fact its own task_struct that shares the memory (mm) and files with its siblings.

0.2Applications, processes, threads

  • An application can consist of several processes, each dedicated to a task (UI, computation, communication): recall Chrome.
  • Each process can consist of several threads, so an application may be many processes and many threads.
  • A classic example is a multithreaded server: one thread listens for requests; for each request it creates a new thread (or takes one from a pool) to service it, and goes back to listening.

0.3Why threads?

EconomyCheaper to create than processes, and cheaper to switch: no MMU registers to reload, no TLB to flush (Lecture 14). In Solaris, switching between processes was about 5× slower than between threads.
Shared resourcesNo duplicated code, data, heap or PCBs. More scalable: a web server with thousands of connections.
Easy communicationThreads share memory, so communication is a read or write of the same memory. Message-passing IPC is slow; shared-memory IPC (Lecture 04) comes closest.

Chapter 1

Where threads live: user space or kernel

A thread library can manage threads entirely in user space, or let the kernel manage them.

1.1User-space threads

  • A thread library gives the programmer an API to create and manage threads, implemented entirely in user space or by the kernel.
  • User-space threads are usually cooperatively multitasked: they voluntarily give the CPU to each other through the library. They are also called fibers (or green threads, coroutines).
  • The OS is unaware of them: it sees only the process. So if one user thread blocks in a system call, the whole process blocks (the many-to-one case).

1.2Kernel threads and mappings

  • Kernel threads are supported by the OS: the kernel sees threads and schedules each one. Linux, macOS and Windows all support them.
  • User threads map onto kernel threads one-to-one (Linux, Windows), many-to-one, or many-to-many.

1.3Three main libraries

POSIX pthreadsA POSIX standard (IEEE 1003.1c) API for creating and synchronizing threads. It specifies behavior, not implementation: user-level or kernel-level. On Linux it is kernel-level, one-to-one.
Win32A kernel-level thread library on Windows.
JavaThreads managed by the JVM, typically on top of the underlying OS's threads.

Chapter 2

The pthreads API

Thread management here; semaphores, mutexes and condition variables in Lectures 08–10.

2.1Create, exit, join

  • pthread_create(&tid, attr, start_routine, arg) returns the new thread's ID in tid. attr sets attributes (NULL for defaults); start_routine is the C function the thread runs; arg is its single argument, passed as a void *.
  • pthread_exit(value) terminates the calling thread, returning value as a pointer. Returning from start_routine does the same.
  • pthread_join(tid, &value) blocks until thread tid terminates and collects its return value (NULL if you do not care). It returns 0 on success, an error number otherwise. It is to threads what wait() is to processes.

2.3Why are processes still used?

  • Some applications are sequential by nature and not easily parallelized.
  • No fault isolation between threads: one crashing thread brings down the whole process. A crashed process leaves the others running in their own address spaces.
  • Writing thread-safe and reentrant code is hard (Chapters 3–4). Processes avoid it with separate copies of data and heap, except when they use shared-memory IPC. The OS kernel, a concurrent program itself, has the same problem.

Chapter 3

When threads collide

Shared memory means shared variables, and the scheduler chooses the order.

3.1Concurrency and parallelism

  • Concurrency on a single core: the threads' instructions are interleaved over time, as the scheduler switches among them.
  • Parallelism on multiple cores: instructions really run at the same time.
  • Either way, the program cannot assume any particular order between two threads' instructions.

3.2What is X?

X = 7 is shared. Thread 1 runs X = X * 2; print X; thread 2 runs X = X + 1; print X. Each statement X = X op k is really three machine steps: load X into a register, compute, store it back. You be the scheduler:

3.3Data race vs. race condition

Data raceTwo threads access the same memory location without synchronization, and at least one access is a write. A low-level memory behavior, not necessarily a bug.
Race conditionThe threads' execution order causes incorrect behavior. A high-level logic flaw.

They overlap, but neither implies the other. A statistics counter that two threads increment with stats_counter++ has a data race; if missing a few increments is acceptable, it is not a race condition. A race condition without a data race needs synchronization to exist first, for example two properly locked steps executed in the wrong order: Lecture 08.

Careful in C

Since C11, a data race on a plain (non-atomic) variable is undefined behavior: the compiler may assume it never happens. "It's only a counter" code should use atomic_ulong with relaxed operations, which states the intent and keeps the program well-defined.

Chapter 4

Thread-safe and reentrant code

Two different promises a piece of code can make.

4.1Definitions

Thread-safeBehaves correctly during simultaneous or concurrent execution by multiple threads. The kernel itself is a concurrent program: user threads in kernel mode, kernel threads, interrupt handlers.
ReentrantA single thread can be interrupted in the middle of the code and re-enter it without breaking anything. Re-entry comes from recursion, another thread, or a signal handler; in the kernel, from recursive calls, system calls from several threads, and interrupt handlers.

In both cases "correct" means what the programmer intended.

Epilogue

Summary and glossary

∎What to take away

  • Threads of a process share code, data, heap and files; each has its own PC, registers and stack. They are cheaper to create and switch, and communicate through memory.
  • User-space threads are invisible to the kernel, so one blocking call blocks them all (many-to-one). Kernel threads, usually one-to-one, are scheduled individually.
  • pthreads: pthread_create, pthread_exit, pthread_join.
  • Processes remain useful for fault isolation and for avoiding shared-state bugs.
  • Interleaved load/compute/store steps can lose updates. A data race is unsynchronized access with a write; a race condition is wrong behavior caused by ordering.
  • Thread-safe: correct under several threads. Reentrant: correct when one thread re-enters it, e.g. from a signal handler. Neither implies the other.

Chapter 0

Why synchronize

Concurrency and parallelism both let two pieces of code access the same data at the same time.

0.1Recall Lecture 05

  • Concurrency on one core means the scheduler interleaves threads to give the appearance of simultaneous execution. The scheduler can preempt a thread at any point (Lecture 06).
  • Parallelism on several cores means truly simultaneous execution. It has the same problem, and more ways to trigger it.
  • Processes, threads, and the OS kernel itself all run concurrently. Concurrent access to shared data can leave it inconsistent. Sometimes the inconsistency is tolerable, and sometimes it is fatal.

0.2A race inside the kernel

Processes P0 and P1 both call fork(). The kernel assigns child PIDs from a variable, next_available_pid. Each fork reads the variable, uses it, and then increments it.

If both forks read the variable before either one increments it, the same PID is assigned to two different processes. Unless a mechanism prevents P0 and P1 from racing on next_available_pid, the result depends on timing. This is a race condition.

Chapter 1

The critical-section problem

We identify the code that accesses shared data, and then require that only one process runs it at a time.

1.1Entry, critical, exit, remainder

  • Keeping data consistent requires mechanisms that order cooperating processes or threads, so that no two use a shared resource at the same time. The resource can be a variable, a table, a file, and so on.
  • The part of a program that accesses the shared resource is its critical section.
  • A process asks for permission in an entry section and then runs the critical section. The critical section may be followed by an exit section. Then the process runs the remainder section.
while (true) { entry sectionask critical sectionshared data exit sectionrelease remainder section}

Fig. 1.1 shows the general structure of a process Pi.

1.2An example

Two processes each read values and keep a running average in the shared variables data, count, and avg. The whole add_new_value function is a critical section. If P2 runs count++ between P1's data[count] = v and P1's count++, a slot is skipped. As a result, the average is computed from the wrong count.

while (true) { // each of Process 1 and Process 2 v = get_value(); add_new_value(v);}add_new_value(v) { int sum = avg*count + v; data[count] = v; count++; avg = sum/count;}

1.3Three requirements

Mutual exclusionIf Pi is in its critical section, no other process is in its critical section.
ProgressIf no process is in the critical section and some processes want to enter, the choice of which process enters next cannot be postponed forever. Only the processes that want to enter take part in this choice. In other words, there is no deadlock. Either Alice or Bob gets in.
Bounded waitingAfter Pi asks to enter, the others may enter only a bounded number of times before Pi does. In other words, there is no starvation. It is not always Alice.

We assume that every process runs at a nonzero speed. However, we assume nothing about their relative speeds. Therefore, a solution has to work under every interleaving.

Chapter 2

The producer–consumer problem

This problem is the running example for this lecture and the next three.

2.1A shared buffer

A producer puts new items into a buffer, and a consumer takes them out. The problem has two variations.

  • Unbounded buffer. It has no practical limit on size. The producer never waits, and the consumer waits when the buffer is empty.
  • Bounded buffer. It has a fixed size. The producer waits when the buffer is full, and the consumer waits when it is empty.
// Producerwhile (true) { produce(next_produced); while (counter == MAX); // do nothing buffer[in] = next_produced; in = (in + 1) % MAX; counter++;}
// Consumerwhile (true) { while (counter == 0); // do nothing next_consumed = buffer[out]; out = (out + 1) % MAX; counter--; consume(next_consumed);}
Try itA bounded buffer, MAX = 8

in and out wrap around modulo MAX. counter holds the number of full slots, and both processes update it.

2.2The race on counter

counter++ and counter-- each consist of three machine instructions, namely load into a register, add or subtract, and store back. Start at counter = 5, with one produce and one consume. The correct result is 5. Pick the order in which the instructions run.

Chapter 3

Solutions

We make three attempts, namely stopping the clock, working around it in software, and getting help from the hardware.

3.1Solution 1, disable interrupts

If nothing can interrupt the process while it is in its critical section, the scheduler cannot preempt it there. Therefore, the process disables all interrupts before it enters and enables them on exit.

Does it work?

  • What if the critical section runs for an hour? With interrupts off, there are no timer interrupts and no I/O completions. Therefore, every other process is blocked.
  • Can a process starve? Yes, because nothing bounds how often the others get in first.
  • What if there are two CPUs? Disabling interrupts on one core does not stop the other core. As such, it gives no mutual exclusion on a multiprocessor.
  • Further, a user program cannot do it at all, because disabling interrupts is a privileged instruction (Lecture 02). Kernels use it only for short sections on one core.
// Producer...in = (in + 1) % MAX;disableInterrupts();counter++;enableInterrupts(); // Consumer...out = (out + 1) % MAX;disableInterrupts();counter--;enableInterrupts();consume(next_consumed);

3.2Solution 2, software only

The first try is a shared boolean lock = FALSE. A process waits while the lock is set and then sets it, with while (lock); lock = TRUE;. However, both processes can see lock == FALSE if a context switch happens just before lock = TRUE. Then both enter.

Peterson's solution uses two shared variables. boolean flag[2] indicates which process is ready to enter, and int turn indicates whose turn it is. Process i runs the code below, where j is the other process.

flag[i] = TRUE; // I want inturn = j; // but you go firstwhile (flag[j] && turn == j); // wait: you want in, your turn critical sectionflag[i] = FALSE;
  • Mutual exclusion. Pi enters only if flag[j] == FALSE or turn == i. If both are ready, only one process can pass, because turn is a single variable and holds the value that was written last.
  • Progress and bounded waiting also hold, because a waiting process enters after the other process enters at most once.
  • However, it works for two processes only.

Instead of arguing each case by hand, we let the page check them. The checker explores every reachable state of two processes that run a protocol, and then tests the three requirements.

Peterson's proof assumes that each load and store happens in program order. However, modern CPUs and compilers reorder independent memory operations. As a result, the solution breaks unless you add memory barriers. This is one more reason to rely on the hardware instructions below.

3.3Solution 3, hardware support

Hardware provides instructions that test and modify a word, or swap the contents of two words, atomically. In other words, each instruction runs as one uninterruptible step, even with respect to other cores.

test_and_set
boolean test_and_set(boolean *target) { boolean rv = *target; *target = true; return rv; // the old value}

It atomically sets *target to true and returns the old value. A lock uses while (test_and_set(&lock)); … lock = false;

compare_and_swap
int compare_and_swap(int *value, int expected, int new_value) { int temp = *value; if (*value == expected) *value = new_value; return temp; // the old value}

It atomically writes new_value, but only if *value == expected. A lock uses while (compare_and_swap(&lock, 0, 1) != 0); … lock = 0;

Mind the semicolon

In while (compare_and_swap(&lock, 0, 1) != 0), the ; is the empty body of the loop. If you leave it out, the next statement, counter++, becomes the body. Then it runs only when the lock is not acquired, and never by the process that holds it.

  • Try "test_and_set" in the model checker. Mutual exclusion and progress hold. However, bounded waiting does not. Nothing orders the waiters, so one process can lose the race every time. The textbook gives a longer TAS algorithm that adds bounded waiting.
  • These instructions are building blocks. Atomic variables provide atomic updates on integers and booleans. For example, increment() is a CAS loop. It reads the value and then tries to swap in value + 1. If another thread changed the value in between, it retries. To see every interleaving end at 5, try "CAS loop" in §2.2.
void increment(atomic_int *v) { int temp; do { temp = *v; } while (temp != compare_and_swap(v, temp, temp + 1));}

3.4Mutex locks and spinlocks

We wrap the instruction in two functions. acquire(&lock) gets the lock without interruption, and release(&lock) gives it back. Then the producer and consumer simply become acquire(&lock); counter++; release(&lock);.

However, this lock still busy-waits. A process that cannot get the lock keeps looping and consumes CPU time. Such a lock is called a spinlock. On a multiprocessor, spinning is acceptable for very short waits, because it avoids a context switch. In contrast, on one core, spinning wastes the rest of the spinner's quantum, because the lock holder cannot run and release the lock until the quantum ends.

void acquire(boolean *lock) { while (test_and_set(lock));}void release(boolean *lock) { *lock = false;}
In the lab

Chapter 4

Busy waiting

Instead of spinning, a process can go to sleep and be woken up. However, this is harder than it sounds.

4.1sleep and wakeup

Two things spin in the bounded buffer, namely the lock, and the while (counter == MAX); and while (counter == 0); loops. For the loops, we need a way to pause a process until there is work to do. The two calls below provide it.

  • sleep() blocks the calling process.
  • wakeup(pid) wakes process pid. It has no effect if pid is not sleeping.
// Producerwhile (true) { produce(next_produced); if (counter == MAX) sleep(); buffer[in] = next_produced; in = (in + 1) % MAX; acquire(&lock); counter++; release(&lock); if (counter == 1) wakeup(consumer);}
// Consumerwhile (true) { if (counter == 0) sleep(); next_consumed = buffer[out]; out = (out + 1) % MAX; acquire(&lock); counter--; release(&lock); consume(next_consumed); if (counter == MAX-1) wakeup(producer);}

4.2The lost wakeup

The waiting loops are gone. However, two problems remain. First, the mutex still spins. Second, the check if (counter == 0) and the sleep() are two separate steps. Therefore, a wakeup can arrive between them and be lost. Step through it with MAX = 4.

Step throughBoth processes asleep, forever
The fix, next lecture

We need a mechanism with two properties. First, it counts the sleep() and wakeup() calls, so that a wakeup sent too early is saved rather than lost. Second, it makes checking and sleeping one atomic step. This mechanism is the semaphore (Lecture 09).

4.3Signals race too

  • A handler that processes signal S1 can be interrupted by another signal S2 (see the reentrancy example in Lecture 05, §4.2).
  • The fix is to block other signals while one signal is handled, with sigprocmask(). A blocked signal becomes pending and is delivered when it is unblocked.
  • At most one signal of each type can be pending. Signals are not queued, so two identical signals may arrive as one.

4.4Blocking vs. non-blocking

"Block" has two different meanings in this lecture. We separate them first.

  • A process blocks when it gives up the CPU and sleeps until an event occurs, such as sleep() in §4.1, a read() on an empty pipe, or a mutex that puts waiters to sleep. The scheduler moves it to the waiting state (Lecture 03) and runs another process.
  • A signal is blocked when delivery is postponed with sigprocmask() (§4.3). The process keeps running, and only the signal waits.

In the first meaning, an operation that may have to wait comes in two styles.

Blocking callA blocking call returns only when it can complete. read() on an empty pipe sleeps until data arrives, and pthread_mutex_lock() waits until it owns the lock. It is simple to use, and the CPU is free for other processes while the caller sleeps. However, the caller can do nothing else in the meantime.
Non-blocking callA non-blocking call returns immediately, even if it cannot complete, and reports this. read() on a pipe opened with O_NONBLOCK returns −1 with errno = EAGAIN, and pthread_mutex_trylock() returns EBUSY. The caller stays in control. However, it has to retry later.

A non-blocking call that is retried in a tight loop is busy waiting again. For example, while (trylock(&m) == EBUSY); is effectively a spinlock. Non-blocking calls are useful when the caller has other work to do between attempts, such as a server that polls many connections.

4.5Synchronous vs. asynchronous

This pair is about when something happens relative to the program's own flow of control.

  • Synchronous signals are caused by the thread's own instruction, such as SIGSEGV from a bad pointer or SIGFPE from dividing by zero. They arrive at a predictable point, namely the faulting instruction, and are delivered to the thread that caused them.
  • Asynchronous signals come from outside the thread, such as SIGINT when the user presses Ctrl-C, SIGALRM from a timer, or kill() from another process. They can arrive between any two instructions. As such, they cause the races in §4.3, and handlers must be reentrant.
  • The same terms also apply to operations. A synchronous operation finishes before the call returns, so the result is available when the next line runs. In contrast, an asynchronous operation is only started by the call. Its completion is reported later, by a signal, a callback, or a status that the caller checks (for example, POSIX aio_read()).
Do not confuse the two

Note that non-blocking is not the same as asynchronous. A non-blocking call gives up now ("not ready, try again"), and the caller must come back. In contrast, an asynchronous call accepts the work now, finishes it later, and tells the caller when it is done. However, the terms overlap in some places. For example, the textbook's message passing (Ch. 3) calls blocking send and receive synchronous, and non-blocking ones asynchronous.

Epilogue

Summary and glossary

∎What to take away

  • Concurrent access to shared data can leave it inconsistent. The code that accesses it is a critical section.
  • A solution needs mutual exclusion, progress, and bounded waiting, under every interleaving and at any relative speed.
  • counter++ consists of three instructions. When it is interleaved with counter--, the result can be 4, 5, or 6.
  • Disabling interrupts fails on multiprocessors, and it is privileged. A plain lock variable violates mutual exclusion. Peterson's solution works for two processes, but only if memory operations happen in program order.
  • Atomic test-and-set and compare-and-swap are used to build spinlocks and atomic variables. They busy-wait, and simple spinlocks do not bound waiting.
  • sleep/wakeup removes the spinning, but it can lose wakeups. The fix is the semaphore, which Lecture 09 introduces.
  • Blocking calls sleep until they can finish. Non-blocking calls return at once and must be retried. Synchronous events happen at a predictable point in the program. Asynchronous ones can happen between any two instructions.

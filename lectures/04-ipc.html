Chapter 0

Why processes talk

Independent processes never affect each other. Cooperating ones do, on purpose.

0.1Cooperating processes

  • Processes may be independent or cooperating. A cooperating process can affect or be affected by others, including by sharing data.
  • Reasons to cooperate: information sharing, computation speedup (split work across cores), modularity, convenience.
  • Cooperating processes need interprocess communication (IPC).
Example

Chrome (Lecture 03, §4.4) runs a browser process, a renderer per site and a process per plug-in. They are isolated for safety, and IPC is how the renderer hands the browser a finished page.

Chapter 1

Signals: a limited IPC

A signal carries one small number: which event happened. Nothing else.

1.1Kernel to process, process to process

  • Kernel to process: the kernel records a signal number for the process, then makes it run its handler. Example: you press Ctrl-C; the terminal driver makes the kernel send SIGINT to the foreground process.
  • Process to process: kill(pid, sig), e.g. kill(X, SIGUSR1). It still goes through the kernel; no process writes into another directly.
  • A process can signal itself: alarm(3) asks the kernel to send it SIGALRM in 3 seconds.

1.2Handlers and default actions

  • The handler lives in the program's own code: a function called when the signal arrives. When it returns, the program continues where it was interrupted.
  • If a process catches a signal, its handler runs. If not, the kernel takes the signal's default action: terminate, terminate with a core dump, ignore, or stop.
  • SIGKILL and SIGSTOP can be neither caught nor ignored: the kernel always acts on them.

Two models for larger volumes

A signal number is not enough to send a web page. Two ways to move real data.

2.1Shared memory and message passing

(a) Shared memory: the OS maps one region into both processes; they read and write it directly.

(b) Message passing: processes send() and receive() messages through the kernel, which copies them.

Chapter 3

Shared memory

The fastest IPC: after setup, communication is just loads and stores.

3.1From fork to sharing

  • When process 2 is a fork() of process 1, what really has to be copied? The code is identical: share it. The data is the same too, until someone changes it.
  • Copy on write shares until a change, then gives the writer its own copy (Lectures 14–15). So the kernel can already map the same frames into two processes.
  • Shared-memory IPC does it on purpose: the OS creates a region and maps it into each process that asks. It applies to processes on the same machine. The catch: shared access must be synchronized (Lectures 08–11).

3.2Two APIs on Linux

System Vshmid = shmget(key, size, flags) creates a region named by a key all parties agree on, or returns the existing one. shm_ptr = shmat(shmid, NULL, 0) attaches (binds) it into the address space; reads and writes then use shm_ptr. shmctl() changes permissions or removes it.
POSIXfd = shm_open("/name", …) creates or opens a named object, ftruncate(fd, size) sets its size, and mmap(…, MAP_SHARED, fd, 0) maps it. munmap, close, shm_unlink clean up. The example below uses this API.

3.3A shared-memory example

writer
#define SHM_NAME "/my_shm"#define SHM_SIZE 4096 int fd = shm_open(SHM_NAME, O_CREAT | O_RDWR, 0666);ftruncate(fd, SHM_SIZE); // set its sizechar *ptr = mmap(NULL, SHM_SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);strcpy(ptr, "Hello from writer process!");printf("Data written.\n");getchar(); // keep it alivemunmap(ptr, SHM_SIZE);close(fd);shm_unlink(SHM_NAME);
reader
#define SHM_NAME "/my_shm"#define SHM_SIZE 4096 int fd = shm_open(SHM_NAME, O_RDONLY, 0666);char *ptr = mmap(NULL, SHM_SIZE, PROT_READ, MAP_SHARED, fd, 0);printf("Read from shared memory:\n");printf("%s\n", ptr); // no read() call!munmap(ptr, SHM_SIZE);close(fd);

The strcpy and the printf touch the same physical frames through different virtual addresses (Lecture 14, §6). The reader's printf reads memory directly: no system call moves the data. (Link with -lrt on older glibc.)

Chapter 4

Message passing

Two operations, send() and receive(), and the kernel in between.

4.1Pipes

  • Message passing is used for small messages: send() and receive(). Kinds: pipes, UNIX-domain sockets, remote procedure calls.
  • A pipe is a conduit between two processes. Design questions: one-way or two-way? If two-way, half- or full-duplex? Must the processes be related (parent and child)? Can it cross a network?
  • Ordinary pipes (pipe(fd)): producer writes to the write end, consumer reads from the read end. Unidirectional, and they need a parent-child relationship, because the child inherits the descriptors across fork(). Windows calls them anonymous pipes. The shell's | is one.
  • Named pipes (FIFOs) persist beyond the processes: mkfifo mypipe creates a file-system entry that any process can open, until it is removed explicitly. On Linux they are one-way per open.

4.2Fill and drain a pipe

Try itA pipe with room for 8 chunks

A real Linux pipe holds 64 KB by default. The rules are the same: write blocks when it is full, read blocks when it is empty, and read returns 0 (end of file) once the pipe is empty and every write end is closed.

4.3A named-pipe example

writer
int fd = open("mypipe", O_WRONLY);char *msg = "Hello from writer\n";write(fd, msg, 18);close(fd);
reader
char buf[100];int fd = open("mypipe", O_RDONLY);int n = read(fd, buf, sizeof(buf));write(STDOUT_FILENO, buf, n);close(fd);

First $ mkfifo mypipe. Each open blocks until the other end is opened too.

4.4Sockets

  • A socket is an endpoint for communication: an IP address plus a port, a number that tells services on one host apart. 161.25.19.8:1625 is port 1625 on host 161.25.19.8. Communication is between a pair of sockets.
  • Ports below 1024 are well known, for standard services (80 HTTP, 443 HTTPS, 22 SSH). 127.0.0.1 (loopback) means this machine.
  • sd = socket(domain, type, protocol): domain PF_UNIX for local, PF_INET for remote; type SOCK_STREAM for a reliable, in-order byte stream (TCP), SOCK_DGRAM for discrete messages (UDP); protocol 0 for the default.
  • PF_UNIX sockets are for processes on one computer: each bind()s to a file name such as /users/yc/my_ipc_socket_file, and I/O looks like reading and writing a file. Usually one process is the server (bind, listen, accept) and the others are clients (connect).

4.5Remote procedure calls

  • A remote procedure call (RPC) makes a call to a procedure in a process on another machine look like a local call. It uses ports to tell services apart.
  • A stub on the client is a proxy for the real procedure: it locates the server and marshals the parameters into a message.
  • The server stub receives the message, unpacks the parameters, and runs the procedure on the server; the result travels back the same way.

Epilogue

Summary and glossary

∎What to take away

  • Cooperating processes need IPC for sharing, speed, modularity and convenience.
  • Signals carry only an event number, from the kernel or from another process via kill(); a handler catches them, or the kernel takes the default action. SIGKILL and SIGSTOP cannot be caught.
  • Shared memory maps one region into several processes: no copies, very fast, but the application must synchronize.
  • Message passing goes through the kernel: pipes (ordinary and named), sockets (UNIX and Internet), RPC with stubs that marshal parameters. Simpler and better isolated, at the cost of copies.
In the lab

The make check harness of every Basecamp talks to the course VM through a virtual serial channel: message passing between your host and the guest. Basecamp 1's undead.c relies on signals: the parent learns of its child's death through SIGCHLD and wait().

Let it tell you

Lecture 17 ends with a driver that spins on a status register while the device works. In this lecture, we remove the spinning in two steps. First, with interrupts, the CPU runs something else until the device calls back. Second, with DMA, the device moves the data itself and calls back only once. Finally, we discuss the two ways in which a driver reaches a controller's registers, namely I/O ports and memory-mapped I/O.

Chapter 0

A recap of polling, and three strategies

This chapter recaps where Lecture 17 stops, and outlines this lecture.

0.1Direct I/O with polling

while (dev.busy || dev.done) ; /* spin 1 */ dev.data[0] = value; dev.command = WRITE; while (dev.busy) ; /* spin 2 */ /* finished: read status bits … */ dev.done = FALSE;

The OS spins twice, once until the device is idle and once until the device finishes. Every spin uses a CPU cycle that an application could have used. Therefore, we want to overlap CPU and I/O.

0.2Three strategies

Underneath the blocking, non-blocking, synchronous, and asynchronous system calls, the device manager can move data in the three ways below.

Direct I/O with pollingThe device manager busy-waits. We have already seen this strategy.
Direct I/O with interruptsThere is no busy waiting. However, the CPU still takes an interrupt and copies data for every transfer. See Chapter 1.
DMA with interruptsA DMA controller moves large blocks without the CPU and interrupts the CPU once at the end. See Chapter 2.

Chapter 1

Direct I/O with interrupts

The driver issues the command, the CPU does something else, and the device interrupts when it is done.

1.1What changes

The task makes its request to the driver, and the driver starts the device. Then the CPU goes back to executing instructions, for this program or another one.

When the device finishes, it interrupts the CPU. Only then does the CPU check the device's state and transfer the data.

As such, the CPU leaves useful work only twice and only briefly, instead of spinning for the whole operation.

1.2Hardware interrupts

  • The CPU has a hardware interrupt flag.
  • Whenever a device finishes a read or write, it signals the CPU and raises the flag. Therefore, the CPU is free to run other tasks instead of polling devices.
  • On an interrupt, the CPU suspends normal execution and invokes the OS's interrupt handler.
  • After the interrupt is handled and the I/O results are processed, the OS resumes normal execution. In the terms of Lecture 17, an interrupt belongs to the asynchronous exception class, which returns to the next instruction.

1.3Inside the interrupt handler

  1. Prep. Disable interrupts, so that a second interrupt cannot arrive in the middle of the first.
  2. Save the processor state, namely the running app's program counter (PC) and register contents.
  3. Find the device that interrupted. To do so, the CPU asks the interrupt controller for the interrupt offset, or polls the devices.
  4. Jump to the device's handler by indexing into the interrupt vectorThe table that maps an interrupt number to its handler's address. On x86, it is the IDT from Lecture 17. with that offset. The code that runs is the interrupt service routine (ISR).
  5. Re-enable interrupts, restore the saved state, and return to the interrupted program.
Going further with top halves and bottom halves

Interrupts are off while the handler runs, so a slow handler delays every other device. Therefore, Linux splits the work into two halves. The top half (the hard-IRQ handler) does the minimum. Specifically, it acknowledges the device, fetches the data, and schedules the rest. The bottom half (a softirq, tasklet, or workqueue item) finishes the job later, with interrupts enabled.

1.4An interrupt-driven read, step by step

  1. The program calls read(device, …), and the call reaches the read driver.
  2. The driver checks the device's status.
  3. If the device is idle, the driver writes the command.
  4. The driver puts the request on the request queue. The process blocks, and the CPU runs something else.
  5. The device finishes and raises an interrupt, which reaches the interrupt handler.
  6. The interrupt handler calls the corresponding device handler.
  7. The device handler takes the pending request off the queue.
  8. 8a It reads the data register. 8b It copies the data into the program's buffer.
  9. It wakes the program, and read() returns.
Two interrupts

If the device is busy at step 2, the request waits in the queue. Then the device interrupts twice. The first interrupt comes when the device finishes the earlier request, so that the handler can issue ours. The second comes when ours is done.

1.5When is polling better than interrupts?

Interrupts are not free, for the three reasons below.

  • Setting up the interrupt takes overhead.
  • Handling the interrupt takes overhead.
  • Blocking the process and scheduling another one takes overhead.

Therefore, if the wait for the I/O is always short, or predictable, polling is better.

Chapter 2

Direct memory access

Interrupts free the CPU from waiting. DMA frees it from copying.

2.1The problem with interrupt-driven I/O

When there is a lot of data, moving it between memory and devices can become the bottleneck.

For example, consider reading a 1 MB file from a disk that delivers 1 KB blocks. Every time a block is ready, the disk raises an interrupt, and the CPU copies 1 KB. As a result, the read takes 1024 interrupts, and each one slows down the running programs and the OS.

The worst case is an interrupt after every byte or character, or after every packet from the network card.

2.2Where the CPU's time goes with polling, interrupts, and DMA

In this model, the disk takes 100 µs per 1 KB block. Taking an interrupt costs the CPU 5 µs, copying 1 KB costs 10 µs, and setting up a DMA transfer costs 10 µs. The timeline shows the first 16 blocks, and the numbers cover the whole file.

2.3The DMA idea

  • Bypass the CPU for large data copies, and raise an interrupt only at the very end of the transfer instead of after every block.
  • Modern systems offload this work to a special-purpose processor, the direct-memory-access (DMA) controller.
  • The DMA controller operates the memory bus directly. It places addresses on the bus and performs the transfers without the main CPU.

2.4DMA with interrupts, step by step

  1. The device driver is told to transfer bytes from the disk to memory at address X.
  2. The driver tells the disk controller.
  3. The disk controller starts the DMA transfer.
  4. The disk controller sends each byte to the DMA controller.
  5. The DMA controller writes each byte to memory at X, X+1, …
  6. When the count reaches zero, the DMA controller interrupts the CPU once.

2.5Sharing the memory bus

The CPU and the DMA controller both need main memory, so they compete for the bus.

Burst modeWhile DMA transfers, the CPU is blocked from accessing memory.
Cycle stealingDMA and the CPU interleave. DMA moves one word, then the CPU gets a memory access, then DMA, then the CPU…
Transparent modeDMA transfers only when the CPU is not using the bus. This mode is the most efficient. However, it is hard to detect when the CPU is not using the bus.

Chapter 3

Reaching the registers with ports and memory-mapped I/O

Every strategy above ends with a driver that reads or writes a controller register. There are two ways to address such a register.

3.1Port-mapped I/O

Controller registers live in a separate I/O port address space, which special machine instructions reach. On Intel x86, these instructions are IN and OUT.

  • OUT dest, src writes CPU register src to device port dest.
  • IN dest, src reads device port src into CPU register dest.

Only the OS, in kernel mode, may execute them. Later, Intel added string versions (INS, OUTS) and width variants (INSB, INSW, INSD).

; send one byte out the primary serial port mov dx, 0x3F8 ; port number mov al, 'A' ; the byte out dx, al ; write it to the port ; read the timer's counter in al, 0x40

The table shows a partial map of the port space of the classic PC (Silberschatz, Fig. 12.3). Each range is a small block of registers. The primary serial port's data register is port 0x3F8, and the next seven ports are its status and control registers.

Note the devices at the lowest addresses. The DMA controller of Chapter 2 and the interrupt controller of Chapter 1 are also devices, and they are programmed through ports like any other device.

3.3The limits of port I/O

  • IN and OUT can only load and store. The CPU's full set of memory operations is not available.
  • For example, to increment a device's data register, the driver copies it into a CPU register, adds one, and copies it back. This takes three instructions and two bus trips.
  • When AMD defined x86-64, it did not extend the port I/O instructions, so there is no 64-bit IN or OUT.

3.4Memory-mapped I/O

Device registers and device memory are mapped into the system's memory address space. As such, ordinary instructions reach them, as the example below shows.

load R3, 0xC0FF01 reads a device register, because address 0xC0FF01 is assigned to that controller's command register.

Each controller's registers are assigned a block of addresses. When a value is written there, the device sees it, loads it, and carries out the command.

Devices are typically mapped into lower memory. Display frame buffers take the most space. Even a large display needs only 10–100 MB, which is modest in an address space of gigabytes. Therefore, memory-mapped I/O costs little address space.

More precisely

The address in the example is a physical address. The MMU still translates the kernel's virtual address to it as usual (Lecture 14). The corresponding page-table entries are marked uncacheable, so that every access actually reaches the device. The memory controller and the bus route a physical address to the controller rather than to RAM.

Epilogue

Recap and glossary

∎Recap

  • The three device controller states are idle, working, and finished.
  • The three I/O strategies are listed below.
    • Direct I/O with polling. The CPU waits for the device to become idle, issues the I/O command, and waits for the device to finish.
    • Direct I/O with interrupts. There is no busy waiting. However, every transfer takes an interrupt and a CPU copy.
    • DMA with interrupts. Large transfers happen without the CPU, with one interrupt at the end.
  • Port vs. memory-mapped I/O. Port registers live in a separate I/O address space, which only the OS reaches, with IN/OUT. In contrast, memory-mapped registers are at memory addresses, which are mapped into kernel (or user) space, and they are accessed like any other memory.
In the lab

The Basecamp 5 driver has no real hardware behind it, so its scd_read copies from a kernel buffer with copy_to_user. A real disk driver does the same last step. However, in a real driver, the data gets into that buffer by DMA, and the driver learns that it is there from an interrupt.

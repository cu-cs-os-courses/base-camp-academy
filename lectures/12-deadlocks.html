Everyone waits, forever

Lectures 09 and 11 kept running into the same failure, in which each thread holds something the next one needs, around a circle. This lecture treats deadlock systematically. It states the four conditions that together make it possible, then covers four responses. The system can prevent it by breaking a condition, avoid it by checking each request (the Banker's algorithm), detect it and recover, or ignore it. It ends with a cousin of deadlock that nearly cost a Mars mission.

Chapter 0

Deadlock characterization

Four conditions, all at once.

0.1System model

  • A system has resource types R1, …, Rm, such as CPU cycles, memory space, I/O devices, and locks. Type Ri has Wi identical instances.
  • Each thread uses a resource in three steps, namely request (wait if it is unavailable), use, and release.
  • The simplest deadlock takes two binary semaphores and two threads that lock them in opposite orders (Lecture 09, §2.1).
// T1wait(S1);wait(S2);
// T2wait(S2);wait(S1);

0.2The four necessary conditions

Deadlock can arise only if all four hold simultaneously.

1 · Mutual exclusion

Only one thread at a time can use a resource.

2 · Hold and wait

A thread holding at least one resource waits to acquire more resources held by others.

3 · No preemption

A resource is released only voluntarily, by the thread holding it, when it is done.

4 · Circular wait

There is a set {T0, …, Tn} of waiting threads where T0 waits for T1, T1 for T2, …, and Tn waits for T0.

They are necessary. Break any one and deadlock is impossible. That is the whole idea of prevention (§2).

Chapter 1

Resource-allocation graphs

Draw who holds what and who wants what. Deadlock shows up as a cycle.

1.1Vertices and edges

  • The vertices are threads T = {T1, …, Tn}, drawn as circles, and resource types R = {R1, …, Rm}, drawn as boxes with one dot per instance.
  • A request edge Ti → Rj means Ti is waiting for an instance of Rj.
  • An assignment edge Rj → Ti, drawn from a dot, means an instance of Rj is held by Ti.

1.2Three graphs

Try itCycles, and whether they deadlock

Reduction is the question "could everyone finish?". Repeatedly find a thread whose requests can all be met from the free instances, let it finish, and return what it holds. Threads left at the end are deadlocked. This is the detection algorithm of §4, run on the picture.

1.3Basic facts

  • No cycle → no deadlock.
  • A cycle, and only one instance per resource type → deadlock.
  • A cycle, with several instances per type → deadlock is possible, but not certain. In the third graph, T2 and T4 are not in the cycle. When either finishes, it frees an instance that breaks the cycle.

A cycle is a necessary but not sufficient condition for deadlock.

Chapter 2

Handling deadlocks by prevention

There are four strategies, and the first breaks one of the four conditions.

2.1Four ways to handle deadlock

  • Prevention. Make sure at least one of the four necessary conditions can never hold.
  • Avoidance. Using advance information, decide at each request whether granting it could lead to deadlock (§3).
  • Detection and recovery. Let deadlocks happen, find them, and break them (§4).
  • Ignore the problem and pretend deadlocks never occur, the "ostrich algorithm". This is what most general-purpose operating systems, Linux and Windows included, do for application-level deadlocks. Preventing them is left to the programmer. (Inside its own code, the Linux kernel checks its lock ordering with a debugging validator called lockdep.)

2.2Breaking each condition

conditionhow to break itcost
mutual exclusionNot needed for sharable resources, such as read-only files.Non-sharable resources, such as a mutex or a printer, must keep it.
hold and waitA thread may request resources only when it holds none. Either it gets everything before it starts, or it acquires all or nothing, like the monitor philosophers of Lecture 11.Low resource utilization, and starvation is possible.
no preemptionIf a thread holding resources requests one it cannot get now, it releases everything it holds. The released resources join its wait list, and it restarts only when it can regain all of them plus the new one.Only for resources whose state can be saved and restored, such as CPU registers and memory. A printer cannot be taken away halfway through a job.
circular waitNumber every resource type and require each thread to request resources in increasing order.Needs discipline. Every lock gets a unique number, and every code path must acquire in order.

2.3Lock ordering in practice

Breaking circular wait is by far the most common technique. Give each lock a number and always acquire locks in increasing order. A cycle would need some thread to hold a higher-numbered lock while waiting for a lower one, and the rule forbids that.

For the dining philosophers, number the chopsticks 1 < 2 < 3 < 4 < 5. Philosopher Pi uses chopsticks i and i+1, so P1–P4 pick up chopstick i first. P5 uses chopsticks 5 and 1, and the ordering makes it pick up 1 before 5, the opposite side from everyone else. P5 then blocks on 1, not on 5, and the circle cannot close. This is the asymmetric solution of Lecture 11, derived from a general rule.

Chapter 3

Deadlock avoidance

Grant a request only if the system stays in a state from which everyone can still finish.

3.1Safe states

  • Avoidance needs information in advance. The simplest and most useful model has each thread declare the maximum number of instances of each type it may need.
  • The resource-allocation state is the available resources, the allocated resources, and the declared maxima.
  • A state is safe if there is a sequence ⟨T1, T2, …, Tn⟩ of all threads such that each Ti's remaining needs can be met by the available resources plus those held by every Tj with j < i. If Ti cannot proceed now, it waits for the earlier ones to finish and return their resources, then runs, returns its own, and Ti+1 goes next.
  • Safe → no deadlock. Unsafe → deadlock is possible. Avoidance keeps the system from ever entering an unsafe state.

3.2Claim edges for single instances

  • When every resource type has one instance, use the resource-allocation graph with claim edges. A dashed Ti ⇢ Rj means Ti may request Rj someday. All claims must be declared in advance.
  • A claim edge becomes a request edge when Ti requests Rj, and an assignment edge when Rj is granted. On release, it reverts to a claim edge.
  • Grant a request only if converting the request edge to an assignment edge does not create a cycle, counting claim edges.

3.3The Banker's algorithm for multiple instances

Like a banker who never lends out cash in a way that could leave some customers unable to finish, the OS grants a request only if the resulting state is safe. Each thread declares its maximum. When it has everything, it returns the resources in finite time. It keeps the data below for n threads and m resource types.

  • Available[m] holds the free instances of each type.
  • Max[n][m] is the most Ti may ever request.
  • Allocation[n][m] is what Ti holds now.
  • Need[n][m] = Max − Allocation is what Ti may still ask for.
// safety algorithmWork = Available; Finish[i] = false for all i;repeat: find i with Finish[i] == false and Need[i] ≤ Work; if none: break; Work += Allocation[i]; Finish[i] = true;safe ⇔ Finish[i] == true for all i
// resource-request algorithm for Ti1. Request ≤ Need[i]? else error: over max2. Request ≤ Available? else Ti waits3. pretend: Available −= Request; Allocation[i] += Request; Need[i] −= Request; safe? → grant unsafe? → Ti waits; restore old state

Vectors compare element by element, so X ≤ Y means X[j] ≤ Y[j] for every j.

    Chapter 4

    Detection and recovery

    Let it happen, notice, and clean up.

    4.1The wait-for graph for single instances

    Collapse the resource-allocation graph. The nodes are threads only, and Ti → Tj means Ti waits for a resource that Tj holds. Periodically search it for a cycle. A cycle means deadlock. Cycle detection takes on the order of n² operations for n vertices.

    4.2The detection algorithm for several instances

    This is the safety algorithm with Request (what each thread is waiting for now) in place of Need, the reduction of §1.2 in matrix form. A thread holding nothing cannot be part of a deadlock, so its Finish starts true. Threads with Finish still false at the end are deadlocked. The cost is O(m × n²). (The widget's order may differ from the slides' ⟨T0, T2, T3, T1, T4⟩, and any complete order proves there is no deadlock.)

    Try itFive threads, with A = 7, B = 2, C = 6 instances

    4.3When to run it, and how to recover

    • How often to invoke detection depends on how often deadlocks occur and how many threads must be rolled back, at least one per disjoint cycle. Running it at every blocked request finds the culprit immediately but costs the most. Running it rarely, or when CPU utilization drops, means many cycles may have formed, and it can no longer tell which thread "caused" the deadlock.
    • Recovery by termination. Abort all deadlocked threads, or abort one at a time until the cycle breaks. To choose the victim, weigh its priority, how long it has computed and how much remains, the resources it holds and still needs, how many threads must go, and whether it is interactive or batch.
    • Recovery by preemption. Pick a victim to minimize cost, roll it back to a safe state and restart it from there, and guard against starvation by counting rollbacks in the cost, so the same thread is not always chosen.

    Chapter 5

    Priority inversion

    Not a deadlock, but a lock and a scheduler combining to stall the most important task.

    5.1A hazard with mutexes

    There are three tasks under preemptive priority scheduling. Task 1 has the highest priority and task 3 the lowest. Task 3 locks a shared object and enters its critical section. Task 1 arrives, preempts it, tries the same lock, and blocks. So far that is expected, since task 1 waits for a short critical section. Then task 2, of medium priority and not needing the lock, arrives and preempts task 3. Now task 1 waits for task 2, which can keep it waiting arbitrarily long. In effect, the priorities of tasks 1 and 2 are inverted.

    Try itThree tasks, one lock

    The shaded parts of a bar are critical-section time, holding the lock. Arrows mark arrivals. The default timeline matches the slide. Task 1 arrives at 2 and blocks at 3, and task 2 arrives at 4.

    5.2Mars Pathfinder, 1997

    Pathfinder landed on Mars on July 4, 1997. A few days into the mission it began missing deadlines and resetting itself, losing data each time. Engineers on the ground diagnosed priority inversion. A low-priority meteorological task held a lock that a high-priority bus-management task needed, while medium-priority tasks kept running. A watchdog saw the high-priority task miss its deadline and reset the system.

    The fix was the one the widget offers. The real-time OS (VxWorks) supported priority inheritance on that mutex, but it was switched off. Engineers enabled it by uploading a small patch to the spacecraft.

    Priority inheritanceA task holding a lock temporarily runs at the highest priority of any task waiting for that lock, and drops back when it releases. Medium tasks can no longer cut in.
    Priority ceilingEach lock has a ceiling, namely the highest priority of any task that ever uses it. A task holding the lock runs at the ceiling from the moment it locks, so the inversion cannot start.

    POSIX exposes both through mutex attributes, namely pthread_mutexattr_setprotocol() with PTHREAD_PRIO_INHERIT or PTHREAD_PRIO_PROTECT.

    Epilogue

    Summary and glossary

    ∎What to take away

    • Deadlock needs mutual exclusion, hold and wait, no preemption, and circular wait, all at once.
    • In a resource-allocation graph, no cycle means no deadlock. A cycle with single-instance resources means deadlock, and with multiple instances it means a possible deadlock.
    • Prevention breaks a condition. In practice, lock ordering breaks circular wait.
    • Avoidance grants only requests that keep the state safe, using claim edges for single instances and the Banker's algorithm for many.
    • Detection runs the reduction on current requests (or looks for wait-for cycles), then recovers by termination or by preemption with rollback.
    • Priority inversion is unbounded blocking of a high-priority task through a medium one. It is fixed by priority inheritance or priority ceilings.

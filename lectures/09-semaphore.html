A counter that remembers

Lecture 08 ended with a lost wakeup, in which a signal sent before anyone waited was forgotten. Dijkstra's semaphore fixes this problem with an integer that counts and a queue of sleeping processes. This one primitive gives you locks, counts of free slots and full slots, and a correct bounded buffer. However, it also gives you new ways to deadlock.

Chapter 0

The semaphore

An integer, a queue, and two atomic operations.

0.1P and V

  • A semaphore S is an abstract data type proposed by Edsger Dijkstra. It is more than an atomic variable, because it also holds a queue of waiting processes.
  • It is accessed only through two operations, and each operation is atomic.
    • wait(), originally P(), from the Dutch proberen, "to test", and
    • signal(), originally V(), from verhogen, "to increase".
  • P decrements the value. If the result is negative, the caller joins the queue and sleeps. V increments the value. If the result is still ≤ 0, at least one process is waiting. Therefore, V wakes one of them.
  • A negative value −n means n processes are waiting. A positive value is the number of P's that can pass without sleeping.
typedef struct { int value; PID *list[]; // sleeping processes} semaphore; P(semaphore *s) { s->value--; if (s->value < 0) { add this process to s->list; sleep(); }}V(semaphore *s) { s->value++; if (s->value <= 0) { remove a process Q from s->list; wakeup(Q); }}
Why the wakeup is no longer lost

The value remembers. A V that comes before any P raises the value. The later P then finds the value positive and does not sleep. In addition, P runs atomically, so "check and go to sleep" is a single step. As such, both flaws of Lecture 08's sleep/wakeup are gone.

Where the spinning went

P and V must themselves be atomic. Therefore, they are built from more basic primitives, namely a spinlock, or disabled interrupts on one core. This primitive is held only while the few instructions of P or V run. As a result, some busy waiting remains. However, it is short and bounded, and it no longer lasts as long as a whole critical section.

0.3Binary semaphores are locks

Initialize S to 1, and bracket the critical section with P(S) and V(S). The first process to pass drops S to 0. Any other process that arrives drops S below 0 and sleeps, without busy waiting. A semaphore whose value stays at 0 or 1 in this way is a binary semaphore. It works like a mutex lock. In contrast, the general kind, whose value can go above 1, is a counting semaphore.

semaphore S; S.value = 1;int counter; // Producer // ConsumerP(S); P(S);counter++; counter--;V(S); V(S);
Same as a mutex? Almost

A mutex has an owner. Only the thread that locked it may unlock it, and POSIX can detect violations of this rule. In contrast, a semaphore has no owner. Any process may call V. This property makes semaphores useful for signaling between processes, and the next chapter relies on it.

Chapter 1

The bounded buffer, solved

Three semaphores, each with one job.

1.1Three goals, three semaphores

An ideal bounded-buffer solution meets the three goals below.

Goal 1The producer sleeps when the buffer is full. space_avail is a counting semaphore initialized to MAX that counts empty slots. Each produce takes one, and when the value reaches 0, the producer blocks.
Goal 2The consumer sleeps when the buffer is empty. item_avail is a counting semaphore initialized to 0 that counts full slots. The producer increments it, and each consume takes one. When the value reaches 0, the consumer blocks.
Goal 3Mutual exclusion on the buffer while it is partially full. mutex is a binary semaphore initialized to 1 that protects buffer, in, and out.
semaphore mutex = 1;semaphore space_avail = MAX;semaphore item_avail = 0;// Producerwhile (true) { produce(next_produced); P(space_avail); P(mutex); buffer[in] = next_produced; in = (in + 1) % MAX; V(mutex); V(item_avail);}
// Consumerwhile (true) { P(item_avail); P(mutex); next_consumed = buffer[out]; out = (out + 1) % MAX; V(mutex); V(space_avail); consume(next_consumed);}

There is no busy waiting anywhere. Note the pairing. The producer waits on space and signals items, and the consumer does the reverse. This pairing relies on the no-owner property of §0.3.

In this section, we check whether the solution still works with several producers and several consumers. Step each process yourself, or let a random scheduler interleave them. Then break the solution by removing the mutex or by swapping the producer's two P's.

1.3Another possible solution

// Producerwhile (true) { produce(next_produced); while ((in + 1) % MAX == out); buffer[in] = next_produced; in = (in + 1) % MAX;}
// Consumerwhile (true) { while (in == out); next_consumed = buffer[out]; out = (out + 1) % MAX; consume(next_consumed);}

This solution has no counter and no locks. The producer writes only in, and the consumer writes only out. Think about each question below before you open it.

Does it work for one producer and one consumer?

Yes. Each shared variable has exactly one writer. Therefore, there is no read-modify-write race. The producer fills a slot before it advances in, so the consumer never reads a slot that is not ready. Note that on modern hardware, this solution needs memory-ordering guarantees, which is the same caveat as for Peterson's solution in Lecture 08.

What are its limitations?

First, it busy-waits in both while loops. Second, it holds only MAX − 1 items. The test for "full" is (in + 1) % MAX == out, because in == out already means "empty". As a result, one slot is always unused.

Does it work for several producers or consumers?

No. Two producers can both see a free slot, both write buffer[in], and both advance in. As a result, one item is overwritten and one slot is skipped. This is exactly the "no mutex" failure in §1.2.

Which solution is more general?

The semaphore solution is more general. It handles any number of producers and consumers, uses all MAX slots, and sleeps instead of spinning. In contrast, the lock-free version is a special case for exactly one producer and one consumer.

Chapter 2

What can go wrong

Semaphores are powerful but unstructured. Nothing checks whether P and V are used correctly.

2.1Deadlock

Consider two shared resources, R1 and R2. Each is guarded by a binary semaphore, namely Q for R1 and S for R2. P1 locks S and then Q, and P2 locks Q and then S. If each process gets its first lock, each blocks on the other's lock. As a result, the V's that would wake them never run.

No rule enforces the order in which P and V are called. As more processes share more semaphores, the potential for deadlock grows. Lecture 12 covers deadlock in full.

Try itOpposite lock order

2.2Starvation

Three processes share one binary semaphore S, which guards R1 and R2. The resource can pass back and forth between P1 and P2 while P3 never gets it. Which process wakes depends on how the semaphore picks from its queue and on scheduling. Run the starvation script in §0.2 with each wake order.

  • LIFO (newest first). P1 and P2 hand S to each other forever. P3, which queued first, starves.
  • FIFO (oldest first). P3 is woken at the first V. A FIFO queue gives bounded waiting.

Chapter 3

Pthread synchronization

The same tools as real C APIs.

3.1POSIX mutex locks

#include <pthread.h>pthread_mutex_t m; // declare a mutex objectpthread_mutex_init(&m, NULL); // initialize (default attributes) // each threadpthread_mutex_lock(&m); // critical sectionpthread_mutex_unlock(&m); pthread_mutex_destroy(&m); // when no thread needs it any more

pthread_mutex_lock sleeps if the mutex is held. pthread_mutex_trylock returns EBUSY instead (Lecture 08, §4.4).

Epilogue

Summary and glossary

∎What to take away

  • A semaphore is an integer plus a queue. P decrements the value and sleeps if it goes negative. V increments it and wakes a sleeping process if there is one. Both operations are atomic.
  • The value counts. Therefore, early wakeups are not lost, and −value is the number of waiting processes.
  • A binary semaphore (initialized to 1) acts as a lock without busy waiting. Counting semaphores count resources.
  • The bounded buffer uses space_avail = MAX, item_avail = 0, and mutex = 1. It works for any number of producers and consumers.
  • Semaphores are unstructured. As a result, lock order can cause deadlock, wake order can cause starvation, and a single misplaced P or V can cause ME violations or hangs.
  • POSIX offers pthread_mutex_*, sem_init/wait/post/getvalue/destroy, and sem_open/close/unlink for named semaphores.

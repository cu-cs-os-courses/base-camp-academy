plays by the rules. Security doesn't

Lecture 22 built mechanisms that decide who may do what, assuming the system knows who is asking and the rules are followed. Security asks what happens when an adversary lies about who they are, feeds programs input they never expected, or listens on the network. This lecture surveys the threats at a conceptual level, then spends most of its time on the defenses: cryptography, authentication, and layered protection.

Chapter 0

The security problem

A system is secure if its resources are used and accessed as intended under all circumstances. That is unachievable; the goal is to make attacks cost more than they are worth.

0.1Threats and attacks

  • A threat is a potential security violation; an attack is an attempt to breach security.
  • Attacks can be accidental or malicious. Protecting against accidental misuse is much easier than against malicious misuse.
ViolationMeaning
breach of confidentialityunauthorized reading of data
breach of integrityunauthorized modification of data
breach of availabilityunauthorized destruction of data
theft of serviceunauthorized use of resources
denial of service (DoS)preventing legitimate use

0.2How violations happen

MasqueradingPretending to be an authorized user: a breach of authentication, often to escalate privileges.
ReplayResending a captured valid message, as is or modified.
Man in the middleThe intruder sits in the data flow, posing as the sender to the receiver and vice versa (§3.4).
Session hijacking · privilege escalationTaking over an already-authenticated session; gaining access beyond what a user or resource is supposed to have.

0.3Four levels, one weakest link

Absolute security is impossible, but security must hold at four levels to be effective:

  • physical: data centers, servers, terminals;
  • application: benign or malicious apps can cause problems;
  • operating system: protection mechanisms, debugging;
  • network: intercepted communications, interruption, DoS.

Security is only as strong as the weakest link. Humans are a link too: phishing and social engineering target people, not code. And too much security can backfire when users route around it.

Chapter 1

Threats

What attackers try to do, at the level an OS designer needs: enough to know what the defenses are for.

1.1Program threats: malware

Malware is software designed to exploit, disable or damage a computer. All of it tries to get around the principle of least privilege.

  • Trojan horse: a program that looks useful but misuses the environment it runs in. It exploits the fact that one user's programs run with another user's rights. Spyware and ransomware (which encrypts data and demands payment) are variants.
  • Trap door (backdoor): a hidden identifier or password that skips normal security checks. It could even be planted in a compiler, which makes it very hard to detect.
  • Logic bomb: code that misbehaves only when a condition is met.
  • Virus: a fragment embedded in a legitimate program that replicates into other programs, usually spread by e-mail or document macros; worm: a standalone program that spreads itself over the network (§1.3).

1.2Bugs as threats: memory-safety errors

Even code that is not malicious can be a threat if it has bugs. The classic example is a program that copies input into a fixed-size buffer without checking the length, written in a language like C or C++ that lets pointers reach any memory. Overlong input then overwrites whatever lies next to the buffer, which can let an attacker change what the program does. This is the family of code-injection and buffer-overflow bugs.

Finding such a bug takes skill, but once someone publishes an attack tool, anyone can run it. The damage is bounded by the rights of the process that has the bug, which is why least privilege (Lecture 22) matters so much.

Defenses, layered

Write safe code: check lengths (strncpy, snprintf), review each other's code, use memory-safe languages. Let the OS and hardware help: mark stack and heap pages non-executable with the page-table NX bit (Lecture 14), randomize where code and data are loaded (ASLR), and have the compiler place guard values (stack canaries) that detect corruption before a function returns. Each can be defeated alone; together they make attacks much harder.

In the lab

This is why your Basecamp 5 driver clamps every offset and length to the 900-byte buffer and moves data only with copy_to_user / copy_from_user. A missing length check in a kernel module is a memory-safety bug with kernel privileges.

1.3System and network threats

  • Some systems are "open" rather than secure by default. Reducing the attack surface (fewer services, fewer open ports) helps, at some cost in convenience.
  • Network threats are harder to detect and prevent: there is no physical boundary once a machine is on the Internet, no easy shared secret, and an IP address is all you know about the other side.
  • Worms spread by themselves. The 1988 Internet worm exploited bugs in the finger and sendmail services and the password-free trust of rsh between "friendly" machines, then tried password guessing.
  • Port scanning probes which network services a host exposes. Administrators use the same tools to audit their own systems.
  • Denial of service overloads a target so it cannot do useful work; distributed DoS comes from many machines at once. It can even be accidental: a buggy fork() loop in a lab (Lecture 3). Telling an attack apart from sudden popularity is hard.

Chapter 2

Cryptography

Inside one computer the OS knows who sent a message. Across a network it cannot, unless secrets are involved.

2.1Why cryptography

  • Within one machine, the OS creates and protects process IDs and communication ports, so the source and destination of a message can be trusted.
  • On a network they cannot: an unauthorized host can be added to a LAN, and on the Internet an IP address proves nothing.
  • Cryptography constrains who can send or receive a message, based on secrets called keys. It enables confirming the source, restricting who can read, and building trust between sender and receiver.

2.2Encryption

Encryption constrains the set of possible receivers. It has a set of keys K, messages M and ciphertexts C, with efficiently computable functions Ek: M → C and Dk: C → M.

The essential property: given ciphertext c, a computer can find m with Ek(m) = c only if it has k. Since ciphertexts are exposed on the network, it must also be infeasible to derive k from them.

2.3Symmetric encryption

  • The same key encrypts and decrypts, so it must stay secret between the two parties.
  • DES was the most common block cipher; its 56-bit keys are now far too short. Triple-DES applies it three times with two or three keys.
  • AES (NIST, 2001) is the standard block cipher: 128-bit blocks, 128-, 192- or 256-bit keys.
  • Stream ciphers encrypt a stream of bytes with a key-driven pseudo-random keystream. RC4 was the most common and is now considered broken; ChaCha20 is a modern replacement.

2.4Asymmetric encryption: RSA

Each user has two keys: a public key that anyone may use to encrypt, and a private key that only the owner uses to decrypt. The scheme must be public without revealing how to decrypt.

RSA relies on the fact that testing whether a number is prime is efficient, but no efficient algorithm is known for factoring a large number into its primes.

  • pick primes p and q; N = p·q;
  • pick ke with ke·kd mod (p−1)(q−1) = 1;
  • encrypt: E(m) = mke mod N; decrypt: D(c) = ckd mod N.

Real keys use N of 2048 bits or more. Asymmetric encryption is far more expensive than symmetric, so it is rarely used for bulk data.

Chapter 3

Authentication and keys

Encryption limits who can read. Authentication limits who can have sent it, and proves it was not changed.

3.1Hashes, MACs, digital signatures

An authentication algorithm produces an authenticator Sk(m) and verifies it with Vk(m, a). Only a holder of k can produce an authenticator that verifies; and k must not be derivable from exposed authenticators.

Hash functionA small, fixed-size digest H(m). Must be collision resistant: infeasible to find m′ ≠ m with H(m′) = H(m). Alone it is not an authenticator: an attacker can change m and recompute H.
MACA message-authentication code: a cryptographic checksum computed with a shared secret key, usually over H(m). Anyone who can verify can also create one.
Digital signatureAsymmetric: sign with the private key, verify with the public one. RSA signing is RSA with the keys reversed: S(m) = H(m)ks mod N. Anyone can verify; only the owner can sign.

MD5 (128-bit) and SHA-1 (160-bit) are the textbook's examples; both now have practical collisions. Use SHA-256 or newer.

3.2Why authenticate without encrypting?

  • It needs fewer computations (except RSA signatures), and authenticators are usually shorter than messages.
  • Sometimes we want authenticity but not secrecy: a signed OS patch is public, but must be exactly what the vendor released (Lecture 22's code signing).
  • Signatures can support non-repudiation: the signer cannot later deny having signed.

3.3Key distribution and certificates

  • Delivering a symmetric key is a huge challenge; sometimes it is done out of band.
  • Public keys can be published, but distribution still needs care: how do you know a public key really belongs to Bob?
  • A digital certificate is a public key signed by a trusted party, a certificate authority, after it checked the owner's identity. Browsers ship with CA public keys; CAs vouch for other authorities by signing their keys, forming a chain.

3.5Where cryptography lives: TLS

  • Cryptography can go at several layers: IPsec at the network layer (the basis of VPNs, with IKE for key exchange), TLS (formerly SSL) above the transport layer. Some things, like user authentication or e-mail delivery, need knowledge only higher layers have.
  • TLS secures web traffic. The server proves its identity with a certificate; asymmetric cryptography establishes a fresh symmetric session key; the bulk of the session then uses fast symmetric encryption.

Chapter 4

User authentication

Every protection decision of Lecture 22 depends on the user ID. So the OS must be sure who you are.

4.1Passwords

  • Identity is most often established with a password, a special case of a key or a capability. It must stay secret: change it, don't reuse it, make it hard to guess, and log invalid attempts (but never the passwords).
  • Protecting it in transit (against sniffing) does not help against shoulder surfing or a keystroke-logging Trojan horse. And how does the system store it?
  • Store only a one-way hash: easy to compute, hard to invert, never decrypted. At login, hash what was typed and compare. Keep even the hashes secret anyway: UNIX puts them in /etc/shadow, readable only by root (Lecture 22, §1.4).
  • Add a random salt per user, stored next to the hash, so that the same password does not hash to the same value and precomputed tables of common-password hashes are useless.

4.3Beyond passwords

One-time passwordsUser and computer compute each password from a shared seed; a hardware token or phone app shows the current one, which changes frequently.
BiometricsA physical attribute: fingerprint, face, hand geometry.
Multi-factorRequire two or more factors: something you know (password), have (token, phone), are (biometric). Stealing one is not enough.

Chapter 5

Defenses

No single mechanism is enough. Defense in depth stacks many.

5.1Policy, assessment, detection

  • A security policy says what is being secured. A vulnerability assessment compares the real state of a system or network against that policy.
  • Intrusion detection looks for attempted or successful intrusions: signature-based detection spots known bad patterns; anomaly detection spots departures from normal behavior and can catch never-seen ("zero-day") attacks. Both suffer false positives and false negatives.
  • Virus protection scans programs for known patterns, or runs them in a sandbox. Auditing, accounting and logging record activity for later review.

5.2Firewalls

  • A network firewall sits between trusted and untrusted hosts and limits access between the two security domains, often with a DMZ for public servers in between.
  • It can be evaded: tunneling hides a disallowed protocol inside an allowed one, and rules based on addresses can be fooled by spoofed addresses.
  • Variants: a personal firewall on one host; an application proxy that understands a protocol such as SMTP; a system-call firewall that applies rules to system calls (seccomp, Lecture 22).

5.4Classifications and a real system

The U.S. Department of Defense's classic criteria rated systems in four divisions: D minimal; C discretionary protection with auditing (C1, C2); B adds sensitivity labels on objects, i.e. mandatory access control (B1–B3); A formal design and verification. They have since been replaced by the international Common Criteria.

Windows bases security on user accounts: each has a unique security ID, and login creates an access token with the user's and groups' IDs and privileges, copied into every process. Each object has a security descriptor: owner, group, a discretionary ACL, and a system ACL for auditing. Mandatory integrity labels on objects and subjects add MAC (Lecture 22, §4.2). Objects in a container inherit its permissions by default.

5.5Defenses, summarized

PeopleEducate users about safe computing and phishing; verify unusual requests another way; use strong passphrases and never write them where they can be found.
ConfigurationMinimize the attack surface; disable unused services; run daemons with least privilege; physically protect hardware.
SoftwareUse modern, patched systems; run only trusted, code-signed applications; use antivirus where appropriate; encrypt disks and important files.
WatchingEnable logging and auditing and review it; use intrusion detection and firewalls; test with periodic vulnerability assessments; keep the security policy up to date.

Epilogue

Summary and glossary

∎What to take away

  • Security violations break confidentiality, integrity, availability or service; they come through masquerading, replay, man-in-the-middle, hijacking and privilege escalation, at the physical, application, OS and network levels.
  • Malware and memory-safety bugs threaten programs; worms, scanning and DoS threaten systems and networks. Least privilege bounds the damage; NX pages, ASLR and canaries raise the cost.
  • Symmetric ciphers (AES) are fast but need a shared key; asymmetric ones (RSA) solve distribution but are slow; TLS combines them.
  • Hashes detect change, MACs add a shared key, signatures let anyone verify. Certificates bind public keys to identities and defeat man-in-the-middle.
  • Store passwords as salted, slow hashes; add one-time passwords and multiple factors.
  • Defense in depth: policy, assessment, detection, firewalls, patching, logging, and educated users.

Chapter 0

Operating-system services

An OS provides an environment for executing programs, and services to programs and users.

0.1Services that help the user

User interfaceAlmost every OS has one, such as a command line (CLI), graphical (GUI), touch screen, or batch interface.
Program executionLoad a program into memory, run it, and end it, normally or abnormally (with an error).
I/O operationsA running program may need I/O to a file or a device, but it cannot drive devices itself.
File-system manipulationRead and write files and directories, create and delete them, search, list information, manage permissions.
CommunicationsProcesses exchange information on one computer or across a network, through shared memory or message passing.
Error detectionErrors occur in the CPU and memory, in devices, and in user programs. Take the right action for each, and offer debugging facilities.

0.2Services that keep the system efficient

Resource allocationWith many users or jobs at once, share out CPU cycles, main memory, file storage, and devices.
LoggingKeep track of which users use how much of which resources.
Protection and securityControl all access to system resources, keep concurrent processes from interfering, and authenticate users against outsiders.

Chapter 1

Booting, or starting the services

Before any service exists, something has to load the kernel into memory and jump to it.

1.1Bootstrapping

  • Booting ("bootstrapping") is loading and starting the operating system.
  • A bootstrap program (bootstrap loader) locates the kernel, loads it into memory, and starts it.
  • It is usually a two-step process. A simple bootstrap loader runs first, which fetches a more complex one, which loads the kernel from disk and jumps to it.
  • The first loader must be inside the machine, not on an external device. It lives in ROM or flash firmware.

1.2The boot chain

Step throughFrom power button to login prompt
BIOS or UEFI

In the classic picture, BIOS firmware reads the first sector of the disk (the MBR), whose 446 bytes of code load the second stage. Modern PCs use UEFI firmware, which reads a small FAT partition and runs the boot loader directly from a file. Either way, GRUB is the second stage, and LILO is now rarely used.

Chapter 2

System calls, or accessing the services

The programming interface to the kernel, and the only door from user mode into kernel mode.

2.1System calls and APIs

  • A system call is the programming interface to a service provided by the OS. The kernel side is typically written in C or C++.
  • Programs mostly reach system calls through a high-level application programming interface (API) rather than directly.
  • The three most common are the Win32 API for Windows, the POSIX API for POSIX systems (virtually every UNIX, Linux, macOS), and the Java API for the JVM.

2.2How many system calls does cp make?

Copying one file to another sounds like one operation. Watch it below as a sequence of system calls.

Step throughcp in.txt out.txt, call by call

A simplified trace in the style of strace, with a 4096-byte buffer. Try strace cp in.txt out.txt in the course VM to see the real one. It has many more calls, most of them from loading the C library.

2.3An example API, read()

#include <unistd.h> ssize_t read(int fd, void *buf, size_t count);

From man 2 read.

  • int fd is the file descriptor to read from.
  • void *buf is the buffer the data goes into.
  • size_t count is the most bytes to read.

It returns the number of bytes read. 0 means end of file, and −1 means an error (with the reason in errno).

2.4API, system call, OS

  • Each system call has a number. The system-call interface keeps a table indexed by these numbers.
  • It invokes the intended call in the kernel and returns its status and any return values.
  • The caller needs to know nothing about how the call is implemented. It obeys the API and understands what the OS will do. The details are hidden by the run-time support library (for C, libc).

Chapter 3

Inside a system call

How the call's number and arguments reach the kernel, and how the kernel handles a pointer it cannot trust.

3.1Passing parameters

A call usually needs more than its number. What and how much depends on the OS and the call. There are three general methods.

1 · RegistersPut the parameters in CPU registers. Fast, but there may be more parameters than registers.
2 · Block + pointerStore the parameters in a block in memory and pass its address in a register. Used by Linux and Solaris for calls with many or large arguments.
3 · StackThe program pushes the parameters, and the OS pops them. Like the pointer method, it limits neither the number nor the length of parameters.

3.2Linux on x86-64

  • The trap instruction is syscall on x86-64 (int 0x80 on 32-bit x86).
  • The system-call number goes in rax. Up to six arguments go in rdi, rsi, rdx, r10, r8, r9. The result comes back in rax.
  • Complex arguments, such as a structure or a buffer, are passed as user-space pointers, using method 2 for the data and method 1 for the pointer.

3.4When the pointer is bad

What if buf in read(fd, buf, count) points somewhere invalid, or into the kernel? The kernel must never trust a user pointer. It uses the special functions below to touch user memory.

Chapter 4

Loadable kernel modules, or extending the services

New kernel code, loaded into the running kernel, without rebuilding or rebooting.

4.1What a module is

  • A loadable kernel module (LKM) is an object file with code that extends a running kernel. It can be loaded and unloaded on demand at run time, without rebuilding or recompiling the kernel.
  • Windows has kernel-mode drivers, Linux has LKMs, macOS had kernel extensions (kexts).
  • Most device drivers are written as modules. The installed ones live under /lib/modules/$(uname -r), and lsmod lists the loaded ones.

4.2Writing one

  • Modules are written in C and built against a Linux kernel source tree, into a .ko (kernel object) file.
  • The running kernel must be the same version the module was built for.
  • A module declares MODULE_AUTHOR and MODULE_LICENSE.
  • The init function runs when the module loads. It initializes everything, typically by registering a handler with the kernel. It returns 0 on success, negative on failure.
  • The exit function runs when it unloads. It frees everything.
#include <linux/kernel.h> #include <linux/module.h> MODULE_AUTHOR("Awesome Developer"); MODULE_LICENSE("GPL"); static int __init hello_init(void) { printk(KERN_ALERT "Hello world: I am a developer in CS3753 speaking from the Kernel\n"); return 0; } static void __exit hello_exit(void) { printk(KERN_ALERT "Goodbye from a developer in CS3753, I am exiting the Kernel\n"); } module_init(hello_init); /* older style: name it init_module() */ module_exit(hello_exit); /* older style: cleanup_module() */

Epilogue

Summary and glossary

∎What to take away

  • The OS offers services to users (UI, program execution, I/O, files, communication, error detection) and to itself (allocation, logging, protection).
  • Booting runs firmware, then a small loader, then a second-stage loader such as GRUB, which loads the kernel.
  • Programs reach services through APIs (POSIX, Win32, Java), which make system calls. A system call is a number and arguments, a trap into kernel mode, a table lookup, and a return.
  • On Linux x86-64, the pieces are syscall, number in rax, arguments in registers, pointers for complex data, checked with copy_*_user.
  • Loadable kernel modules add code, such as drivers, to a running kernel. They must match its version and run with full privilege.
In the lab

Basecamp 0 boots the course VM through exactly this chain, headless, under QEMU. Basecamp 5 has you write a module. It uses the same module_init / module_exit skeleton, plus a file_operations table that makes your code the target of read() and write() system calls.

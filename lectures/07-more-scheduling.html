Chapter 0

Priority scheduling

Not all processes are equal: give the CPU to the most important one.

0.1Priorities

  • Each process has an integer priority; the CPU goes to the highest-priority process. Here, as in Linux, a smaller number means higher priority.
  • It can be preemptive (a newly ready higher-priority process takes the CPU) or nonpreemptive (it waits for the current burst to end).
  • SJF is a priority scheduler whose priority is the predicted next CPU burst: the shorter the burst, the higher the priority.
  • Problem: starvation. A low-priority process may never run if higher-priority work keeps arriving.
  • Solution: aging. The longer a process waits, the higher its priority becomes.

0.2Two examples

All processes arrive at time 0. In the first example, each priority level holds one process, so the schedule is just the priority order: average wait 8.2. The second example has ties. Processes with the same priority take turns round robin (q = 2), and a lower level runs only after every higher level is empty.

Chapter 1

Multilevel queues

Split the ready queue, give each part its own policy, and let processes move between parts.

1.1One queue per class

The ready queue becomes several queues. A multilevel queue scheduler is defined by:

  • the number of queues;
  • the scheduling algorithm within each queue;
  • how to pick which queue a process enters;
  • scheduling among the queues, usually strict priority: run a lower queue only when all higher queues are empty.

With priority scheduling, keep one queue per priority. Or prioritize by process type, as in Fig. 1.1.

1.2Multilevel feedback queue

In a multilevel feedback queue (MLFQ), a process can move between queues. Beyond the four parameters above, it needs rules for when to promote a process and when to demote it. Aging fits naturally: promote a process that has waited too long.

The classic three-queue example:

  • Q0: RR with q = 8 ms. Every new process enters here. If it does not finish within 8 ms, it moves to Q1.
  • Q1: RR with q = 16 ms. If it still does not finish, it moves to Q2.
  • Q2: FCFS, run only when Q0 and Q1 are empty.
  • A process arriving in a higher queue preempts one running from a lower queue.

A process preempted by a new arrival keeps its place at the head of its queue and the part of its quantum it has already used.

1.3What MLFQ learns

  • By age: with promotion for old processes, a low-priority process eventually reaches the CPU. No starvation.
  • By behavior: CPU-bound processes use up their quanta and sink. Interactive and I/O-bound processes block before the quantum ends and stay near the top, so they get fast response.
  • Over time, a process settles in the queue whose quantum matches its typical CPU burst. MLFQ gets most of SJF's benefit without being told burst lengths.

Chapter 2

Linux, before CFS

140 priority levels, a nice value, and a scheduler whose cost did not grow with the number of tasks.

2.1Priorities and nice

  • Linux has 140 priorities, 0–139. 0–99 are for real-time tasks and 100–139 for normal (non-RT) tasks. In the O(1) scheduler, higher priority also meant a longer quantum: the textbook's figure runs from 200 ms at the top to 10 ms at the bottom.
  • A normal task's priority comes from its nice value, −20 to +19, where lower is higher priority. A process at nice +15 is "nicer" to the others.
  • To run a heavy computation politely, type nice -n 19 ./compute. Lowering niceness to raise priority usually requires root.
  • Each Linux scheduler uses the nice value in its own way. §2.3 shows how O(1) used it, and §3.4 how CFS does.

2.2O(N), then O(1)

  • Linux 2.4: O(N). Each task had a "goodness"; an interactive task that gave up the CPU early was rewarded with a higher value next time. The list was unordered, so picking the next task meant scanning all N tasks. That does not scale.
  • Linux 2.6 to 2.6.22: O(1). Keep one queue per priority. Picking the next task means finding the first nonempty queue among a fixed 140, so the cost is bounded by the number of priorities, not the number of tasks. It is priority-based and preemptive.

2.3Active and expired arrays

  • There are two arrays, each indexed by the 140 priorities: active holds tasks with quantum left, and expired holds tasks that have used up theirs.
  • The scheduler runs the first task of the highest-priority nonempty queue in active. At worst it searches 140 levels. The real kernel keeps a 140-bit bitmap of nonempty queues, and one find-first-set-bit instruction per word locates the first one.
  • A task that exhausts its quantum moves to expired and cannot run again until every other task has used up its quantum. When active is empty, the two arrays are swapped, which is just a pointer swap.
  • On the move, the priority is recalculated: nice priority ± f(interactivity), at most ±5. Tasks that sleep a lot waiting for I/O get closer to −5, a boost. Compute-bound tasks get closer to +5. Only normal priorities, 100–139, are adjusted.

Why it was replaced

"The O(1) scheduler is a collection of heuristics," its author Ingo Molnar said. Deciding who counts as interactive, and by how much, made it hard to maintain and hard to predict.

Chapter 3

The Completely Fair Scheduler

Linux 2.6.23 replaced quanta and heuristics with one number per task.

3.1The ideal CPU

  • Picture an ideal CPU that runs N tasks truly in parallel, each at 1/N speed. With a 4 GHz processor and four tasks, each gets a 1 GHz processor at every instant. Everyone progresses all the time: perfectly fair.
  • A real core runs one task at a time. It gives concurrency, not parallelism.
  • CFS's goal is to approximate the ideal CPU. When a task runs for T, CFS keeps a running balance of how much time is owed to each of the others, as if they had all run on the ideal CPU.
  • CFS is based on a proportion of CPU time rather than fixed time allotments. It has two scheduling classes, default and real-time.

3.2Keeping the books

There are four tasks. In any interval T, the ideal CPU gives each one T/4. When the real CPU gives all of T to T1, T1 is over-allocated by 3T/4 and each of the others is owed T/4. Run them round robin and watch the balance Wi, the time owed to task i.

Step throughTime owed to each task

3.3Virtual run time

  • The bookkeeping simplifies. Sum the run time each task has received, and run the task with the minimum sum. That is the same task as the one owed the most on the ideal CPU.
  • The caveat: a task that was blocked for a long time, or is brand new, has a tiny sum. It would then hog the CPU until its sum caught up, blocking everyone else.
  • So CFS keeps a virtual run time, vruntime. When a task joins the run queue, whether new or waking from I/O, its vruntime is raised to at least the minimum vruntime in the queue. It becomes the next to run, but only a little ahead of the others.
  • CFS picks the minimum vruntime at every decision. That also makes it responsive: an interactive task gets the CPU almost immediately after its I/O completes.

3.4Priorities are weights

Each nice value maps to a weight. Nice 0 is 1024, and each step multiplies it by about 1.25. vruntime then advances more slowly for heavier tasks:

Δvruntime = Δ(actual run time) × 1024 / weight

At nice 0, vruntime equals real run time. A higher-priority task has a larger weight, so its vruntime grows more slowly. It stays leftmost longer and runs more often. Over time, each task gets CPU in proportion to weighti / Σ weight, the weighted round robin share from Lecture 06, but without quanta.

3.5Implementation: one red-black tree

  • Runnable tasks sit in a red-black tree keyed by vruntime. The leftmost node is the next to run; the kernel caches a pointer to it, so picking is O(1). Inserting a task or reinserting it after it runs is O(log N).
  • All normal tasks share one tree, whatever their priority. Priority only changes how fast vruntime grows, so there is no need for 40 run queues, one per nice level.

3.6Fair to whom?

CFS is fair to tasks, not necessarily to applications. If application A1 has 100 threads and the interactive A2 has one, A1 gets 100/101 of the CPU. With group scheduling, A1 and A2 are separate groups that split the CPU fairly first. A1's 100 threads then share A1's 50%.

Chapter 4

Real-time scheduling

In real-time systems, finishing late is the same as being wrong.

4.1Hard and soft deadlines

Hard real timeCertain tasks must finish by a certain time or the system fails. Robots and self-driving cars need a real-time OS (RTOS) that actuates the arm or turns the steering wheel by the deadline.
Soft real timeMeet most deadlines, allow some misses, perhaps with probabilistic guarantees. For some systems, meeting 60% of deadlines is enough. Linux's priority-based real-time classes are soft real time.

4.2Earliest deadline first

  • EDF runs the task with the earliest deadline. In the first example, all tasks arrive at 0 and the order is P3, P1, P2, P4. Every deadline is met.
  • It is preemptive: a newly arrived task with an earlier deadline preempts a running task with a later one. In the second example, the scheduler decides again after every time unit.
  • On one CPU, if any schedule can meet all the deadlines, EDF does. Compare it with FCFS and SJF below.

4.3Real-time classes in Linux

  • SCHED_FIFO: real-time first-come first-served, soft real time.
  • SCHED_RR: real-time round robin, soft real time.
  • SCHED_DEADLINE: EDF-based. Each task declares its runtime, period and deadline, and the kernel admits it only if the declared demands fit on the CPUs. It is the closest Linux comes to hard real time, but mainline Linux is not a hard RTOS.
  • FIFO and RR tasks use the real-time priorities, 0–99 in Fig. 2.1. Every real-time task outranks every normal task: a weight only shares the CPU, but a policy ranks tasks (Basecamp 2, Part 3).

Chapter 5

Multiprocessor scheduling

With more than one CPU, the scheduler also has to decide where each task runs.

5.1SMP: one queue or many?

Multiprocessors come in several forms: multicore CPUs, multithreaded cores, NUMA systems, and heterogeneous multiprocessing (fast and slow cores). In symmetric multiprocessing (SMP), each processor schedules itself. Either:

  • (a) all threads wait in one common ready queue. It is simple, but the cores contend for the queue's lock; or
  • (b) each processor has its own private queue. There is no contention and caches stay warm, but the queues must be balanced. Linux does this.

5.2Affinity and load balancing

  • A thread that has been running on a processor has filled that processor's cache with its data. It has affinity for that processor.
  • Soft affinity: the OS tries to keep a thread on the same processor but makes no promise. Hard affinity: the process names the set of processors it may run on. Linux supports both; taskset and sched_setaffinity() set hard affinity, and Basecamp 2 uses taskset -c 0 to pin its spinners.
  • Load balancing keeps work evenly spread. In push migration, a periodic task checks each CPU's load and pushes tasks off overloaded ones. In pull migration, an idle CPU pulls a waiting task from a busy one.
  • These goals conflict. Migrating a thread balances load but throws away its warm cache, which breaks affinity. Spreading work over every core fights power management, which wants to power unused cores down, especially on phones.

5.3NUMA-aware scheduling

On a NUMA machine, each CPU reaches its own memory quickly and the other node's memory slowly, over an interconnect. A NUMA-aware OS allocates a thread's memory on the node where the thread runs, and it prefers to keep the thread there. Affinity then covers memory as well as cache.

Epilogue

Summary and glossary

∎What to take away

  • Priority scheduling runs the most important process first. It can starve others; aging fixes that.
  • Multilevel queues give each class its own queue and policy. Feedback queues move processes by behavior and age, approximating SJF without being told burst lengths.
  • Linux has 140 priorities: 0–99 real-time, 100–139 for nice −20 to +19. The O(1) scheduler used active and expired arrays and interactivity heuristics.
  • CFS runs the task with the minimum vruntime, which advances at 1024/weight per unit of run time. Shares follow the weights; one red-black tree holds every normal task; waking tasks start at the minimum vruntime; groups make it fair across applications.
  • Real time: EDF meets every deadline that can be met on one CPU. Linux offers SCHED_FIFO, SCHED_RR and SCHED_DEADLINE.
  • Multiprocessors: per-CPU queues, affinity, push and pull migration, NUMA awareness, and trade-offs between them.

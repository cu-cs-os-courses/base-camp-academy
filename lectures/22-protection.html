Who may do what,
to which object?

Every mechanism in this course so far, from the mode bit to page tables to file permissions, answers one question on every access: is this allowed? This lecture turns that question into a model: processes run in domains, a matrix says what each domain may do to each object, and the OS stores and enforces that matrix. Then it looks at how real systems slice up power: setuid, roles, labels the owner cannot override, capabilities that split root into pieces, sandboxes, and the stack inspection of the Java VM.

Protection

Domains, the access matrix, and how real systems enforce it.

Instructor: Yueqi Chen · Textbook: Silberschatz, Ch. 17
Chapter 0

Goals and principles

Protection is about mechanisms inside the system: making sure each object is used correctly, and only by those allowed to. (Lecture 23, Security, is about attackers from outside.)

0.1The protection problem

  • In one protection model, a computer is a collection of objects, hardware (CPU, memory, printers, disks) or software (files, programs, semaphores).
  • Each object has a unique name and is accessed through a well-defined set of operations: a file is read, written, executed; a semaphore gets wait and signal.
  • The protection problem: ensure that each object is accessed correctly, and only by those processes that are allowed to do so.

0.2The principle of least privilege

The guiding principle: programs, users and systems get just enough privilege to do their tasks.

  • Properly set permissions limit the damage when an entity has a bug or is abused.
  • Privilege can be static (for the life of the system or the process) or dynamic, changed by the process as needed: domain switching, privilege escalation.
  • Compartmentalization is a derivative idea: protect each individual system component with its own specific permissions and access restrictions.
Key idea

The question is never only "can this program do its job?" but "what else could it do, if it were buggy or hijacked?" Least privilege keeps that second answer small.

0.3Grain, audit, defense in depth

  • Grain. Coarse-grained privilege management is simpler, but least privilege then comes in large chunks: a traditional UNIX process has either its user's powers or root's. Fine-grained management (file ACLs, role-based access control) is more complex and has more overhead, but protects more.
  • A protection domain can be a user, a process, or even a procedure.
  • An audit trail records all protection-related activity, to understand what happened and why, and to catch what should not have.
  • No single principle is a cure-all: we need defense in depth, several independent layers.

Chapter 1

Rings and domains

Hardware rings order privilege in a few big steps; protection domains describe it object by object.

1.1Protection rings

  • Components are ordered by privilege and protected from each other: the kernel in one ring, applications in another. This separation needs hardware support (Lecture 21, §3.3).
  • Gates transfer control between rings: the syscall instruction, and also traps and interrupts.
  • Hypervisors needed yet another level. ARM added TrustZone, a secure world entered only through the SMC (Secure Monitor Call) instruction, to protect crypto keys and the NFC secure element even from the kernel. Android uses it for its keystore.

1.2Protection domains

A process operates inside a protection domain, which specifies the resources it may access: a set of objects and the operations allowed on each.

The ability to execute an operation on an object is an access right: <object-name, rights-set>, where the rights-set is a subset of the object's valid operations. A domain is a set of access rights.

Domains may share rights (O4 in Fig. 1.2). The association between a process and a domain can be static, or dynamic, in which case the process can switch domains. A process should have access only to the objects it currently needs: the need-to-know principle.

1.3Domains in UNIX

In UNIX, a domain is a user ID. There are three ways to switch domains:

  • Through the file system: each file has a domain bit, the setuid bit. When a file with setuid on is executed, the process's effective user ID becomes the file's owner; when it finishes, the ID is reset.
  • Through passwords: su switches to another user's domain when that user's password is given.
  • Through commands: sudo cmd runs one command in another domain, if the original domain is allowed to (the sudoers file) or a password is given.

1.5Domains in Android: one user ID per app

  • Android gives every application its own user ID. At install time the installd daemon assigns the app a distinct UID and GID and a private data directory, /data/data/<appname>, owned by that UID/GID alone.
  • Apps then enjoy the same separation UNIX gives separate users: a quick, simple way to get isolation, security and privacy, reusing a mechanism that already existed.
  • Android extends it: a modified kernel allows some operations, such as opening network sockets, only to members of a particular group (AID_INET, GID 3003). And some UIDs are marked isolated, which blocks them from making RPC requests to all but a bare minimum of services.

Chapter 2

The access matrix

Write every domain's rights on every object into one table, and protection becomes a lookup.

2.1Rows are domains, columns are objects

View protection as a matrix: rows are domains, columns are objects, and Access(i, j) is the set of operations a process in domain Di may invoke on object Oj.

If a process in Di tries operation op on Oj, then op must be in Access(i, j). The user who creates an object can define its column.

2.2Changing the matrix itself

For dynamic protection, the matrix needs operations that add and remove rights, controlled by special rights of their own:

switchPut domains in the columns too: switch in (Di, Dj) lets a process move from Di to Dj.
copy ( * )read* in (Di, Oj) lets Di copy read into any other domain's entry in the same column.
ownerowner of Oj lets Di add or remove any right anywhere in column j.
controlcontrol in (Di, Dj) lets Di remove rights from row Dj. Copy and owner apply to objects; control applies to domain objects.

2.4Mechanism vs. policy

The access matrix separates mechanism from policy:

  • Mechanism: the OS provides the matrix and its rules, and ensures the matrix is changed only by authorized agents and that the rules are strictly enforced.
  • Policy: users decide who may access which object, in which mode.

But the matrix does not solve the general confinement problem: guaranteeing that no information held in an object ever leaks out of its execution environment. A domain allowed to read a file can always copy what it read somewhere else.

Chapter 3

Implementing the access matrix

The matrix is huge and mostly empty. Four ways to store only what matters.

3.1Four representations

1 · Global tableStore triples <domain, object, rights-set>. For operation M on Oj in Di, search for <Di, Oj, Rk> with M ∈ Rk. Simple, but the table can be too big for memory, and grouping is hard: an object every domain can read needs an entry per domain.
2 · Access lists (per object)Each column becomes the object's access-control list (ACL): pairs <domain, rights-set> for every domain with non-empty rights. Easily extended with a default set: if M is in the default set, allow it too.
3 · Capability lists (per domain)Each row becomes the domain's capability list: objects with the operations allowed on them. An object's name or address in that list is a capability; holding it means access is allowed. The list belongs to the domain but the domain can never touch it directly: the OS keeps it, like a "secure pointer".
4 · Lock-keyA compromise: each object has a list of unique bit patterns, its locks; each domain has a list of keys. A process may access the object only if its domain holds a key matching one of the locks.

3.3Comparison, and what real systems do

  • The global table is simple but can be large.
  • Access lists match how users think ("who may use my file?"), but the rights of one domain are scattered over many lists, and every access must be checked: with many objects and rights, slow.
  • Capability lists keep one process's rights together, but revoking a right to an object can be inefficient.
  • Lock-key is effective and flexible: keys pass freely between domains, and revocation is easy.

Most systems combine access lists and capabilities. The first access to an object searches its access list; if allowed, a capability is created and attached to the process, and later accesses are not checked again; after the last access, the capability is destroyed. That is exactly UNIX files: open() checks the permission bits once, and the file descriptor it returns is the capability (Lecture 20).

3.4Revoking access rights

Revocation can be immediate or delayed, selective (some users) or general, partial (some rights) or total, temporary or permanent.

With access lists it is simple: search the object's list and delete the entry. Every kind of revocation above is easy.

With capabilities the capabilities must first be found, since they are spread over the domains that hold them:

  • reacquisition: delete capabilities periodically; a process must reacquire them, and is refused if its right was revoked;
  • back-pointers: each object keeps pointers to all its capabilities (MULTICS);
  • indirection: capabilities point to a global table entry that points to the object; delete the entry (CAL). Not selective;
  • keys: each capability carries a key that must match the object's master key; revoke by changing the master key. Who may create and change keys, the owner or others, is a policy decision.

Chapter 4

Beyond user permissions

UNIX permission bits let each owner decide. Modern systems add controls that are finer, or that even root cannot override.

4.1Role-based access control (RBAC)

  • Protection can apply to non-file resources too. Oracle Solaris 10 uses RBAC to implement least privilege.
  • A privilege is the right to execute a system call, or to use an option within one. Privileges can be assigned to processes.
  • Users are assigned roles, which grant privileges and programs; a user enables a role (with a password) to gain its privileges. It resembles the access matrix, with roles in the rows.

4.2Discretionary vs. mandatory access control

  • Traditionally, operating systems used discretionary access control (DAC): UNIX file permissions, Windows ACLs. It is "discretionary" because owners decide, and that is a weakness: users and admins must act to increase protection.
  • Mandatory access control (MAC) is stronger: a policy that even root cannot circumvent makes resources inaccessible except to their intended owners.
  • At its heart are labels on objects and on subjects (including processes). When a subject requests an access, the policy decides whether that label may perform that action on that label.
  • Modern systems implement both, with MAC as a stronger, optional configuration: SELinux, TrustedBSD (used in macOS), Trusted Solaris, Windows integrity levels (since Vista).

4.3Capabilities: slicing up root

  • Hydra and CAP were the first capability-based systems. Linux and Android include a version based on POSIX.1e (a draft that never became a standard).
  • It slices root's powers into distinct areas, each one a bit in a bitmap. Setting or masking bits gives fine-grained control over privileged operations.
  • There are three bitmaps, permitted, effective and inheritable, per process or per thread. A process can start with privileges and voluntarily drop them during execution; once dropped from the permitted set, they cannot be regained. A direct implementation of least privilege.
  • An improvement over all-powerful root, but inflexible: adding a new privilege is hard.

4.5More protection mechanisms

System integrity protectionApple, macOS 10.11: system files and resources are off limits even to root. Extended file attributes mark binaries to prevent changes and block debugging; only code-signed kernel extensions load, and optionally only code-signed apps.
System-call filteringA firewall for system calls, possibly inspecting their arguments too. Linux implements it with seccomp-BPF: a process installs a filter program that allows, denies or kills on each system call.
SandboxingImpose irremovable restrictions early in a process's startup, before main(); afterwards it cannot reach anything outside its allowed set. Java and .NET do it in the VM; others use MAC. Apple's "seatbelt" (macOS 10.5) wrote dynamic profiles in Scheme, down to system-call arguments.
Code signingThe developer signs the executable with a cryptographic hash, so the system can trust the code is exactly as compiled. If it changes, the signature is invalid and some systems refuse to run it. A vendor can also revoke signatures to stop old programs running.

Chapter 5

Language-based protection

Protection can also be written into the programming language and enforced by its runtime.

5.1Protection in the language

  • Specifying protection in a programming language gives a high-level description of policies for allocating and using resources.
  • The language implementation can enforce protection in software when hardware-supported checking is unavailable.
  • Or it can interpret the protection specifications into calls on whatever protection the hardware and OS provide.

5.2Protection in Java

  • The JVM handles protection. When the JVM loads a class, it assigns the class a protection domain that says which operations it may and may not perform.
  • When a library method performs a privileged operation, the JVM inspects the stack to make sure the operation is allowed for everyone who led to it.
  • A method can take responsibility with doPrivileged: stack inspection stops at that frame, so trusted code can do a specific privileged thing on behalf of untrusted callers.
  • More generally, Java's load-time and run-time checks enforce type safety, and classes encapsulate and protect their data and methods from other classes.

Epilogue

Summary and glossary

∎What to take away

  • Protection makes sure each object is used correctly and only by those allowed to. Guided by least privilege, compartmentalization, audit trails and defense in depth.
  • Hardware rings order privilege coarsely; protection domains (a UNIX user ID, an Android app's UID) describe it per object. Setuid, su and sudo switch domains.
  • The access matrix (domains × objects) is the model; switch, copy, owner and control rights let it change safely.
  • It is stored as a global table, access lists (columns), capability lists (rows) or locks and keys. Access lists make revocation easy; capabilities make repeated access fast; real systems combine them (open → file descriptor).
  • RBAC, MAC, POSIX capabilities, SIP, seccomp, sandboxes and code signing give finer or non-overridable control; the JVM adds stack inspection.
In the lab

Basecamp 5 shows both layers. Loading your module takes root inside the VM (in capability terms, CAP_SYS_MODULE); after that, whether filetest may open your device is decided only by the /dev node's permission bits, a discretionary access list.

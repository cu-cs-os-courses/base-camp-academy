Chapter 0

The network stack

Web search, peer-to-peer, streaming video, social networks, and mobile apps all send and receive data over the Internet, through one part of the kernel.

0.1Sockets and the kernel

Every networked application talks to a remote process through the socket API, which offers send(message) and receive(message).

The socket library makes system calls into the kernel's network stack, a manager next to the process, memory, file and device managers.

The stack drives the network interface cards (NICs) on the I/O bus, such as Ethernet, WiFi, and Bluetooth. Those are devices, handled exactly as in Lectures 17–18.

0.2A stack of protocol layers

The network stack is organized into layers of protocols, and each protocol performs a specific set of duties.

To send, each layer passes the packet down to the layer below. To receive, each layer takes the packet from the layer below, processes it, and passes it up.

The socket API sits between the application and the transport layer. Everything below it is in the kernel (or the NIC).

Chapter 1

Packetization

Data leaves as a stack of headers wrapped around a payload, and arrives with the headers peeled off in reverse.

1.1From a buffer to packets

  • To send, the application calls the socket API's send() with a pointer to a user-space buffer holding the data.
  • A large file is cut into smaller packets, say a 1 GB file into 1 KB pieces.
  • Each layer N prepends its own header NHx to data x and hands the result down. The packet grows as it descends. The header carries what the peer layer at the receiver needs to decode the packet.
  • On receipt, each layer N strips off its header, and the packet shrinks as it moves up.
Who cuts

In practice the application usually hands the whole buffer to send(), and TCP does the cutting. It cuts the data into segments that fit one link-layer frame, about 1460 bytes of payload on Ethernet.

Chapter 2

Layer by layer

What each layer is responsible for, from the application down to the voltages on a wire.

2.1Application layer (5)

Ignore the lower layers for a moment. The layer-5 sender exchanges application-specific information with its peer layer 5 at the receiver. A web (HTTP) client sends a GET request for a page, and the remote web server's layer 5 answers with the page.

2.2Transport layer (4), TCP

  • The Internet can lose the application's message. The transport layer's job is end-to-end error recovery, if wanted, which means it must retransmit lost packets. That is TCP, the Transmission Control Protocol.
  • How does the sender know a packet arrived? The receiver sends an acknowledgment (ACK). When should it retransmit? It sets a timer. If the timer expires before the ACK arrives, it retransmits.
  • TCP also guarantees in-order delivery. The web and email need both, because a page with holes, or with its text reordered, is unreadable.
  • So an application can treat a TCP connection as a pipe. Everything put in comes out the other end, in the same order.

2.3When reliability is too slow, use UDP

  • Reliability costs delay, because every retransmission waits for a timer.
  • Interactive real-time applications like video conferencing cannot wait. A packet must arrive within about 30 ms or it is useless.
  • Voice-over-IP apps like Skype and FaceTime can tolerate loss. The audio drops out briefly, and that's OK. They are built on the unreliable UDP (User Datagram Protocol) at layer 4 instead of TCP.

2.4Network layer (3), routing

The Internet is many routers connected into a graph. The Internet Protocol (IP) must route each packet to its destination, and there are many routes. The network layer looks for the shortest path, for example with Dijkstra's algorithm. "Shortest" may mean fewest hops, shortest distance, lowest delay, or lowest cost.

Every router implements the network layer. IP routing can lose packets, because any router or link may fail, and congested router buffers overflow. That's fine, as long as TCP retransmits them.

2.5Data link (2) and physical (1)

Data link layer. Every link between two neighboring nodes (routers or endpoints) must carry packets. This layer defines where a packet begins and ends (framing), and since packets can be lost on a link, it may also retransmit locally. Examples are Ethernet, WiFi, and Bluetooth.

Physical layer. It defines how 1s and 0s actually travel along each link. A 1 might be +5 volts and a 0 be 0 volts. Or 1s and 0s might be different frequencies.

Chapter 3

A recap of what the OS provides, and how it protects itself

A virtual machine is built from exactly these pieces, so start by laying them out again.

3.1What does an operating system provide?

An OS is a layer of software between many applications and diverse hardware. It does the three things below.

  1. It provides a hardware abstraction, so an application saving a file need not know how the disk operates.
  2. It arbitrates access to resources among applications, and lets them share (one printer, many apps).
  3. It provides protection. It isolates apps from each other, protects the OS from apps, and limits how much of a resource any one app consumes.

A task (application, job, process) is the unit of work. It consists of its code and data in memory, plus the OS's data about it, the task descriptors.

3.2Privileged instructions and the mode bit

Protection means stopping apps from writing privileged memory (another app's, or the kernel's) and from running the privileged operations below.

  • memory address mapping, invalidating TLB entries, flushing caches,
  • loading system registers, changing the processor mode from kernel to user,
  • changing processor voltage and frequency, halting or resetting the CPU,
  • and performing I/O.

But then how can a task reach OS functionality at all? The CPU needs to know whether an instruction is allowed right now, and how to switch from the task's code to the OS's. The hardware helper is the mode bit.

3.3Rings of privilege

Intel x86 CPUs support four rings of privilege, 0 (most) to 3 (least). In the common configuration, the OS kernel (Linux, Windows) runs in ring 0, applications in ring 3, and rings 1–2 are unused.

One possible configuration for virtual machines puts the hypervisor in ring 0, the guest OS in ring 1 or 2, and applications in ring 3.

Chapter 4

Virtual machines

Extend the process abstraction one step further, and give an entire operating system the illusion of its own machine.

4.1What is a virtual machine?

  • A simulated computer running inside a real one. The virtual computer can run a different operating system from the host.
  • Every request for real hardware is routed to the appropriate host hardware, so the virtual OS and its applications do not know they are virtual. Like a person living in the Matrix.
  • "Virtual X." A process already has the illusion of its own memory (virtual memory) and its own CPU (time slicing). A virtual machine adds the illusion of its own hardware, and extends the idea from one process to an entire OS with its own memory, CPU, and I/O devices.

4.2The hypervisor

A Type 1 hypervisor provides a virtualization layer for guest operating systems and sits just above the hardware. Each guest OS believes it is running on real hardware.

Each guest keeps providing abstraction, arbitration and protection for its own applications. The hypervisor does the same for the guests.

Type 2, too

A Type 2 (hosted) hypervisor, such as VirtualBox or VMware Workstation, runs as an application on an ordinary host OS instead of directly on the hardware. Linux's KVM is somewhere in between. It is a kernel module that turns Linux itself into a hypervisor. The QEMU VM you use in the labs runs on top of one of these.

4.3How it works, trap-and-emulate

  • The goal is to run a VM at close to native speed. Emulating or interpreting every instruction in software is far too slow.
  • The solution is to let the guest OS run normally, directly on the CPU, but not in kernel mode. Any privileged instruction it executes then traps to the hypervisor, which is in kernel mode.
  • The hypervisor emulates only those instructions, then passes control back to the guest, which is a VM entry. The trap into the hypervisor is a VM exit.
  • Ordinary instructions run at full speed, and only privileged ones pay for a trap. This is trap-and-emulate.

Why classic x86 needed help

Trap-and-emulate needs every sensitive instruction to trap when run outside kernel mode (Popek and Goldberg, 1974). Classic x86 broke that rule. POPF in ring 1 silently ignores changes to the interrupt flag instead of trapping. VMware worked around it with binary translation, Xen by modifying the guest kernel (paravirtualization). Since 2005–06, Intel VT-x and AMD-V add a "guest mode" in which the guest kernel runs in its own ring 0 and every sensitive instruction can be made to exit.

4.5Why virtual machines?

Many OSes, one hostRun several operating systems simultaneously on the same machine.
Fault isolationIf one guest OS crashes, the others keep running. Also useful for debugging a new OS.
Easier deploymentShip an app inside a VM image customized for it, instead of worrying about compatibility with the target OS. Useful for cloud servers.

4.6Cloud computing

  • It is very easy to provision and deploy VM instances in the cloud. Amazon's Elastic Compute Cloud (EC2) was built on Xen virtualization.
  • There are different types of instances (standard, high-memory, high-CPU), and users create and reboot their own VMs.
  • To store data persistently, EC2 is supplemented with another cloud service, such as Amazon's Simple Storage Service (S3).

Since 2017, new EC2 instance types run on AWS Nitro, a KVM-based hypervisor with its virtualization work offloaded to dedicated cards.

4.7Process VMs and the Java Virtual Machine

Process VMs differ from system VMs. The goal is not to run several OSes on one host, but portable execution of one application across different hosts.

Java programs are compiled to byte code that runs on any Java VM. The JVM acts as an interpreter, turning each byte-code instruction into a local action on the host OS.

Just-in-time (JIT) compilation speeds this up. Byte code is compiled at run time into native machine code that runs directly on the hardware.

A JVM virtualizes an abstract machine, a software specification, not real hardware as system VMs do.

Epilogue

Summary and glossary

∎What to take away

  • Applications reach the network through sockets. The kernel's stack is five layers, each adding its header on the way down and stripping it on the way up.
  • TCP turns a lossy network into a reliable, ordered pipe with ACKs, timers and retransmission. UDP skips that for applications that value timeliness over completeness.
  • IP routes packets over a graph of routers along shortest paths, and may lose them. The data link and physical layers move frames and bits across single links.
  • The mode bit and privilege rings let the kernel keep privileged instructions for itself.
  • A hypervisor runs guest OSes directly on the CPU and traps their privileged instructions (trap-and-emulate), so most code runs at full speed. Hardware support made this work on x86.
  • Process VMs like the JVM virtualize an abstract machine for portability, and use JIT compilation to regain speed.
In the lab

Every Basecamp lab ran inside a QEMU virtual machine, that is, a guest Linux kernel that believed the CPU, disk and serial port were its own. The make check harness talks to it over a virtual serial device, emulated exactly as in §4.4.

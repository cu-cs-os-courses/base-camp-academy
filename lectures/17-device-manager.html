Chapter 0

Where devices plug in

Before the OS can manage a device, the device has to be wired to the CPU. This chapter shows three pictures, from 1945 to today.

0.1The von Neumann computer

In 1945, von Neumann described a stored-program computer, in which memory holds both instructions and data. As such, loading a new program meant writing memory, not rewiring the machine.

Then, more devices came, such as card readers, magnetic tape, printers, displays, and disk storage. A shared system bus evolved to connect them all. The system bus is actually three buses, namely control, address, and data.

0.2A typical PC bus structure

Dated, on purpose

PCI, IDE, SCSI, and parallel and serial ports form the classic picture of the textbook. A laptop today has PCI Express links, NVMe SSDs, and USB instead. However, the idea that this chapter needs has not changed. Devices are attached to buses behind controllers, and the CPU talks only to the controllers.

0.3How devices get the CPU's attention

Today, the CPU reaches memory over a memory bus and devices over an I/O bus. An I/O bridge joins the two buses.

Devices signal the CPU with device interrupts, such as "the disk read you asked for is done" or "a packet arrived".

The CPU is also interrupted from inside. It is interrupted by the timer (this is how the scheduler of Lecture 6 regains control) and by the running instruction itself, through traps and faults.

Chapter 1

Exceptions, the four ways the CPU is interrupted

Every device request and every device reply crosses into the kernel through the same mechanism. The mechanism has four classes. They differ in one important respect, namely where execution continues afterward.

1.1Classes of exceptions

ClassCauseExamplesAfterward
Trapintentional exception, that is, a software interruptsystem callsalways returns to the next instruction · synchronous
Faulta potentially recoverable errordivide by 0, stack overflow, invalid opcode, page fault, segmentation faultmight return to the current instruction · synchronous
Interrupta signal from an I/O devicedisk read finished, packet arrived at the network card (NIC)always returns to the next instruction · asynchronous
Aborta nonrecoverable errorhardware bus failurenever returns · synchronous

Synchronous means that the running instruction caused the exception. Therefore, it happens at the same point every time the program runs. In contrast, an interrupt is asynchronous. The device picks the moment, and the instruction that the interrupt lands on has nothing to do with it.

1.3The x86 exception table

An x86 CPU numbers its exceptions from 0 to 255. Numbers 0–31 are reserved for the exceptions of the CPU itself (divide by zero, protection violations, page faults). The OS assigns the rest to device interrupts and traps.

An exception-table base register points to the table. Therefore, the OS can put the table anywhere in memory. On x86, this register is the IDTR, and the table is the interrupt descriptor table (IDT).

When exception n happens, the CPU reads entry n of the table and jumps to the handler that the entry names. The exception numbers are offsets, and they form the interrupt vector.

Does Linux still make system calls with exception 128?

32-bit Linux did. A program executed int 0x80 (0x80 = 128), which raises exception 128 and lands in the system-call handler. In contrast, 64-bit x86 programs use a dedicated syscall instruction, which jumps to a handler address that the kernel stores in a model-specific register. It is faster. However, it is still a trap. It is intentional and synchronous, and it returns to the next instruction.

Chapter 2

The device manager

The device manager is the part of the kernel that owns every I/O device. It is also the reason why one program can read a disk and a keyboard with the same call.

2.1Its place in the kernel

The kernel divides the hardware among managers. The scheduler owns the CPU, and the memory manager owns RAM.

The device manager owns everything else, such as disks, displays, mice, and network cards. The file system is one of its most important clients, because every file read ends up as a disk request.

2.2What the device manager does

It controls the operation of the I/O devices.

  • It issues I/O commands to the devices.
  • It catches their interrupts.
  • It handles their errors.
  • It provides a simple, easy-to-use interface to programs.
  • It provides device independence, which means that all devices have the same interface.
Key idea

Device independence is the main goal. A program that copies its input to its output should not need to know whether the input is a file on disk, a keyboard, or a network connection.

2.3How it is organized

Programs enter through the system-call interface, which offers open, close, read, write, set, and so on. Some requests go through the file manager first.

The device manager (the I/O subsystem) has two layers. The device-independent top layer is shared by all devices.

The device-dependent bottom layer is a set of device drivers, one per kind of device, behind a common device-driver interface.

Drivers talk across the hardware interface to the command, status, and data registers of a device controller.

Chapter 3

The system-call interface

One small set of calls has to fit every device. Devices differ in four ways, and these differences decide how the calls behave.

3.1One interface for every device

The goal is a simple, standard interface that reaches most devices. Every I/O device driver should support open, close, read, write, set (ioctl in UNIX), stop, and so on. However, devices still differ in the four ways below.

Block vs. characterThis difference is how we talk to the device, either in addressable fixed-size blocks (disk) or in a stream of bytes (keyboard, serial port).
Sequential vs. random accessOld tape must be read in order. In contrast, a disk can jump directly to any block.
Blocking vs. non-blockingBlocking means that the process waits on a wait queue until the I/O completes. Non-blocking means that the call returns immediately with however many bytes were ready (keyboard, mouse, network).
Synchronous vs. asynchronousAsynchronous means that the call returns immediately, and the full number of requested bytes is transferred at some later time.

3.3Beyond read and write with ioctl and fcntl

Programs need a richer interface than open, close, read, and write. For example, they need to set the speed of a device, eject a disk, or ask a terminal how wide it is.

int ioctl(int fd, int cmd, ...) makes a system call that runs a device-specific command cmd on the device behind fd. The kernel directs the command to the driver of that device. New devices and new device functions need no new system calls. As such, the kernel stays extensible. UNIX, Linux, and macOS support ioctl, and Windows has its own version.

fcntl (file control) is a related call. It configures file parameters. Since UNIX models each device as a file, these parameters often control I/O behavior. This call is part of POSIX. Therefore, it is portable across platforms.

/* ask the terminal for its size */ struct winsize ws; ioctl(STDOUT_FILENO, TIOCGWINSZ, &ws); printf("%d x %d\n", ws.ws_col, ws.ws_row); /* eject a CD-ROM */ ioctl(cd_fd, CDROMEJECT); /* make a socket non-blocking (POSIX) */ int fl = fcntl(sock, F_GETFL); fcntl(sock, F_SETFL, fl | O_NONBLOCK);

The last two lines turn the blocking read of §3.2 into the non-blocking read.

3.4Every device is a file

In UNIX, each device appears as a file under /dev. The first letter in the output of ls -l marks a character or block device, and two numbers replace the file size.

  • The major number picks the driver, because the kernel keeps a table of drivers indexed by this number.
  • The minor number tells that driver which of its devices this device is.

Chapter 4

Drivers and controllers

The driver is software that knows one kind of device. The controller is the hardware that the driver talks to.

4.1Device drivers

An I/O device has two high-level parts, namely mechanical components and electronic components. The electronic components form the device controller, which operates the mechanics. The OS deals with the controller through a device driver.

A device driver does the four things below.

  • It implements the device system-call interface (open, read, write, …) for that device.
  • It interacts directly with the device controller.
  • It knows the details, such as which commands the device accepts and which bits to set and read in the registers of the controller.
  • It is the device-dependent part of the device manager.
Control flow

An I/O system call traps into the kernel. The trap handler for I/O, namely the device manager, indexes into a table with the arguments of the call. In this way, it finds and runs the correct device driver. In Linux, that table is indexed by the major number of §3.4, and each entry is a struct file_operations.

4.2The device controller interface

The driver sees a controller as a small set of registers.

  • command specifies what to do next.
  • status holds a busy bit, a done bit, and an error code.
  • data 0 … n−1 holds the bytes that go to or come from the device.

The logic of the controller itself turns a command into motor steps, voltages, or light.

How does the CPU actually reach those registers?

There are two ways, and real machines use both. With port-mapped I/O, registers live in a separate I/O address space, which special instructions reach (in and out on x86). With memory-mapped I/O, registers appear at physical addresses, and an ordinary load or store reaches the controller instead of RAM. The page tables of Lecture 14 mark those pages uncacheable. Therefore, every access actually goes to the device. Lecture 18, Chapter 3 examines both in detail.

4.3Three states in two bits

The status register must distinguish three states, namely idle (no app is using the device), working (exactly one app is using it), and finished (the results are ready for that one app). Two bits, BUSY and DONE, are sufficient.

Chapter 5

Polling I/O

The simplest way for a driver to wait for a device is to keep checking the status register until it changes.

5.1A polling read, step by step

  1. The program calls read(device, …), which traps into the kernel and reaches the read driver.
  2. The driver reads the status register to check whether the device is idle.
  3. The driver writes a read command.
  4. The driver reads status again and again until DONE is set.
  5. The driver copies the data register into the buffer of the program and returns.

5.3The problem with polling

The OS spins in a loop twice. First, it waits for the device to become idle. Second, it waits for the device to finish, so that the results can be collected.

This is called busy waiting. Every check is a CPU cycle that could have run an application. For example, a device operation that takes 1 ms costs about three million loop iterations on a 3 GHz CPU.

Key idea

We want to overlap CPU and I/O. In other words, we free the CPU while the device works on a read or write, and the device reports when it is done.

5.4Next time, I/O strategies

Under the blocking, non-blocking, synchronous, and asynchronous calls of Chapter 3, the device manager can move data in the ways below.

Direct I/O with pollingThe device manager busy-waits. This chapter covers this case.
Direct I/O with interruptsThe device raises an interrupt when it finishes. Therefore, the CPU runs something else in the meantime. This is more efficient than busy waiting.
DMA with interruptsThe controller itself copies the data to memory, and it interrupts once at the end.

Lecture 18, Device Strategies, examines these strategies in detail.

Epilogue

Summary and glossary

∎What to take away

  • Devices sit behind controllers on buses. The CPU talks to controllers and never to the mechanics.
  • There are four kinds of exceptions. Traps (system calls) and faults are caused by the running instruction. Interrupts come from devices at a time that the devices choose. Aborts never return. An exception table maps each number to its handler.
  • The device manager gives every device the same interface. Its device-independent layer sits on top of per-device drivers.
  • Devices are block or character devices, with sequential or random access. Calls on them are blocking, non-blocking, or asynchronous. ioctl and fcntl cover everything else.
  • Each device is a file in /dev. Its major number picks the driver, and its minor number picks the device within that driver.
  • A driver operates a controller through command, status, and data registers. Polling the status register works. However, it wastes the CPU on busy waiting.

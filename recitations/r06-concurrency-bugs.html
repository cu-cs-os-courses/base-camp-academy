Part 1 · follow along

v1: a flag and a spin data race

/* hand1.c */#include <pthread.h>#include <stdio.h>#include <unistd.h> int data, ready; void *consumer(void *arg) { (void)arg; while (!ready) ; /* spin until main says go */ printf("got %d\n", data); return NULL;} int main(void) { pthread_t t; pthread_create(&t, NULL, consumer, NULL); sleep(1); /* let the consumer start spinning */ data = 42; ready = 1; pthread_join(t, NULL); return 0;}
gcc -Wall -Werror -O0 -pthread -o hand1 hand1.c && ./hand1 # got 42 ... by luckgcc -Wall -Werror -O2 -pthread -o hand1 hand1.c && ./hand1 # hangs: Ctrl-Cgcc -g -O1 -fsanitize=thread -pthread -o hand1 hand1.c && ./hand1
  • At -O2 it hangs: the compiler read ready once and loops forever. It is allowed to, because a data race is undefined behavior: the compiler may assume no other thread changes ready behind its back.
  • ThreadSanitizer (-fsanitize=thread) watches the program as it runs and prints WARNING: ThreadSanitizer: data race. The report shows the two conflicting accesses, a write in main and a read in consumer, with the file and line of each.
If TSan refuses to start

It works in the course VM. On some other Linux machines you may see FATAL: ThreadSanitizer: unexpected memory mapping; then run the program as setarch -R ./hand1. That turns off address randomization for that one run, which TSan needs on some kernels.

Part 2 · follow along

v2: a condition variable, no predicate hangs

/* hand2.c */#include <pthread.h>#include <stdio.h>#include <unistd.h> pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;pthread_cond_t c = PTHREAD_COND_INITIALIZER;int data; void *consumer(void *arg) { (void)arg; sleep(1); /* make the bad timing certain */ pthread_mutex_lock(&m); pthread_cond_wait(&c, &m); /* wait for main's signal */ printf("got %d\n", data); pthread_mutex_unlock(&m); return NULL;} int main(void) { pthread_t t; pthread_create(&t, NULL, consumer, NULL); pthread_mutex_lock(&m); data = 42; pthread_cond_signal(&c); pthread_mutex_unlock(&m); pthread_join(t, NULL); return 0;}
Why does it hang? Think first.

main signals while the consumer is still sleeping. Nobody is waiting, so the signal does nothing. A condition variable has no memory. The consumer then waits for a signal that already came and went. The sleep only makes this interleaving certain; without it, the program would hang only some of the time, which is worse.

Part 3 · follow along

v3: the predicate, in a while loop correct

Keep the sleep(1), and change v2 in three places:

int data, ready = 0; /* the state lives in shared memory */ /* consumer */ pthread_mutex_lock(&m); while (!ready) /* check before sleeping, re-check after */ pthread_cond_wait(&c, &m); printf("got %d\n", data); pthread_mutex_unlock(&m); /* main */ pthread_mutex_lock(&m); data = 42; ready = 1; pthread_cond_signal(&c); pthread_mutex_unlock(&m);
  • The state records that the event happened, so an early signal no longer matters: the consumer finds ready == 1 and never sleeps. ThreadSanitizer reports nothing.
  • pthread_cond_wait releases the mutex and sleeps in one atomic step, then re-acquires the mutex before returning. That closes the gap between checking and sleeping (Lecture 10, §3.1).
  • It is while, not if. POSIX allows spurious wakeups, and with several waiters another thread can change the state between the signal and the moment you run (Lecture 10, §1.3).

Cheat sheet

-fsanitize=thread -g -O1Build with ThreadSanitizer: reports data races with both stack traces.
setarch -R ./progRun with address randomization off, if TSan says "unexpected memory mapping".
-fsanitize=address -gAddressSanitizer (R01): overflows and use-after-free. Use one sanitizer at a time.
data raceTwo threads access the same memory, at least one writes, nothing orders them. Undefined behavior in C.
lost wakeupA signal sent when nobody waits does nothing; the later wait sleeps forever.
the wait patternlock; while (!cond) pthread_cond_wait(&c, &m); … unlock
the signal patternlock; change the state; pthread_cond_signal(&c); unlock

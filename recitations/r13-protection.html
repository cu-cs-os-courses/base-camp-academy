Who may do what?

Lecture 22 described protection as domains, objects and an access matrix. Today you watch the kernel enforce it. A second user is refused a file until the permission bits change. Then a program switches domains with the setuid bit, which is how passwd edits a file ordinary users cannot even read. You end with the rule that follows: least privilege.

Part 1 · follow along

Users, bits, and the check on every open

id # uid=0(root)useradd -m alice # a second user, in your own VMecho "for root only" > /tmp/secret.txtchmod 600 /tmp/secret.txtsu alice -c 'cat /tmp/secret.txt' # cat: /tmp/secret.txt: Permission deniedchmod 644 /tmp/secret.txtsu alice -c 'cat /tmp/secret.txt' # for root only
  • The nine bits are three triples, owner / group / other, each rwx. In octal: 6 = rw-, 4 = r--, 0 = ---.
  • ls -l shows one column of the access matrix, the file's access list in compact form, for three domains.
  • The check happens in the kernel, inside open, every time. cat only reports the error it got back.
ownergroupother
600rw-------
644rw-r--r--
640rw-r-----
755rwxr-xr-x
Part 2 · follow along

setuid: running in someone else's domain

ls -l /etc/passwd /etc/shadow /usr/bin/passwd
-rw-r--r-- 1 root root 997 … /etc/passwd-rw-r----- 1 root shadow 623 … /etc/shadow-rwsr-xr-x 1 root root 68248 … /usr/bin/passwd

/etc/shadow holds the salted password hashes (Lecture 23), and alice cannot even read it. So how does alice change her own password? Look at the s in /usr/bin/passwd. Now try it with a program of your own:

/* who.c */#include <stdio.h>#include <unistd.h> int main(void) { printf("real uid %d, effective uid %d\n", (int)getuid(), (int)geteuid()); FILE *f = fopen("/etc/shadow", "r"); printf("open /etc/shadow: %s\n", f ? "allowed" : "Permission denied"); if (f) fclose(f); return 0;}

Save it in a directory on your laptop and boot with it shared, e.g. SHARE=$HOME/r13 env/run.sh, so it appears at /share/who.c.

gcc -Wall -Werror -o /tmp/who /share/who.csu alice -c /tmp/whochmod u+s /tmp/whosu alice -c /tmp/who
What you should see, and why
real uid 1000, effective uid 1000open /etc/shadow: Permission denied# after chmod u+s: -rwsr-xr-x 1 root root … /tmp/whoreal uid 1000, effective uid 0open /etc/shadow: allowed

The real uid says who started the program; the effective uid is what the kernel checks. A setuid program runs with its owner's effective uid: a switch of protection domain. That is how passwd works. A small, carefully written program may edit /etc/shadow on alice's behalf, while alice herself never can.

Part 3 · follow along

Why setuid programs must be few and small

find / -xdev -perm -4000 -type f 2>/dev/null # every setuid program on the diskrm -f /tmp/who /tmp/secret.txt # clean upuserdel -r alice

The course VM has /tmp/who plus nine system programs: passwd, su, chsh, chfn, gpasswd, newgrp, mount, umount and ssh-keysign. Each runs with root's power no matter who starts it, so a bug in any of them is a bug with root's power.

Hence least privilege (Lecture 22): keep setuid programs few, small and audited, and have them drop privilege as early as possible. Prefer narrower rights, such as a dedicated group like shadow or Linux capabilities, over full root. Administrators run exactly this find to audit a machine.

Clean up

Run the last two lines. /etc/passwd and alice's home directory persist in your VM image. userdel may warn that alice had no mail spool; that is harmless.

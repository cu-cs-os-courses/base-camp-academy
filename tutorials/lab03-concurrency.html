Watch a race, then build the cure

This page walks you through Lab03 step by step. In this lab, you first make a race visible. Four threads increment one shared counter, and some of the increments vanish. Then you build the standard cure, a bounded buffer that many threads can share safely, from one mutex and two condition variables. This page and the header comment of each file in labs/03-concurrency/submit/ are the specification for this lab.

Step 1

race.c, making the race happen

The goal of this step is to see a raceA data race is two threads accessing the same memory location without synchronization, where at least one access is a write. A race condition is incorrect behavior caused by the order in which the threads run. lose updates, and then to prevent it with a lock. Four threads (NTHREADS) each increment one shared counter 200,000 times (NITER). race racy increments the counter bare, and it must print a different wrong COUNT= on each run. race locked increments it under the mutex, and it must print COUNT=800000 every time.

  1. On your laptop, read the header of race.c, and fill in the TODO in worker.

    The worker repeats NITER times. If use_lock is set, it increments the counter while it holds the mutexA mutex is a lock. pthread_mutex_lock takes it, and it sleeps if another thread holds it. pthread_mutex_unlock gives it back. Therefore, at most one thread at a time runs the code between the two calls. lock, which race.c already declares. Otherwise it increments the counter bare. The increment is then the critical sectionThe part of a program that accesses a shared resource is its critical section. Mutual exclusion means that at most one thread is in its critical section at a time.. Lecture 09 §3.1 shows the two calls.

  2. Fill in the TODO in main.

    Start NTHREADS workers, and then wait for all of them, before the printf that is already there. pthread_create(3) starts a thread, and pthread_join(3) waits for one, as Lecture 05 §2.1 showed.

  3. In the VM, recompile with the gcc command of Step 0, and run the racy mode three times.

    for i in 1 2 3; do /tmp/race racy; done

    The for loop runs the program three times. You get three different counts, all below 800000. In our runs in the VM, usually 9% to 16% of the increments vanished. Once in a while, one run prints exactly 800000. Write the three counts down, because report question 1 asks for them.

  4. Run the locked mode.

    /tmp/race locked

    It prints COUNT=800000, every time you run it.

  5. Time both modes.

    time /tmp/race racytime /tmp/race locked

    time is a bash keyword. It runs the command, and then it prints three lines. Look at real, the wall-clock time. The locked run takes roughly ten times as long as the racy run. The lock makes the count correct, but it is not free.

What the symptom tells you

racy prints exactly 800000 every time. Lecture 05 §3.3 says the compiler may assume a data race never happens, so at -O2 gcc may turn a loop whose only work is counter++ into one addition. Follow the header's shape, one loop that decides on every iteration whether to lock. COUNT=0 or a tiny number. main printed before the workers finished. Check that every thread is joined. locked is not 800000. Something touches the counter outside the lock.

Rule

racy mode must actually race. Therefore, "fixing" the demonstration with atomic operations does not pass it. A check fails if _Atomic, stdatomic, __atomic or atomic_fetch appears in race.c outside // comments.

Step 2

Threads in /proc

The goal of this step is to see the four workers the way the kernel sees them, and to find out what they have in common. There is no code in this step. Write down what you see, because report question 2 needs it.

  1. In the VM, start a locked run in the background, and freeze it a moment later.

    /tmp/race locked & sleep 0.01; kill -STOP $!

    A locked run lasts only about a tenth of a second, which is too short to look at by hand. Therefore, you stop it. The & starts the program in the background, and the shell prints its job number, [1], and its PID. The shell keeps that PID in $!. sleep 0.01 gives main 10 ms to create its workers. kill -STOP then sends the signal SIGSTOP, whose default action is stop and which cannot be caught (Lecture 04 §1.2). The process stays frozen while you look at it. The shell reports the job as Stopped after your next command, as in Fig. 2.1.

  2. List the tasks of the process, and read its thread count.

    ls /proc/$!/taskgrep Threads /proc/$!/status

    Linux keeps one taskOn Linux, every thread is its own task_struct (Lecture 05 §0.1). /proc/<pid>/task/ has one entry per thread. for every thread. Count the entries, and read the Threads line, as in Recitation 02 Part 1. If Threads shows fewer than 5, some workers were not created yet or had already finished. In that case, end the job as in item 4, and try item 1 again.

  3. Go into the task directory, and compare the open files of two tasks.

    cd /proc/$!/taskls -l <tid1>/fdls -l <tid2>/fd

    Use two of the numbers that ls printed. Each task directory holds the same files as a process directory. Its fd directory lists the open file descriptors, as links to what they refer to, as in Recitation 02 Part 1. Write down whether the two lists are the same.

  4. Leave the directory, and end the frozen run.

    cd /sharekill -KILL %1jobs

    %1 names job 1, so you do not need to type the PID. SIGKILL ends the frozen run (Lecture 04 §1.2). It prints no COUNT, which is fine. The shell may print the Stopped line once more. jobs lists your background jobs, and it reports job 1 as Killed.

Step 3

Design the array struct

The goal of this step is to design the array type in array.h, namely to decide what the struct must hold so that the four functions of Part 2 can work. Decide the design on paper before you write any C.

Part 2 is a bounded bufferA bounded buffer has a fixed number of slots. A producer puts items into it, and a consumer takes them out. The producer waits when the buffer is full, and the consumer waits when it is empty. of char * values, called array. Any number of threads may call array_put and array_get at the same time.

  1. On your laptop, read the header of array.h.

    It gives the four prototypes, and the harness calls them exactly as declared there. It also lists what the struct needs. That is storage for ARRAY_SIZE char * values, bookkeeping, one mutex, and two condition variablesA condition variable lets a thread wait until a condition is true. Its wait operation blocks the caller and releases the lock, so that others can enter. Its signal operation resumes one waiting thread, and it has no effect if no thread waits.. The storage and the synchronization are fixed by the header. The bookkeeping is your design.

  2. Read the worked example below, a stack of ints that is not thread-safe.

    /* stack.h, the interface and the struct behind it */#pragma once#define STACK_SIZE 10 typedef struct { int array[STACK_SIZE]; int top;} stack; int stack_init(stack *s);int stack_push(stack *s, int element);int stack_pop (stack *s, int *element);void stack_free(stack *s);

    A header file is the interface, and it says what the functions do. The C file is the implementation, and it says how. In this stack, stack_push returns -1 when the stack is full, and stack_pop returns -1 when it is empty. Otherwise, each returns 0. Your array copies three conventions from it. First, the header starts with #pragma once. Second, every function that can fail returns an int status, and 0 means success. Third, an output comes back through a pointer parameter, as in stack_pop's int *element and array_get's char **hostname.

    However, your array differs from the stack in three ways. First, it stores char * values. Second, it is safe under any number of threads. Third, where the stack fails when it is full or empty, your array blocksA thread blocks when it gives up the CPU and sleeps until an event occurs. The scheduler runs someone else in the meantime. A thread that instead loops and checks again and again is busy waiting, and it burns CPU the whole time., namely it waits until the call can succeed.

  3. Choose the bookkeeping. It must answer the three questions below at any moment.

    • Where does the next put store its pointer?
    • Where does the next get take its pointer from?
    • How many items are held right now, so that you can tell "full" from "empty"?

  4. Test your design by hand.

    Draw 8 slots, and simulate put ×8, get ×3, put ×3, get ×8. Every value of your bookkeeping must stay inside the array. The three puts in the third batch have to reuse slots that the gets freed.

  5. Write the struct in array.h.

    Replace the placeholder field todo_delete_me with your storage, your bookkeeping, the mutex, and the two condition variables. The two condition variables mean two different things, namely "there is now space" and "there is now an item". Give them names that say which is which.

What the checks require of the design

Each item put must come out exactly once. The checks do not test the order in which items come out. The array stores the pointers it is given, and it never copies the strings.

Step 4

array.c and its four functions

The goal of this step is to write the four functions in array.c, so that array_put blocks while the array is full and array_get blocks while it is empty. Both wait on a condition variable, and both return 0 on success. Together with the struct, they form a monitorA monitor keeps shared variables together with the functions that use them, and only one thread at a time is active inside it. In C, you build one yourself. Every function holds one mutex while it touches the shared variables..

  1. Read the lecture's rules first.

    Lecture 10 §3.2 lists the three rules, and its table says what pthread_cond_wait does with the mutex and whom pthread_cond_signal wakes. The table below gives what each function must do.

functionwhat it must doread first
array_initSet the bookkeeping to "empty", and initialize the mutex and both condition variables. Return 0.Lecture 09 §3.1 for the mutex, Lecture 10 §3.2 for the condition variables
array_putWait while the array is full, store the pointer, update the bookkeeping, and let a waiting getter know. Return 0.Lecture 09 §3.1 for the mutex, Lecture 10 §3.2 for the wait and the signal
array_getThe mirror image. Wait while the array is empty, take a pointer out through *hostname, update the bookkeeping, and let a waiting putter know. Return 0.the same two sections
array_freeRelease what array_init created.Lecture 09 §3.1 for the mutex, Lecture 10 §3.2 for the condition variables

  1. Before you write array_put, answer the six questions below on paper. array_get has the same questions.

    1. Which lines read or change the shared bookkeeping? The mutex must be held for all of them.
    2. What exactly is the condition for "I must wait"? On which of your two condition variables do you wait for it?
    3. What does pthread_cond_wait do with the mutex while the thread sleeps, and in what state is the mutex when it returns?
    4. When the wait returns, is your condition guaranteed to be true? Think of two getters and one put. Lecture 10 §1.3 lets you step through this exact scenario, with if and with while.
    5. After you change the state, which thread could now be able to continue, and on which condition variable is it waiting?
    6. Is there a path out of the function that leaves the mutex locked?

  2. Write array_init and array_free, then array_put, then array_get.

    Delete each (void) line and each return -1 of the starter as you fill in the function. Then go to Step 5, which compiles and tests your code.

Blocking, not polling

Blocking means a wait on a condition variable. A loop that unlocks, locks again, and rechecks the state is busy waiting, even though it uses the mutex. A waiting thread must burn almost no CPU, and the no-busy-wait check in Step 5 measures exactly that.

Step 5

Test one guarantee at a time

The goal of this step is to test each promise of your array on its own, with the instructor harness check/array-test.c. The harness is not secret, so read it. Each scenario tests one guarantee. Run them in order, and fix the first one that fails.

  1. In the VM, in /share, compile the harness together with your array.c.

    gcc -Wall -Werror -O2 -pthread -Isubmit -o /tmp/array-test \ check/array-test.c submit/array.c

    -Isubmit adds submit/ to the directories that gcc searches for header files. Therefore, the line #include "array.h" in the harness finds your header. If you run the harness with the starter files, every scenario prints FAIL init, because the starter's array_init returns -1.

  2. Run roundtrip.

    /tmp/array-test roundtripOK roundtrip

    One thread puts three strings, gets three back, and checks that each one came out exactly once.

  3. Run blocks-empty.

    /tmp/array-test blocks-emptyCPU_MS=0OK blocks-empty

    A second thread calls array_get on the empty array. The harness sleeps for one second, and checks that the get has not returned. Then it puts one item, and checks that the waiting get returns that item. CPU_MS is the CPU time, in milliseconds, that the kernel charged to the whole program during that second, the CPU used in its accounting information (Lecture 03 §3.2). A thread that sleeps uses almost none. The check no-busy-wait requires a value below 500.

  4. Run blocks-full.

    /tmp/array-test blocks-fullOK blocks-full

    The harness fills all 8 slots. A second thread then makes a 9th put, which must wait. After one second, the harness gets one item, and the waiting put must then return.

  5. Run stress, first once and then 20 times.

    /tmp/array-test stressOK stressfor i in $(seq 20); do /tmp/array-test stress; done | sort | uniq -c 20 OK stress

    stress runs 2 producers and 2 consumers at once. Each producer puts 500 items (PER in the harness), and every item must come out exactly once. A bug in a concurrent program may show up in one run and hide in the next. Therefore, you run it 20 times. seq 20 prints the numbers 1 to 20. sort puts identical lines next to each other, and uniq -c prints each distinct line once, with its count. A single line 20 OK stress means that all 20 runs passed.

  6. Build the harness with ThreadSanitizer, and run stress again.

    gcc -g -O1 -fsanitize=thread -pthread -Isubmit -o /tmp/array-tsan \ check/array-test.c submit/array.c/tmp/array-tsan stressOK stress

    -fsanitize=thread builds the program with ThreadSanitizer, which Recitation 06 introduces. It watches every memory access while the program runs. When two threads touch the same location without synchronization, it prints WARNING: ThreadSanitizer: data race, with the file and line of both accesses. -g puts those line numbers into the binary. A correct array prints only OK stress.

Step 7

The report

The goal of this step is to answer the three questions that submit/report.md already holds. Each one asks you to argue from your own numbers and observations. Each item below tells you how to investigate, not what the answer is.

  1. Question 1. "Your three racy COUNTs (paste them). Why do they differ from run to run? Name the three machine steps hiding inside counter++ and show, with a two-thread interleaving, exactly where an increment gets lost."

    Paste the counts from Step 1, item 3. For the machine steps, use Lecture 08 §2.2 and Recitation 05 Part 3, which take counter++ apart into load, add, and store. Then draw a timeline with one column per thread, which ends with one increment lost. The widget in Lecture 08 §2.2 lets you try such interleavings.

  2. Question 2. "What did ls /proc/<pid>/task/ and Threads: show while race ran? In Lab01 terms, what do the four workers share that four processes would not, and what does each still own privately?"

    Use your notes from Step 2. The fd lists show what the tasks share. For memory and for what each thread owns, use Lecture 05 §0.1 and its Fig. 0.1. Then compare with Lab01, where after fork the parent could not see the child's change to a variable.

  3. Question 3. "Why must array_put/array_get wait on a condition variable instead of looping until the state changes? One of the checks measured the CPU time your program used while its thread waited. Connect that number to your answer. And why does pthread_cond_wait sit inside a while, not an if?"

    Quote your CPU_MS from Step 5, item 3, and compare it with the one second that the thread waited. Lecture 08 §3.4 and §4.4 explain what a busy-waiting thread costs. If you want a measured comparison, write a throwaway polling version outside submit/, and run blocks-empty on it. For while against if, use your answer to Step 4 question 4, and the scenario in Lecture 10 §1.3.

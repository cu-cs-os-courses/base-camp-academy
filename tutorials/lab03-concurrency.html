Watch a race, then build the cure

Part 1 makes a race visible: four threads, one counter, updates that vanish. Part 2 builds the standard cure, a bounded buffer guarded by a mutex and two condition variables. This page says what each function must guarantee, which questions to answer before writing it, and how to test each guarantee on its own with the instructor harness. It never shows code for the lab files. The README and the file headers are the specification; L08–L10 are the lectures behind it.

Step 0

Set up the loop

Every compile in this lab needs -pthread. Without it you get link errors about pthread_create.

Step 1

race.c: make the race happen

Goal: race racy loses increments and prints a different wrong COUNT= each run; race locked prints COUNT=800000 every time.

TODOwhat it must doread first
workerRepeat NITER times: increment the counter, holding the mutex if use_lock is set, bare otherwise.man 3 pthread_mutex_lock
mainStart NTHREADS workers, then wait for all of them before the print that is already there.man 3 pthread_create, man 3 pthread_join

How to check it yourself: run the README's experiment and write the numbers down; the report asks for them.

for i in 1 2 3; do /tmp/race racy; done # three different numbers, all below 800000/tmp/race locked # COUNT=800000time /tmp/race racy; time /tmp/race locked
What the symptom tells you

racy prints exactly 800000 every time: the compiler turned your bare loop into a single addition, so there is nothing left to race. This happens at -O2 when the bare increments sit in a loop of their own. The TODO describes one loop whose body makes the lock decision on every iteration; follow that shape. (You can see which you got with objdump -d /tmp/race | less: search for your worker function.) COUNT=0 or a tiny number: main printed before the workers finished; check that every thread is joined. locked is not 800000: something touches the counter outside the lock.

Rule

No atomics. A check fails if _Atomic, stdatomic, __atomic or atomic_fetch appears outside // comments. racy is supposed to be broken; that is the demonstration.

Step 2

Threads in /proc

No code. Look at a running race with Lab01 eyes and write down what you see for report question 2.

/tmp/race locked & ls /proc/$!/task/ # locked runs longer, so it is easier to catchgrep Threads: /proc/$!/status
  • Count the entries in task/. How many threads is that, and which one is main?
  • Pick two entries and compare a few files inside them, for example status and maps. What is the same, and what differs?
  • If the run ends before you can look, run it in a loop or run it three times in a row.
Step 3

Design the array struct

Goal: the array type in array.h holds everything the four functions need. Decide the design on paper before you write any C.

The header lists what the struct needs: storage for ARRAY_SIZE char * values, bookkeeping, one mutex, and two condition variables. The storage and the synchronization are fixed by the spec. The bookkeeping is your design, and it must answer three questions at any moment:

  1. Where does the next put store its pointer?
  2. Where does the next get take its pointer from?
  3. How many items are held right now, so that you can tell "full" from "empty"?

Test your design by hand: draw 8 slots and simulate put ×8, get ×3, put ×3, get ×8. Every value of your bookkeeping must stay inside the array, and the third batch (the 3 puts) has to reuse slots that the gets freed.

What the checks require of the design

Each item put must come out exactly once. The checks do not test the order in which items come out. The array stores the pointers it is given and never copies the strings. The two condition variables mean two different things: "there is now space" and "there is now an item". Give them names that say which is which.

Step 4

array.c: four functions

Goal: put blocks while the array is full and get blocks while it is empty. Both wait on a condition variable, and both return 0 on success. This is the bounded buffer from L10, written as a monitor.

functionwhat it must doread first
array_initSet the bookkeeping to "empty", and initialize the mutex and both condition variables. Return 0.man 3 pthread_mutex_init, man 3 pthread_cond_init
array_putWait while full, store the pointer, update the bookkeeping, let a waiting getter know. Return 0.L10's bounded buffer; man 3 pthread_cond_wait, pthread_cond_signal
array_getThe mirror image: wait while empty, take a pointer out through *hostname, update, let a waiting putter know. Return 0.the same
array_freeRelease what init created.pthread_mutex_destroy, pthread_cond_destroy

Before writing put, answer these on paper. get has the same questions.

  1. Which lines read or change the shared bookkeeping? The mutex must be held for all of them.
  2. What exactly is the condition for "I must wait"? On which of your two condition variables do you wait for it?
  3. What does pthread_cond_wait do with the mutex while you sleep, and in what state is the mutex when it returns? (Read its manual page.)
  4. When wait returns, is your condition guaranteed to be true? Think of two getters and one put. This is why the README says while, not if.
  5. After you change the state, which thread could now be able to continue, and which condition variable is it waiting on?
  6. Is there a path out of the function that leaves the mutex locked?
Step 5

The instructor harness check/array-test.c is not secret: read it. Each scenario tests one guarantee, so run them in order and fix the first one that fails.

Step 7

Report and submit

Four questions in submit/report.md. How to investigate, not the answers:

  1. Inside counter++. Paste your three racy counts. To see the machine steps, compile a small file that contains only a function incrementing a global, with gcc -O1 -S, and read the .s file. Then draw a two-thread timeline, one column per thread, that ends with one increment lost.
  2. Threads in /proc. Use your Step 2 notes. Compare with Lab01: after fork, what did parent and child not share?
  3. The price of the lock. Use your time numbers. Count how many lock and unlock calls the locked run makes in total, and think about what each one costs when four threads want the same lock.
  4. Blocking beats polling. Quote your CPU_MS. If you want a comparison, write a throwaway polling version outside submit/ and measure it with the same harness. For while vs if, use your answer to Step 4 question 4.

Stretch, ungraded

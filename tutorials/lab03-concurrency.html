Watch a race, then build the cure

Part 1 makes a race visible, with four threads, one counter, and updates that vanish. Part 2 builds the standard cure, a bounded buffer guarded by a mutex and two condition variables. This page says what each function must guarantee, which questions to answer before writing it, and how to test each guarantee on its own with the instructor harness. It never shows code for the lab files. This page and the file headers in submit/ are the specification, and L08–L10 are the lectures behind it.

Step 1

race.c, making the race happen

The goal of this step is that race racy loses increments and prints a different wrong COUNT= each run, while race locked prints COUNT=800000 every time.

counter++ looks atomic. However, it is several machine steps, and another thread can run between any two of them. Report question 1 asks you to name the steps.

You edit submit/race.c. Four threads (NTHREADS) each increment one shared counter 200,000 times (NITER). ./race racy increments bare, and ./race locked increments under the mutex. The output is exactly one line, COUNT=<n>.

TODOwhat it must doread first
workerRepeat NITER times to increment the counter, holding the mutex if use_lock is set and bare otherwise.man 3 pthread_mutex_lock
mainStart NTHREADS workers, then wait for all of them before the print that is already there.man 3 pthread_create, man 3 pthread_join

How to check it yourself. Run this experiment and write the numbers down, because the report asks for them.

for i in 1 2 3; do /tmp/race racy; done # three different numbers, all below 800000/tmp/race locked # COUNT=800000time /tmp/race racy; time /tmp/race locked

Three racy runs give three different wrong answers. On our reference VM, 10–12% of the increments vanish. The locked run gives exactly 800000 every time, and costs about 10× the wall time. Both facts go in your report.

What the symptom tells you

racy prints exactly 800000 every time. The compiler turned your bare loop into a single addition, so there is nothing left to race. This happens at -O2 when the bare increments sit in a loop of their own. The TODO describes one loop whose body makes the lock decision on every iteration, so follow that shape. (You can see which you got with objdump -d /tmp/race | less by searching for your worker function.) COUNT=0 or a tiny number. Here main printed before the workers finished, so check that every thread is joined. locked is not 800000. Something touches the counter outside the lock.

Rule

racy mode must actually race, and "fixing" the demo with atomics is not passing it. A check fails if _Atomic, stdatomic, __atomic or atomic_fetch appears outside // comments. racy is supposed to be broken. That is the demonstration.

Step 3

Design the array struct

The goal of this step is that the array type in array.h holds everything the four functions need. Decide the design on paper before you write any C.

Interface and implementation. An interface says what, and an implementation says how. The header/C file split keeps them apart. Here array.h is the interface and the struct behind it, and array.c is the implementation. Here is a worked example of the shape, namely the interface of a stack of ints that is not thread-safe.

/* stack.h — the interface, and the struct behind it */#pragma once#define STACK_SIZE 10 typedef struct { int array[STACK_SIZE]; int top;} stack; int stack_init(stack *s);int stack_push(stack *s, int element);int stack_pop (stack *s, int *element);void stack_free(stack *s);

In this stack, stack_push returns -1 when the stack is full, and stack_pop returns -1 when it is empty. Otherwise each returns 0. Copy three conventions from it. First, #pragma once. Second, every fallible function returns an int status (0 = success). Third, outputs come back through pointer parameters, as in stack_pop's int *element and array_get's char **hostname.

Your array has the same shape, with three upgrades. First, it stores char * payloads. Second, it is safe under any number of threads. Third, where the stack fails when full or empty, your array blocks. The four prototypes are in submit/array.h, and the harness calls them exactly as declared there.

The header lists what the struct needs, namely storage for ARRAY_SIZE char * values, bookkeeping, one mutex, and two condition variables. The storage and the synchronization are fixed by the spec. The bookkeeping is your design, and it must answer the three questions below at any moment.

  1. Where does the next put store its pointer?
  2. Where does the next get take its pointer from?
  3. How many items are held right now, so that you can tell "full" from "empty"?

Test your design by hand. Draw 8 slots and simulate put ×8, get ×3, put ×3, get ×8. Every value of your bookkeeping must stay inside the array, and the third batch (the 3 puts) has to reuse slots that the gets freed.

What the checks require of the design

Each item put must come out exactly once. The checks do not test the order in which items come out. The array stores the pointers it is given and never copies the strings. The two condition variables mean two different things, namely "there is now space" and "there is now an item". Give them names that say which is which.

Step 4

array.c and its four functions

The goal of this step is that put blocks while the array is full and get blocks while it is empty. Both wait on a condition variable, and both return 0 on success. This is the bounded buffer from L10, written as a monitor. Blocking means a condition-variable wait, not a retry loop. A waiting thread must burn almost no CPU, and the no-busy-wait check measures exactly that.

functionwhat it must doread first
array_initSet the bookkeeping to "empty", and initialize the mutex and both condition variables. Return 0.man 3 pthread_mutex_init, man 3 pthread_cond_init
array_putWait while full, store the pointer, update the bookkeeping, let a waiting getter know. Return 0.L10's bounded buffer and man 3 pthread_cond_wait, pthread_cond_signal
array_getThe mirror image. Wait while empty, take a pointer out through *hostname, update, let a waiting putter know. Return 0.the same
array_freeRelease what init created.pthread_mutex_destroy, pthread_cond_destroy

Before writing put, answer these on paper. get has the same questions.

  1. Which lines read or change the shared bookkeeping? The mutex must be held for all of them.
  2. What exactly is the condition for "I must wait"? On which of your two condition variables do you wait for it?
  3. What does pthread_cond_wait do with the mutex while you sleep, and in what state is the mutex when it returns? (Read its manual page.)
  4. When wait returns, is your condition guaranteed to be true? Think of two getters and one put. This is why pthread_cond_wait lives inside a while loop, not an if. It matters the moment there are two consumers.
  5. After you change the state, which thread could now be able to continue, and which condition variable is it waiting on?
  6. Is there a path out of the function that leaves the mutex locked?

Step 7

Report and submit

Four questions in submit/report.md. Below is how to investigate, not the answers.

  1. Inside counter++. Paste your three racy counts. To see the machine steps, compile a small file that contains only a function incrementing a global, with gcc -O1 -S, and read the .s file. Then draw a two-thread timeline, one column per thread, that ends with one increment lost.
  2. Threads in /proc. Use your Step 2 notes. Compare with Lab01. After fork, what did parent and child not share?
  3. The price of the lock. Use your time numbers. Count how many lock and unlock calls the locked run makes in total, and think about what each one costs when four threads want the same lock.
  4. Blocking beats polling. Quote your CPU_MS. If you want a comparison, write a throwaway polling version outside submit/ and measure it with the same harness. For while vs if, use your answer to Step 4 question 4.

Stretch, ungraded

A tiny multi-lookup. The legacy course built a whole threaded DNS resolver on this exact interface, and this is the taste without the network. Write multi-lookup.c. One requester thread reads names from a file and array_puts them. Two resolver threads array_get names, look each up in a local table file (name ip lines, no network), and append name, ip to a results file. Your buffer is reused unchanged. The interesting part is clean shutdown. Resolvers must terminate when the input is exhausted. Where does "no more work is coming" live in your design? Try answering that before you write any code.

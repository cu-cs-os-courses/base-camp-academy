Make load, then measure the scheduler

This page walks you through Lab02 step by step. In this lab, you watch the Linux scheduler share one CPU. You write a spinner that always wants the CPU, and an instrument, fairshare.sh, that measures how the scheduler divides one CPU between two spinners. Then you start a real-time spinner and see that a scheduling policy outranks every weight. This page and the header comment of each file in labs/02-scheduling/submit/ are the specification for this lab.

    Lab02 is released in the course repository, upstream. git pull upstream main copies it into your local repository, and git push copies it on to your private repository on GitHub. A release never touches your submit/ directories, so your earlier work stays as it is.

    In this lab, you edit the three files below.

    SHARE=$PWD/labs/02-scheduling/submit env/run.sh

    Run it from the repository root. The VM now sees labs/02-scheduling/submit at /share.

  3. In the VM, count the CPUs.

    nproc # 2

    The VM has two CPUs, numbered 0 and 1. Every experiment in this lab runs its spinners on CPU 0 only, with taskset -c 0. This is called pinningA process can name the set of CPUs it may run on. This is hard affinity. taskset -c 0 pins a program to CPU 0, so the scheduler never moves it to another CPU.. As a result, two spinners must share CPU 0, and the scheduler has to decide between them. CPU 1 stays free for your shell, so the VM stays responsive while the spinners fight.

Lab02 opens before Lecture 07, which explains how Linux shares the CPU. Therefore, a new idea is underlined with a dashed line where you first need it. Click it for a short explanation and a link to the lecture section.

The one rule

A spinner never stops on its own. Before every new experiment, make sure that no spinner is left over from the last one. In your shell, jobs lists the background programs you started, and it must print nothing. A leftover spinner on CPU 0 takes part of the CPU and silently changes every number you measure.

Step 1

spin.c, burning one CPU

The goal of this step is to make load, namely a process that always wants the CPU. spin.c runs in user space forever and never sleeps. Every later experiment uses it to force the scheduler to make decisions.

  1. On your laptop, read the header of spin.c, and write the loop.

    The program is a loop and nothing else. Watch out for the optimizer. A loop that never ends stays in the program. However, at -O2, the compiler may delete a loop that ends and has no visible effect, such as a loop that only counts to a large number. The program then exits at once. The hint in the header names the keyword that makes every access to a variable count as visible.

  2. In the VM, compile spin.c, and start it on CPU 0 in the background.

    cd /sharegcc -Wall -Werror -O2 -o /tmp/spin spin.ctaskset -c 0 /tmp/spin &[1] 187

    The shell prints the job number, [1], and the PID. taskset sets the CPU and then execs /tmp/spin, so the PID belongs to the spinner itself. The shell keeps that PID in $!.

  3. Read the spinner's state and user time, wait 5 seconds, and read them again.

    awk '{print $3, $14}' /proc/$!/statR 101sleep 5awk '{print $3, $14}' /proc/$!/statR 596

    Field 3 of the stat file is the state, and field 14 is the user time, utime. The state is R, because the spinner never waits for anything. utime counts user-mode CPU time in hundredths of a second. Therefore, a spinner that owns a CPU for 5 seconds gains about 500. fairshare.sh in Step 3 makes exactly this measurement. proc_pid_stat(5) lists every field.

  4. Stop the spinner, and check that nothing is left.

    kill %1jobs # prints nothing once it is gone

    %1 names job 1, so you do not need to type the PID.

What the symptom tells you

The growth is near 0. The loop is not running. Either the optimizer deleted it and the program exited, or the program sleeps. /proc/…/stat does not exist. The program has already exited, which is the same problem. make check demands a growth of at least 300, that is 3 s of CPU, in 5 s, and state R.

Step 2

Two spinners on one CPU, watching preemption

The goal of this step is to watch the scheduler share one CPU between two processes, and to see the numbers it keeps to do so. There is no code in this step. Write down every value, because the report needs them.

  1. In the VM, start two spinners on CPU 0.

    taskset -c 0 /tmp/spin &taskset -c 0 /tmp/spin &jobs -l

    jobs -l lists both jobs with their PIDs. Use these PIDs in the items below.

  2. Read the state of each spinner.

    awk '{print $3}' /proc/<pid>/stat

    Both show R, although only one of them can run on CPU 0 at a time. State RLinux shows a process state as a letter. As the R03 cheat sheet says, R means running or ready, namely waiting only for a CPU. A process that waits for an event, such as a timer, is in state S. covers both.

  3. Read how often each spinner was forced off the CPU. Read it again a few seconds later.

    grep nr_involuntary /proc/<pid>/sched

    A spinner never gives up the CPU by itself. Therefore, every switch away from it is involuntary, and the count keeps growing while both spinners run. This is preemptionA preemptive scheduler may take the CPU away from a running process and give it to another ready process. Linux is preemptive.. Two processes share one CPU, and neither starves.

  4. Read the virtual run time of both spinners. Read both again a few seconds later.

    grep se.vruntime /proc/<pid>/sched

    The vruntimeThe scheduler keeps a virtual run time, vruntime, for every task. It grows while the task runs, and it grows more slowly for a heavier task. CFS always runs the task with the smallest vruntime. is in milliseconds. Compare how the two values move relative to each other.

  5. Stop both spinners.

    kill %1 %2jobs # empty

  6. Start a nice 0 spinner and a nice 10 spinner on CPU 0.

    taskset -c 0 /tmp/spin &taskset -c 0 nice -n 10 /tmp/spin &jobs -l

    nice -n 10 sets the nice valueA normal task's priority comes from its nice value, from −20 to +19. A lower value means a higher priority. A process at nice +10 is "nicer" to the others, so it gets less of the CPU. to 10 and then execs the spinner, as taskset does. The first spinner keeps the default, nice 0. The scheduler turns each nice value into a weightEach nice value maps to a weight. Nice 0 is 1024, and each nice step changes the weight by a factor of about 1.25. Over time, each task gets the CPU in proportion to its weight divided by the sum of all weights..

  7. Read the vruntime and the utime of both spinners, wait 10 seconds, and read them again.

    grep se.vruntime /proc/<A>/sched /proc/<B>/schedawk '{print $14}' /proc/<A>/stat /proc/<B>/statsleep 10grep se.vruntime /proc/<A>/sched /proc/<B>/schedawk '{print $14}' /proc/<A>/stat /proc/<B>/stat

    Here <A> is the PID of the nice 0 spinner and <B> the PID of the nice 10 spinner. Given two files, grep puts the file name in front of each line, and awk prints one line per file, A first. Write down how much each of the four values grew, because report question 2 asks you to explain them.

  8. Stop both spinners.

    kill %1 %2jobs # empty

make check repeats the experiment of items 1 to 3. It requires at least 5 involuntary switches in 5 seconds.

Look deeper (ungraded). Watch every switch the scheduler makes.

The kernel can record every context switch it makes, with a timestamp in microseconds. Start two spinners on CPU 0 as in item 1, and run the commands below.

trace-cmd record -e sched_switch -o /tmp/trace.dat -- sleep 1trace-cmd report -i /tmp/trace.dat | grep spin | headspin-169 [000] 5.775576: sched_switch: spin:169 [120] R ==> spin:168 [120]kill %1 %2

Each line is one switch on CPU [000]. The task on the left of ==> leaves the CPU, and the task on the right gets it. The R means the leaving task was still ready to run, so the switch was a preemption. The [120] is the priority, 120 + nice. The -o /tmp/trace.dat keeps the trace file out of /share. Nothing in make check or the report depends on this fold.

Step 3

fairshare.sh, building the instrument

The goal of this step is to build an instrument that measures how the scheduler divides one CPU between two tasks with different nice values. fairshare.sh <niceA> <niceB> <seconds> prints exactly one line, A=<n> B=<n> RATIO=<A/B, two decimals>. The two numbers are each spinner's utime growth during the window.

  1. On your laptop, read the header of fairshare.sh.

    It gives the exact output format and the start command. It also gives the one rule. The script reads only /proc, so the words top and ps must not appear in it outside comments.

  2. Start the two spinners, and keep their PIDs.

    Start spinner A at nice $na and spinner B at nice $nb, both on CPU 0 and both in the background, with the command in the header. As in Step 2, nice sets the nice value and then execs the next program. Therefore, $! is again the spinner's own PID. The checker sets SPIN=/tmp/spin, so start the binary through $SPIN.

  3. Arrange for both spinners to be killed when the script exits, right after you start them.

    The header's hint, trap '…' EXIT, runs a command whenever the script exits, normally or with an error. Then test it. Run the script, let it finish, and check in the VM that no spinner is left.

    bash /share/fairshare.sh 0 0 5ps -C spin # prints only its header line

  4. Wait 2 to 3 seconds, then read field 14 of each spinner's stat file.

    The wait keeps the startup cost out of the measurement. For a test, print the two raw samples, and compare them with a cat of the same stat files.

  5. Sleep $secs, read both again, and compute each growth as "after minus before".

  6. Print the line, with the ratio to two decimals.

    The shell does only integer arithmetic. However, awk computes with fractions, and its printf controls the number of decimals. The header shows how to pass the two growths into awk.

Format details the check enforces

A and B are whole numbers, and RATIO has exactly two digits after the point, so 9.30 is right and 9.3 is wrong. The checker reads only the last line of the output.

Step 4

Predict, measure, and decide whether to trust it

The goal of this step is to check your instrument against cases whose answer you know, before you trust it with one you do not know.

Nice is not a polite suggestion. It selects a weight from the table in L07 §3.4, and the scheduler divides the CPU in proportion to the weights. The weight for nice 0 is 1024, and for nice 10 it is 110. Each nice step is a factor of about 1.25.

  1. Predict the ratio for two equal nice values. Then measure it.

    bash /share/fairshare.sh 0 0 10A=498 B=498 RATIO=1.00

    Equal weights give equal shares, so RATIO is near 1. Each spinner's utime grows by about 50 per second, half of CPU 0.

  2. Predict the ratio for nice 0 against nice 10. Then measure it.

    bash /share/fairshare.sh 0 10 15

    The prediction is the ratio of the two weights, 1024 / 110 ≈ 9.3. Write your measured ratio down, because report question 1 asks for it.

  3. Predict the ratio for nice 0 against nice 5, and for nice 10 against nice 15. Then measure both.

    bash /share/fairshare.sh 0 5 15bash /share/fairshare.sh 10 15 15

    Predict each ratio from the weight table in L07 §3.4 before you run it. The table does not list nice 15, so start from nice 10 and apply the factor of about 1.25 per step. These runs are not checked, but report question 1 asks for both predictions and both measurements.

runpredictionmake check accepts
fairshare.sh 0 0 10near 10.60 to 1.60
fairshare.sh 0 10 151024 / 110 ≈ 9.36.0 to 13.0
What the symptom tells you

RATIO near 1 for nice 0 against nice 10. The two spinners are not competing. Either they are not both on CPU 0, or the nice value never reached the spinner. Check with taskset -p <pid>, which prints the affinity mask 1 for CPU 0, and with field 19 of each stat file, which is the nice value. RATIO wildly off, or a division error. A sample came from the wrong PID, or it was empty. Print the four raw samples. Results drift between runs. Look for a leftover spinner from an earlier run.

Step 5

Policy beats weight

The goal of this step is to see that a real-time scheduling policy outranks every weight. You measure by hand, and there is no code to submit. Write down the numbers, because report question 3 asks for them.

Weights share the CPU. However, policies rank tasks. A SCHED_FIFOSCHED_FIFO is a real-time policy, first-come first-served. Real-time tasks use the priorities 0 to 99, and every real-time task outranks every normal task. task outranks every normal task.

  1. In the VM, pin your shell to CPU 1.

    taskset -pc 1 $$

    $$ is the PID of your shell. taskset -p changes the CPUs of a process that is already running, and -c 1 names CPU 1. This is the hard affinity of L07 §5.2 again, now for your shell. From here on, the shell and every command you type run only on CPU 1, so they never wait behind a spinner on CPU 0. A program that you start with taskset -c 0 still runs on CPU 0. The pinning lasts until you leave this shell.

  2. Predict first.

    A real-time spinner and a normal spinner share CPU 0. From L07 §4.3, what share of CPU 0 should the normal one get? Write your prediction down.

  3. Start a normal spinner, and then a real-time spinner, both on CPU 0.

    taskset -c 0 /tmp/spin &taskset -c 0 chrt -f 50 /tmp/spin &jobs -l

    chrt -f 50 makes the spinner a SCHED_FIFO real-time task. The first spinner stays a normal task. Job 1 is the normal spinner, and job 2 is the real-time one.

  4. Read the utime of both spinners, wait 5 seconds, and read it again.

    awk '{print $14}' /proc/<N>/stat /proc/<F>/statsleep 5awk '{print $14}' /proc/<N>/stat /proc/<F>/stat

    Here <N> is the PID of the normal spinner and <F> the PID of the real-time one. The first line of each pair is the normal spinner, and the second is the real-time one. Compute each growth. The real-time spinner gains about 500, all of CPU 0. The normal spinner gains about 0, as L07 §4.3 predicts. Notice that your shell kept working the whole time.

  5. Stop both spinners at once.

    kill %1 %2jobs # empty
What make check expects

The checker repeats this experiment itself, without your code. It first pins itself to CPU 1. Over 5 seconds, it expects the normal spinner's utime to grow by at most 2, and the real-time spinner's by at least 300.

Look deeper (ungraded). The share that stock Linux keeps for normal tasks.

A stock Linux kernel does not let real-time tasks take a CPU completely. By default, it keeps a small part of every second for normal tasks. This is called real-time throttling. The course VM boots with it turned off, so that Step 5 behaves as L07 §4.3 describes. Nothing in make check or the report depends on this fold.

To see the throttling, keep your shell pinned to CPU 1 as in item 1, and run the commands below.

cat /proc/sys/kernel/sched_rt_runtime_us-1echo 950000 > /proc/sys/kernel/sched_rt_runtime_us# repeat items 3 to 5 of Step 5echo -1 > /proc/sys/kernel/sched_rt_runtime_us

The value -1 means no limit. The value 950000 lets real-time tasks use at most 950000 µs, namely 0.95 s, of every second. With the limit on, the normal spinner's utime grows by about 25 in 5 s, about 5% of CPU 0, and the real-time spinner's by about 475. Set the value back to -1 before you go on. The VM also turns the limit off again at every boot.

Step 7

The report

submit/report.md already holds three questions. Each one asks you to argue from your own numbers. Each item below tells you how to investigate, not what the answer is.

  1. Question 1. "Compare your measured fairshare.sh 0 10 15 ratio with the prediction 1024/110 ≈ 9.3 from the weight table in L07 §3.4. How close did you land? Then predict, from the same table, the ratios for fairshare.sh 0 5 15 and fairshare.sh 10 15 15, and measure both. Why are those two ratios nearly equal? What would a table that subtracts the same amount of weight at every nice step predict for them instead?"

    Quote your three ratios from Step 4, and how far each one is from its prediction. Each prediction is one weight divided by the other. The table in L07 §3.4 does not list nice 15, so start from nice 10 and apply the factor of about 1.25 per step. Then look at what the two pairs, 0 and 5, and 10 and 15, have in common. For the last part, make up such a table, for example one that starts at 1024 for nice 0 and subtracts 50 at every step, and compute the same two ratios from it.

  2. Question 2. "Start a nice 0 spinner and a nice 10 spinner on CPU 0 as in Step 2. Read se.vruntime from /proc/<pid>/sched and utime from /proc/<pid>/stat for both, wait 10 seconds, and read them again. Quote how much each value grew. One spinner ran about nine times as long as the other, yet the two vruntimes grew by about the same amount. Use the formula in L07 §3.4 to show why, and explain how the rule of running the task with the smallest vruntime produces the ratio your fairshare.sh measured."

    Use the numbers you wrote down in Step 2, item 7. A utime growth of 100 is one second of CPU, and the vruntime is in milliseconds. Put each spinner's run time and weight into the formula Δvruntime = Δ(actual run time) × 1024 / weight from L07 §3.4. For the second part, ask what the scheduler does as soon as one vruntime falls behind the other, and what that forces the two vruntimes to do over 10 seconds.

  3. Question 3. "In Step 5 a SCHED_FIFO spinner and a normal spinner shared CPU 0. Quote the utime growth of each and the normal spinner's share. Use L07 §4.3 to explain that share. Would starting the normal spinner at nice −20 have changed it? Why or why not? Your shell kept working the whole time. Use L07 §5.1 and §5.2 to explain why."

    Use the numbers from Step 5, item 4. The share is the normal spinner's growth divided by the sum of both growths. For nice −20, compare what a nice value changes, in L07 §3.4, with what decides between a real-time task and a normal task, in L07 §4.3. For the shell, recall which CPU you pinned it to in Step 5, item 1, and how many ready queues Linux keeps in L07 §5.1.

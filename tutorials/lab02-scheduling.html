Make load, then measure the scheduler

This lab is an experiment more than a program: a spinner that burns CPU, an instrument (fairshare.sh) that measures how the scheduler divides one CPU between two spinners, and a real-time spinner that breaks the rules. This page says what each piece must do and print, and how to tell whether your measurement can be trusted. It never shows code for the lab files. The README and the file headers are the specification.

Step 0

Set up the loop

# laptop, repository rootSHARE=$PWD/labs/02-scheduling/submit env/run.sh# VMcd /sharegcc -Wall -Werror -O2 -o /tmp/spin spin.c
  • The VM has 2 CPUs. Every experiment in this lab pins its spinners to CPU 0 with taskset -c 0, which leaves CPU 1 free for your shell. That is why the VM stays usable while two spinners fight.
  • Spinners never stop on their own. Before every new experiment, make sure none is left over from the last one (jobs, or ps -C spin in the terminal), because a leftover spinner on CPU 0 silently changes every number you measure.
Step 1

spin.c: burn one CPU

Goal: a program that runs in user space forever, never sleeps, and is not optimized away.

The program is a loop and nothing else. The one trap is the compiler: at -O2 it may remove a loop whose work has no visible effect. The file's hint names the keyword that makes a variable's accesses count as visible. Look it up and decide which variable needs it.

How to check it yourself. Run it alone on CPU 0 and measure its user time growth, the same measurement fairshare.sh will make:

taskset -c 0 /tmp/spin &awk '{print $3, $14}' /proc/$!/stat # state, utime in tickssleep 5awk '{print $3, $14}' /proc/$!/stat # utime grew by about 500kill %1
Reading the number

utime counts in clock ticks, 100 per second. A spinner that owns a CPU for 5 seconds gains about 500. make check demands at least 300 and state R. If the growth is near 0, the loop is not running: either it was optimized away and the program exited, or it is sleeping.

Step 2

Two spinners, one CPU: watch preemption

No code in this step. Run the README's Part 1 commands and write down what you see: you will need it for the report.

look atwhat to record
/proc/<pid>/stat field 3The state of each spinner. Both are on one CPU; what state is each in?
nr_involuntary_switchesRead it twice, a few seconds apart, in /proc/<pid>/sched. How fast does it grow?
se.load.weightThe weight of a nice-0 task. Note the value; Step 4 uses it.
se.vruntimeRead it for both spinners, twice. How do the two values move relative to each other?

Then kill both (kill %1 %2). make check repeats this experiment and requires at least 5 involuntary switches in 5 seconds.

Step 3

fairshare.sh: build the instrument

Goal: fairshare.sh <niceA> <niceB> <seconds> prints exactly one line, A=<ticks> B=<ticks> RATIO=<A/B, two decimals>, where the ticks are each spinner's utime growth during the window.

The script is a timeline. Write it in this order, and run it after each stage:

stagewhat happenswhat the file header gives you
1 startStart spinner A at nice $na and spinner B at nice $nb, both on CPU 0, both in the background. Keep each PID.The exact start command, and where the PID comes from.
2 cleanupArrange for both spinners to be killed when the script exits, however it exits.The trap … EXIT hint. Do this right after starting them, not at the end.
3 warm upWait 2–3 seconds before measuring anything.Why: startup cost should not pollute the window.
4 sampleRead field 14 of each spinner's stat file.Field 14; you read fields with awk in Step 1.
5 windowSleep $secs.
6 sample againRead both again; each growth is "after minus before".
7 printPrint the line, with the ratio to two decimals.awk does floating point, and its printf controls the number of decimals.

A good intermediate test: after stage 4, print the raw samples and compare them with a cat of the same stat files. After stage 2, run the script, let it finish, and check that no spinner is left (ps -C spin prints only its header).

Format details the check enforces

A and B are whole numbers; RATIO has exactly two digits after the point (9.30, not 9.3). The script may read only /proc: the words top and ps must not appear in it outside comments. The checker runs it with SPIN=/tmp/spin, so start the binary through $SPIN, as the header does.

Step 4

Predict, measure, and decide whether to trust it

An instrument is only useful once you have checked it against a case whose answer you know.

runpredictionmake check accepts
bash fairshare.sh 0 0 10Equal weights, so work out what the ratio must be.0.60 – 1.60
bash fairshare.sh 0 10 15The ratio of the two weights; the README gives both.6.0 – 13.0
a pair of your choicePredict it from "each nice level is a factor of about 1.25" before you run it.not checked; good for the report
What the symptom tells you

RATIO near 1 for nice 0 vs 10: the two spinners are not competing. Either they are not both on CPU 0, or the nice value never reached the spinner. Check with taskset -p <pid> and field 19 of each stat file. RATIO wildly off, or a division error: a sample came from the wrong PID or was empty; print the four raw samples. Results drift between runs: look for a leftover spinner from an earlier run.

Step 5

Policy beats weight

Goal: measure the share a normal spinner gets next to a SCHED_FIFO spinner, then find the setting that explains it. No code to submit here.

  1. Predict first, from lecture: a real-time task outranks every fair-class task. What share should the normal one get?
  2. Measure by hand. Start the README's two spinners, then use the fairshare method manually: two samples of each utime, some seconds apart. Compute the normal spinner's share, its growth divided by the total.
  3. Find the setting. It lives in /proc/sys/kernel/. List that directory and look at the names about real-time scheduling. man 7 sched has a section on limiting the CPU usage of real-time processes; read it and match its numbers with your measured share.
  4. Clean up both spinners at once.
What make check expects

The checker repeats this itself (your code is not involved) and expects the normal spinner's share between 2% and 10%. Your hand measurement should land in the same range. If the console becomes sluggish, remember the FIFO spinner is pinned to CPU 0 and your shell can still run on CPU 1: kill %2 works.

Step 7

Report and submit

The three questions in submit/report.md ask you to argue from your own numbers. How to investigate, not the answers:

  1. The geometry of nice. Quote your measured ratio and how far it is from 9.3. For the "why geometric" part, take the README's hint literally: with 100 runnable tasks, compute what share one task gains or loses from one nice step under a table that adds a fixed amount per level, and under one that multiplies. Which keeps its meaning?
  2. CFS vs EEVDF. Use the se.load.weight and se.vruntime values you recorded in Step 2. Lecture tells you what CFS does with them. Then ask: your ratio measures how much CPU each task gets over 15 seconds, not which task runs next. Which of those two did EEVDF change?
  3. The safety valve. Name the setting from Step 5, quote its value (and the value it is measured against), and show that it matches your measured share. For the "why", imagine the FIFO spinner with no limit on a machine with one CPU: what could no longer run, including anything you would use to stop it?

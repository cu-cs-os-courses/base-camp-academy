Both sides of read()

Part 1 calls the five file verbs from user space; Part 2 implements them inside the kernel, for a device whose "disk" is a 900-byte buffer. The capstone runs one session through your tool against a regular file and against your device, and the two outputs must match. This page says what each function must do, what each verb must return at the edges, and how to test each piece before make check. It never shows code for the lab files. This page and the contract at the top of each file are the specification; L17–L20 and R11 are behind it.

Step 0

Set up the loop

Part 1 uses the usual loop. Part 2 adds a build on the laptop, in Docker, because the VM has no kernel source tree to build modules against.

# laptop, repository root: Part 1SHARE=$PWD/labs/05-storage-and-io/submit env/run.sh# VMgcc -Wall -Werror -O2 -o /tmp/filetest /share/filetest.c
Docker must be running

This is the course's only kernel-code lab. Both the manual build (Step 3) and make check build the module in the same Docker container that built your VM, against the pinned kernel tree. A kernel module is built for one exact kernel, and the VM has no kernel tree of its own. On macOS, colima start first. The first build ever also indexes the kernel's exported symbols, which takes a few minutes once.

Step 1

filetest.c: open, or die with 255

Goal: open the named file for reading and writing, create it with mode 0644 if it does not exist, and on failure call perror("open") and exit with status 255.

Read man 2 open: which flag means read-write, which means "create if absent", and why the third argument (the mode) matters only together with that flag. The command loop and parsing are already written. Only the syscalls are yours, and they are raw syscalls: open, read, write, lseek, close, never fopen and friends.

echo q | /tmp/filetest /tmp/new.txt; ls -l /tmp/new.txt # created, -rw-r--r--echo q | /tmp/filetest /no-such-dir/f; echo $? # open: No such file or directory, then 255
Step 2

filetest.c: r, w, s

Goal: each command makes one syscall and prints exactly one line, built from that syscall's return value.

commandsyscall and what to printdetails to get right
r <n>read up to n bytes; print READ <k> <data>k is what read returned, which can be less than n. The data is not a C string, so print exactly k bytes; the TODO's printf hint shows how.
w <text>write the text; print WROTE <k>No newline is written, only the text.
s <off> <whence>lseek; print OFFSET <newoff>Map set, cur, end to the three SEEK_ constants; anything else prints ERR. Print what lseek returns.
q, or end of inputclose; print nothing; exit 0Already written in the skeleton.

There is deliberately no "tell" command: s 0 cur is tell. Work out why; understanding it is half the point of lseek.

How to check it yourself. These are the checker's own sessions; each output must match exactly.

printf 'hello, basecamp!' > /tmp/fx # 16 bytes, no newlineprintf 'r 5\nq\n' | /tmp/filetest /tmp/fx # READ 5 hellorm -f /tmp/f2; printf 'w abcdef\ns 0 set\nr 6\nq\n' | /tmp/filetest /tmp/f2 # WROTE 6 / OFFSET 0 / READ 6 abcdefprintf 's 7 set\nr 8\ns -8 end\nr 8\ns 0 cur\nq\n' | /tmp/filetest /tmp/fx # OFFSET 7 / READ 8 basecamp / OFFSET 8 / READ 8 asecamp! / OFFSET 16
What the symptom tells you

Garbage after the data in READ: you printed the buffer as a string instead of exactly k bytes. READ 0 right after a write: the offset is now after what you wrote; the session has to seek back first, and s 0 set has to really move it. Nothing printed at all when piped: output was buffered and lost; the loop's fflush must still run after your print.

Then run the same tool on a scratch file, then on /proc/version, then on /dev/null, and note what r, w, and s 0 end do on each. Same tool, three very different things pretending to be files.

Step 3

The driver's build and load loop

Get this loop working with the unfilled skeleton first. Then every later change is edit, rebuild, reload.

make check LAB=05-storage-and-io builds the .ko automatically: a host-side step runs before the VM boots. For iterating by hand, copy the loop below exactly. On the laptop, it stages your file in mod/ at the repository root and builds mod/char_driver.ko. In the VM (booted with SHARE=$PWD/mod), it loads the module, creates the device node, and pokes it. R11 walked through the same commands.

Kernel code is different

Rebuild, then rmmod and insmod again: the VM keeps running the old module until you reload it. insmod: File exists: the module is still loaded; rmmod it first. insmod: Device or resource busy: major 511 is still registered although the module is gone, usually because an earlier version's exit did not unregister it. Boot the VM again. dmesg shows "BUG" or "Oops": your code crashed inside the kernel. The VM is no longer trustworthy: leave it (Ctrl-a x) and boot again. Do not commit mod/; only submit/char_driver.c is graded.

Step 4

init, exit, open, release

Goal: the module registers major 511 under the exact name, owns a zeroed 900-byte buffer while loaded, and logs every open and close in the exact format.

The contract at the top of char_driver.c gives major 511, the name simple_char_driver, the exact printk formats, and the lseek semantics. The checks match it literally, including the dmesg lines. struct file_operations is the dispatch table. Registering it against major 511 is what makes read(fd, ...) on your device node arrive at your scd_read; this is the fork in the road that report question 4 asks you to find.

functionwhat it must doread first
scd_initAllocate the buffer, zeroed. Register the device with your file_operations. If registration fails, free the buffer and return a negative errno. Delete the three placeholder casts.kzalloc in include/linux/slab.h; register_chrdev in include/linux/fs.h and L17/R11
scd_exitUndo init, in reverse order.unregister_chrdev, kfree
scd_openCount the open, then print the opened %d times line from the contract.the contract, character for character
scd_releasePrint the closed %d times line, using the same running counter.the contract

How to check it yourself: reload, then cat /dev/simple_char_driver once. It prints nothing yet, because read is still a TODO. dmesg | tail -2 must show exactly one "opened" line and one "closed" line in the contract's format. Run it again and watch the number. For example, the lines for a third open and close read:

simple_char_driver: opened 3 timessimple_char_driver: closed 3 times
What the symptom tells you

The build fails on unused variables: kernel builds treat warnings as errors; the placeholder casts or an unused local are the usual cause. /proc/devices shows 511 with a different name: the name you registered is not DEVICE_NAME. The line is still there after rmmod: exit does not unregister, and the next insmod will fail.

Step 5

read, write, llseek

Goal: the buffer behaves like a 900-byte file. Reads and writes start at the current offset, never go past byte 900, and move the offset by exactly the number of bytes they handled.

Read and write move bytes with copy_to_user and copy_from_user. The user's buffer pointer lives in another address space; Lab04 made you watch those pages materialize. Therefore, the kernel must not dereference user pointers directly. These helpers check and copy across the boundary.

Answer these for read before writing it. write has the same questions.

  1. The caller asked for len bytes at *offset. How many bytes are actually left between *offset and BUFFER_SIZE? How many will you copy?
  2. If that number is 0, what must read return? The contract says what 0 means to the caller.
  3. copy_to_user returns the number of bytes it could not copy. What should the driver return if that is not 0? (-EFAULT is the convention: look it up.)
  4. After copying, what happens to *offset, and what number do you return?

For llseek, the contract gives the three formulas and the clamp to [0, 900]. Two questions remain: where does the new position have to be stored so that the next read and write use it? (It is a field of struct file, and it is what *offset points to in read and write.) And what does llseek return?

How to check it yourself: these are the checker's device tests.

printf 'hello world' > /dev/simple_char_driverdd if=/dev/simple_char_driver bs=1 count=11 2>/dev/null; echo # hello worlddd if=/dev/simple_char_driver bs=1 skip=6 count=5 2>/dev/null; echo # world (dd skips with lseek)dd if=/dev/zero of=/dev/simple_char_driver bs=1200 count=1 conv=notruncdd if=/dev/simple_char_driver bs=1 skip=895 count=100 2>/dev/null | wc -c # 5
What the symptom tells you

cat never stops: read never returns 0 at the end of the buffer. world test prints hello: llseek computed the position but did not store it, or SEEK_CUR is wrong. The count is 100, not 5: read does not stop at byte 900. The 1200-byte write gives an Oops or strange data later: write copied past byte 900, into memory that is not yours. Clamp before copying, exactly as read does. Oops in dmesg: most often a direct access to the user pointer instead of copy_*_user, or an offset outside the buffer.

Step 6

The capstone: your tool, your device

Goal: one filetest session gives identical output on a regular file and on your device.

The driver VM shares mod/, so put your tool there too: on the laptop, cp labs/05-storage-and-io/submit/filetest.c mod/; in the VM, gcc -Wall -Werror -O2 -o /tmp/filetest /share/filetest.c. With the module loaded and the node created, run the checker's session against both and compare:

rm -f /tmp/plainprintf 'w kernel-mode\ns 0 set\nr 11\ns 0 cur\nq\n' | /tmp/filetest /tmp/plain > /tmp/aprintf 'w kernel-mode\ns 0 set\nr 11\ns 0 cur\nq\n' | /tmp/filetest /dev/simple_char_driver > /tmp/bdiff /tmp/a /tmp/b && echo identical

If they differ, the first differing line names the verb to fix: WROTE is write, OFFSET is llseek, READ is read. Then try sessions of your own, especially near byte 900 (s -3 end, then w and r). Inside the 900-byte world, the device should behave like a file of that size. What differs past it is worth a sentence in the report.

Step 8

Report and submit

You submit three files in submit/: filetest.c (Part 1), char_driver.c (Part 2), and report.md. The report has four questions: who owns the offset, why copy_to_user exists, your buffer's afterlife across rmmod, and where the ext4 path and your driver's path diverge in the kernel. Their full wording is in submit/report.md. How to investigate, not the answers:

  1. Who owns the offset? The question describes the experiment. Run it, record each command and output, and then run a variant: one process whose two file descriptors come from a single open (look up dup), against two independent opens. Then name the level where the offset lives, using your driver's code as evidence: which argument of scd_read carries it?
  2. Why copy_to_user. Recall from Lab04 whose address space a user pointer belongs to, and whether the page behind it is even present. For the garbage-pointer half, predict what your driver returns for one, and what the process then sees. The errno list in man 2 read helps.
  3. The buffer's afterlife. Test it: write, rmmod, insmod, read. Then look at your init and exit to explain the result. For kmalloc, ask what memory it hands you and who used that memory before.
  4. Where the paths diverge. Start from read(2), then look in the kernel source (fs/read_write.c in the build container's tree, or an online kernel cross-reference for 6.6) for the function that calls file->f_op->read. Then ask where f_op was set for your device, and for an ext4 file.

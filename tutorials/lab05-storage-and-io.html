Both sides of read()

This page walks you through Lab05 step by step. In this lab, you look at file I/O from both sides of the system call. In Part 1, you write filetest.c, a small program that calls open, read, write, lseek and close on any file you name. In Part 2, you write char_driver.c, a kernel module that implements the same calls for a device whose storage is a 900-byte buffer in kernel memory. At the end, one filetest session prints the same output on a regular file and on your device. This page and the header comment of each file in labs/05-storage-and-io/submit/ are the specification for this lab.

Step 1

filetest.c, open or exit with 255

The goal of this step is to open a file with the open system call, and to handle an open that fails. filetest opens the file named on its command line for reading and writing, and creates it with mode 0644 if it does not exist. If the open fails, filetest calls perror("open") and exits with status 255.

  1. On your laptop, read the header of filetest.c.

    It gives the four commands and the exact line each one prints. The command loop and the parsing are already written. Your work is the system calls, and only the raw ones, namely open, read, write, lseek and close. Do not use fopen or the other stdio functions on the file. The loop itself still reads its commands with fgets.

  2. Write the open, and its failure path.

    Read open(2) to find the flag that opens a file for both reading and writing, and the flag that creates the file if it is absent. The same page explains why the third argument, the mode, matters only together with the second flag. open returns -1 on failure. perror(3) then prints your text, followed by the reason for the failure.

  3. In the VM, recompile, and test both cases.

    gcc -Wall -Werror -O2 -o /tmp/filetest filetest.cecho q | /tmp/filetest /tmp/new.txt; ls -l /tmp/new.txt-rw-r--r-- 1 root root 0 Nov 6 22:17 /tmp/new.txtecho q | /tmp/filetest /no-such-dir/f; echo $?open: No such file or directory255

    The first run creates an empty file, and rw-r--r-- is mode 0644. The second open fails, because the directory /no-such-dir does not exist. perror prints the first highlighted line, and $? holds the exit status of the last command.

What the symptom tells you

ls reports No such file or directory. The open did not create the file. Check the flags. The exit status is not 255. The failure path did not run, or it returns another value.

Step 2

The r, w, s commands in filetest.c

The goal of this step is to see how read, write and lseek all work on one number, the file positionFor each open file, the kernel keeps a current file position, namely where the next read or write starts. read and write move it forward by the number of bytes they handle. lseek sets it directly.. Each command makes one system call and prints exactly one line, built from that call's return value.

  1. On your laptop, write the three actions in the table below.

commandsystem call, and what to printdetails to get right
r <n>read(2) up to n bytes, then print READ <k> <data>k is what read returned, which can be less than n. The data is not a C string, so print exactly k bytes. The TODO's printf hint shows how.
w <text>write(2) the text, then print WROTE <k>Write only the text, with no newline. k is what write returned.
s <off> <whence>lseek(2), then print OFFSET <newoff>Map set, cur and end to the three SEEK_ constants. Any other word prints ERR. Print what lseek returned.
q, or end of inputclose the file, print nothing, and exit 0Already written in the skeleton.

  1. In the VM, recompile, and run the three sessions that make check runs.

    printf 'hello, basecamp!' > /tmp/fxprintf 'r 5\nq\n' | /tmp/filetest /tmp/fxREAD 5 hellorm -f /tmp/f2printf 'w abcdef\ns 0 set\nr 6\nq\n' | /tmp/filetest /tmp/f2WROTE 6OFFSET 0READ 6 abcdefprintf 's 7 set\nr 8\ns -8 end\nr 8\ns 0 cur\nq\n' | /tmp/filetest /tmp/fxOFFSET 7READ 8 basecampOFFSET 8READ 8 asecamp!OFFSET 16

    The shell's printf writes its text without a newline, so /tmp/fx holds exactly 16 bytes. In the sessions, each \n ends one command. Your output must match the highlighted lines exactly, including the spaces. In the third session, s -8 end moves to 8 bytes before the end of the 16-byte file, namely byte 8. There is no "tell" command. The header asks you to work out why s 0 cur is enough.

  1. Run one session on three files that are not alike.

    Store the session in a shell variable, S, so that you type it once. Then run it on a new regular file, on /proc/version, and on /dev/null, as Fig. 2.1 shows.

    The regular file starts empty. Therefore, the first read finds nothing, the write makes the file 3 bytes long, and s 0 end moves to byte 3.

    The kernel makes up the text of /proc/version when you read it (R02 Part 1), so the file has no stored bytes to write into and no fixed end. Both calls fail and return -1.

    /dev/null is a device fileIn UNIX, each device appears as a file under /dev. The first letter of ls -l is c for a character device or b for a block device, and two numbers replace the file size. A read on the file runs the device's driver.. Its driver accepts and discards every write, and every read finds nothing.

    The same five system calls reach three very different things. In Part 2, you write the code behind a file like /dev/null.

What the symptom tells you

Garbage after the data in a READ line. You printed the buffer as a C string, not exactly k bytes. READ 0 right after a write. This is correct. The write moved the position to the end of what it wrote, so the session has to seek back first. OFFSET -1 on a regular file. lseek failed. Check how you map the whence word to a SEEK_ constant. ERR for a valid s command. The comparison of the whence word does not match set, cur or end.

Step 3

The driver's build and load loop

The goal of this step is to learn the loop that puts your code into the running kernel and takes it out again, namely build, load, test, and unload. Do it first with the unfilled skeleton. After that, every change to char_driver.c is edit, rebuild, and reload.

char_driver.c is a loadable kernel module (L02 §4.1). It is the driverA device driver is the kernel code that knows one kind of device. It implements the device's system-call interface, such as open, read and write. It is the device-dependent part of the device manager. for a character deviceA character device is used as a stream of bytes, such as a keyboard or a serial port. A block device is used in fixed-size blocks that can be addressed, such as a disk., and that device has no hardware behind it. Its storage is a 900-byte buffer in kernel memory.

  1. On your laptop, start Docker.

    On macOS, run colima start. A module must be built against the source tree of the exact kernel it runs in, and the VM has no kernel source tree. Therefore, the module is built on your laptop, in the course's Docker container, the same container that built your VM. The container keeps the 6.6.87 tree that your VM's kernel came from.

  2. Leave the VM with poweroff. Then, at the repository root, run make check once.

    make check LAB=05-storage-and-ioRESULT lab=05-storage-and-io status=fail passes=7 fails=10

    make check builds your module on the laptop, and then boots a VM of its own. Only one VM can run at a time. If another VM is still running, make check stops with Could not set up host forwarding rule. The very first time, it prints one-time: preparing the kernel tree, a few minutes. The manual build in item 3 needs this preparation, and it happens only once. The 10 failures are expected, because every TODO is still empty.

  3. Stage the driver in mod/, and build it.

    mkdir -p modcp labs/05-storage-and-io/submit/char_driver.c mod/printf 'obj-m := char_driver.o\n' > mod/Makefiledocker run --rm --platform linux/amd64 \ -v kernel-lens-cache:/work/cache -v "$PWD/mod:/mod" kernel-lens-build \ sh -c 'make -C /work/cache/linux-6.6.87 M=/mod modules \ && objcopy --remove-section .BTF /mod/char_driver.ko'make: Entering directory '/work/cache/linux-6.6.87' CC [M] /mod/char_driver.o MODPOST /mod/Module.symvers CC [M] /mod/char_driver.mod.o LD [M] /mod/char_driver.ko BTF [M] /mod/char_driver.komake: Leaving directory '/work/cache/linux-6.6.87'

    Keep mod/ inside the repository. The container sees only the directories that Docker shares with it, and the repository is one of them. The one-line Makefile tells the kernel's build system to build char_driver.c as a module. docker run starts the container with two directories attached, the kernel tree from the Docker volume kernel-lens-cache at /work/cache, and your mod/ at /mod. Inside, make -C … M=/mod modules runs the kernel's own build and compiles your module in /mod. The result is mod/char_driver.ko, a kernel object file.

    The last command, objcopy, is a fixed part of the course's build recipe. Copy it exactly.

  4. Boot the VM with mod/ shared.

    SHARE=$PWD/mod env/run.sh

    A VM sees only the directory that was shared when it booted. In this VM, /share is mod/, and /share/char_driver.ko is your module.

  5. In the VM, load the module.

    insmod /share/char_driver.kolsmodModule Size Used bychar_driver 12288 0

    insmod loads the .ko file into the running kernel and runs its init function, scd_init. It prints nothing when it succeeds. lsmod lists the loaded modules, with their size in bytes and how many users hold them, such as open device files.

  6. Look for the driver's major number.

    head -3 /proc/devicesCharacter devices: 1 mem 4 /dev/vc/0grep simple_char_driver /proc/devices

    /proc/devices lists every registered driver, one per line, as a major numberA device file carries two numbers instead of a size. The major number picks the driver, because the kernel keeps a table of drivers indexed by it. The minor number tells that driver which of its devices this is. and a name. For example, major 1, mem, is the driver behind /dev/null. The grep prints nothing, because the skeleton's init registers nothing. After Step 4, it prints 511 simple_char_driver.

  7. Create the device file.

    mknod /dev/simple_char_driver c 511 0ls -l /dev/simple_char_drivercrw-r--r-- 1 root root 511, 0 Nov 6 22:17 /dev/simple_char_driver

    mknod creates a special file. c makes it a character device, with major number 511 and minor number 0. In the ls -l line, the first letter is c, and 511, 0 stands where a regular file shows its size. The file holds no data. It is only a name for the pair (511, 0). The VM builds /dev afresh at every boot, so create the file once per boot. A second mknod in the same boot prints File exists, which is harmless.

  8. Open the device file.

    cat /dev/simple_char_drivercat: /dev/simple_char_driver: No such device or address

    The file exists, but no driver has registered major 511 yet. Therefore, the open fails. Your init in Step 4 changes this.

  9. Unload the module.

    rmmod char_driverlsmodModule Size Used by

    rmmod runs the module's exit function, scd_exit, and removes the module from the kernel. It takes the module's name, not the file name.

Step 4

init, exit, open, release

The goal of this step is to make the kernel send a device file's open and close to your code. The module registers major 511 under the name simple_char_driver, owns a zeroed 900-byte buffer while it is loaded, and logs every open and close in the exact format of the contract.

The contract at the top of char_driver.c gives the major number, the name, the exact printk formats, and the llseek rules. The checks match it literally, including the dmesg lines. At the bottom of the file, scd_fops is a struct file_operationsAn I/O system call traps into the kernel, and the kernel looks up the correct driver in a table. In Linux, that table is indexed by the major number, and each entry is a struct file_operations, a set of pointers to the driver's open, read, write and other functions.. It already lists your five functions. Registering it under major 511 is what connects the device file from Step 3 to your code.

functionwhat it must docalls to use
scd_initAllocate the buffer, zeroed. Register the device with your file_operations. If registration fails, free the buffer and return a negative error code. Delete the three placeholder casts.kzalloc(BUFFER_SIZE, GFP_KERNEL) returns zeroed memory, or NULL if none is free. register_chrdev(MAJOR_NUMBER, DEVICE_NAME, &scd_fops) returns 0, or a negative error.
scd_exitUndo init, in reverse order.unregister_chrdev(MAJOR_NUMBER, DEVICE_NAME), then kfree(device_buffer), which frees what kzalloc returned.
scd_openCount the open, then print the opened %d times line of the contract.printk, which works like printf but writes to the kernel log (L02 §4.2). Copy the format from the contract.
scd_releasePrint the closed %d times line, with the same running counter.printk, with the format from the contract.

A kernel function reports an error by returning a negative error number (L02 §4.2), such as -ENOMEM or -EBUSY. errno(3) lists the names.

  1. Write the four functions, rebuild, and reload, with the loop of Step 3.

  2. In the VM, check the registration.

    grep simple_char_driver /proc/devices511 simple_char_driver

  3. Open and close the device once, and read the log.

    cat /dev/simple_char_driverdmesg | tail -2[ 7.353480] simple_char_driver: opened 1 times[ 7.353705] simple_char_driver: closed 1 times

    dmesg prints the kernel log, where printk writes (L02 §4.3). The number in brackets is the time since boot, in seconds. cat opens the file, reads until a read returns 0, and closes it. It prints nothing yet, because your read is still a TODO that returns 0. The open and the close each leave one line in the log. Run both commands again, and the count becomes 2. If you booted again since Step 3, create the device file first.

  4. Unload the module, and check that the registration is gone.

    rmmod char_drivergrep -c simple_char_driver /proc/devices0

    grep -c counts the matching lines.

What the symptom tells you

The build fails with defined but not used [-Werror=unused-variable]. Kernel builds treat warnings as errors. You deleted a placeholder cast before your code used that variable, or a local variable is unused. /proc/devices shows 511 with a different name. The name you registered is not DEVICE_NAME. The count is still 1 after rmmod. Your exit does not unregister, and the next insmod fails. The dmesg lines differ from the contract. Compare them with the contract, character by character.

Step 5

read, write, llseek

The goal of this step is to make the 900-byte buffer behave like a 900-byte file. Reads and writes start at the current position, never go past byte 900, and move the position by exactly the number of bytes they handled.

  1. Learn the rule for user pointers.

    scd_read receives buf, a pointer into the memory of the process that called read. Kernel code never touches such a pointer directly. It copies with copy_to_user and copy_from_user instead, as L02 §3.4 showed. Both return the number of bytes they could not copy, so 0 means success. If the copy fails, return -EFAULT (L02 §3.4). Report question 2 asks why the rule exists.

  2. Answer these questions for read before you write it. Write has the same questions.

    1. The caller asked for len bytes at *offset. How many bytes are left between *offset and BUFFER_SIZE? How many will you copy?
    2. If that number is 0, what must read return? The contract says what 0 means to the caller.
    3. After the copy, what happens to *offset, and what number do you return?

  3. Write llseek.

    The contract gives the three formulas and the clamp to [0, 900]. filp points to this open's entry in the open-file table (L20 §0.3). Its field f_pos is the current file position, so store the new position there and return it.

  4. Rebuild, reload, and run the device tests that make check runs.

    printf 'hello world' > /dev/simple_char_driverdd if=/dev/simple_char_driver bs=1 count=11 2>/dev/null; echohello worlddd if=/dev/simple_char_driver bs=1 skip=6 count=5 2>/dev/null; echoworlddd if=/dev/zero of=/dev/simple_char_driver bs=1200 count=1 conv=notrunc 2>/dev/nulldd if=/dev/simple_char_driver bs=1 skip=895 count=100 2>/dev/null | wc -c5

    dd copies from if= to of=, in count blocks of bs bytes. skip=6 first skips 6 input blocks, and on a device dd skips with lseek. Therefore, the second test checks your llseek. 2>/dev/null hides dd's summary, and echo ends the line. /dev/zero supplies zero bytes. The third test writes 1200 of them. Your write keeps the first 900 bytes. The read that follows proves it. It reads from byte 895, so only 5 bytes remain, and wc -c counts them.

  5. Read the whole device.

    cat /dev/simple_char_driver | wc -c900

    cat stops only when a read returns 0. Therefore, 900 shows that your read ends the file at byte 900.

What the symptom tells you

cat never stops. Your read never returns 0 at the end of the buffer. The world test prints hello. Your llseek computed the position but did not store it, or SEEK_CUR is wrong. The count is 100, not 5. Your read does not stop at byte 900. The 1200-byte write gives an Oops or strange data later. Your write copied past byte 900, into memory that is not yours. Limit the length before copying, exactly as read does. An Oops in dmesg. Most often, the code touched the user pointer directly instead of through copy_*_user, or used an offset outside the buffer.

Step 8

The report

The goal of this step is to explain what your two programs showed you. submit/report.md already holds three questions. Each item below tells you how to investigate, not what the answer is.

  1. Question 1. "Run your Step 2 session S on a new regular file, then run filetest on the same file again with the single command s 0 cur.   2. Question 2. "In your driver, the user's buffer pointer arrives in read. Why can't you just memcpy into it? Connect your answer to the address spaces of Lab04. And what happens (to your driver, and to the process) if the user hands you a garbage pointer?"

Watch the kernel page, then be the pager

Part 1 measures the real kernel handing out memory lazily, one page fault at a time. Part 2 puts you inside a paging simulator: every tick it calls your pageit(), and your eviction policy decides how much time 20 processes spend waiting for the disk. This page says what each piece must do, which questions your LRU has to answer each tick, and how to read the simulator's score. It never shows code for the lab files. This page, check/sim/simulator.h, and the file headers are the specification; L15–L16 are the lectures behind it.

Step 1

touch.c: watch pages materialize

Goal: print exactly RSS_KB_BEFORE=, RSS_KB_AFTER= and MINFLT_DELTA=, measured around a loop that touches every page of a 64 MiB region.

How to check it yourself (with huge pages off; see Step 2):

echo never > /sys/kernel/mm/transparent_hugepage/enabled/tmp/touch# BEFORE: a few thousand kB. AFTER: about 65,536 kB more. DELTA: about 16,384.
What the symptom tells you

A value of -1: that reader failed to open or parse; print the line it found. MINFLT_DELTA about 16,384 but RSS barely grows: your touch reads instead of writing. Reading an untouched page does not give the process a page of its own; why not is a good sentence for report question 1. MINFLT_DELTA of only a few hundred: huge pages are still on (Step 2). RSS_KB_BEFORE already about 65,000: something touched the region before the first measurement.

Step 3

Meet the simulator

Before writing a policy, get the baseline score and learn what your function can see and do.

In Part 2 you switch roles: you are the page-fault handler. The simulator runs 20 concurrent processes over 400 virtual pages with only 100 physical frames, and it calls your pageit() every tick. One instruction costs 1 tick; one swap-in or one swap-out costs 100 ticks. Your score is the ratio of blocked ticks to compute ticks: time spent waiting on paging versus useful work.

Grading uses the default constants in simulator.h: 20 processes × 20 virtual pages, 100 physical frames, PAGESIZE 128, and PAGEWAIT 100. check/sim/pager-basic.c is provided and readable; it is your baseline, and on our reference VM it scores about 15. The simulator is seeded and exactly deterministic: the same seed gives the same ratio, every time.

gcc -Wall -Werror -O2 -Icheck/sim -o /tmp/test-basic \ check/sim/simulator.c check/sim/programs.c check/sim/pager-basic.c/tmp/test-basic -seed 1 2>&1 | grep ratio # ratio blocked/compute=… (about 15)/tmp/test-basic -help # the other flags

The simulator writes everything, the score included, to stderr, hence the 2>&1 before any pipe. Read check/sim/simulator.h and pager-basic.c, then make sure you can answer these from the source, not from memory:

questionwhere the answer is

Interface reference. simulator.h declares the types and the three functions. pageit(Pentry q[MAXPROCESSES]) receives one entry per process:

fieldmeaning
active1 running, 0 exited
pcthe program counter; the page the process needs is pc / PAGESIZE
npagespages in the process's space (20 while active)
pages[]the page map: 1 swapped in, 0 not. A 0 covers three situations: out, going out, or coming in. The map alone does not distinguish them. If your policy needs to know about in-flight operations, track them yourself.

You act through pagein(proc, page) and pageout(proc, page). Both return 1 if the operation starts, is already underway, or is already done. Both return 0 if it cannot start: there is no free frame, or the page is mid-swap the other way. An operation completes 100 ticks after it starts.

The programs being paged. The simulator runs 40 processes in total, at most 20 at a time. Each is drawn randomly from five known program shapes:

1: loop w/ branch 2: one loop 3: doubly nested for 10 30 for 20 50 for 10 20 run 500 run 1129 run 1166 if .4 end for 10 20 run 900 exit run 516 else end run 131 4: linear end endif run 1911 exit end exit exit 5: probabilistic backward branch for 10 20 label: run 500 if .5 goto label end exit

Which branches fire and how many iterations run depend on the seed. Therefore, you can never predict an execution, only its probabilistic shape. The shapes matter mostly for the stretch in Step 7 and for report question 4. For LRU, you need only one assumption: the recent past predicts the near future most of the time.

Step 4

Design your LRU

Goal: pageit() keeps every active process's needed page in memory as often as it can, and when it must evict, it evicts the least recently used page.

Each call is one tick. On every tick your function has four jobs. Decide how you will do each one before you write it:

jobthe question you must answer
1 · record useWhich (process, page) pairs are in use on this tick? The skeleton's timestamps array and tick counter exist to store "when was this page last used".
2 · requestFor each active process whose needed page is not in memory: ask for it.
3 · make roomIf the request cannot start, choose a victim: the page with the oldest timestamp, among which pages? Only this process's (local), or all processes' (global)? Local means each process evicts its own pages; if you choose it, consider reserving frames per process. This is your design decision, and report question 2 asks you to defend it. Never choose a page someone needs right now.
4 · in flightA swap takes 100 ticks, and the page map cannot tell "going out" from "coming in" from "out". What stops your function from choosing the same victim again on the next tick? Does it matter?
Before you write it

Delete the three placeholder lines in the skeleton (the fprintf and exit), and keep tick++ as the last thing the function does on every path. A return in the middle that skips it freezes your clock.

Step 5

Measure and iterate

gcc -Wall -Werror -O2 -Icheck/sim -o /tmp/test-lru \ check/sim/simulator.c check/sim/programs.c submit/pager-lru.cfor s in 1 2 3; do /tmp/test-lru -seed $s 2>&1 | grep ratio; done # make check averages these threefor i in 1 2; do /tmp/test-lru -seed 1 2>&1 | grep ratio; done # must be identical

The legacy course graded this ratio, averaged over several seeds. Use its bands to see where your average stands:

avg ratioverdict
≥ 5.12worse than useless
2.56 – 5.12barely paging
1.28 – 2.56getting there
0.64 – 1.28the checks' passing bar
0.32 – 0.64good LRU
< 0.32excellent: reference territory

make check requires the average over seeds 1–3 to be below 1.28; an honest LRU clears that several times over. Only the score matters to the check, so once you pass, the local vs global choice is yours to explore: try both and report what you saw.

What the symptom tells you

"pager-lru not yet implemented": the placeholder lines are still there. The run never ends: rerun with -dead. If it prints "All needed pages swapped out!", then at some tick every process was waiting and nothing was coming in, and the simulator will wait forever: your function evicted without requesting, or requested nothing. Stop it with Ctrl-C. Two runs with the same seed differ: the policy uses something that is not repeatable, such as rand(), the time, or an uninitialized variable. A score around 5 or more: eviction is barely working. Check that job 1 really updates the timestamps, and that job 3 picks the smallest one. It is merely slow: make check gives each run 120 seconds. Look for a loop inside pageit that keeps searching when no victim exists.

Seeing your policy think

-block logs every block and unblock with its tick, and -page every pagein and pageout: /tmp/test-lru -seed 1 -block -page 2>&1 | head -80. Follow one process: how long does it wait for each page, and is it waiting for the same page over and over? The second pattern means you are evicting pages that come back soon. (-csv writes the same events to output.csv and pages.csv in the current directory, for plotting.)

Step 7

Report and submit

Five questions in submit/report.md; the file holds their exact wording, and your answer replaces each (your answer) placeholder. How to investigate, not the answers:

  1. The lie of malloc. Paste your Step 1 and Step 2 numbers. For "what did each fault do", compare RSS just before and just after the loop, and think about the read-vs-write experiment. For "major", ask where the data of a page would have to come from for a fault to need the disk.
  2. The 75×. Put your three seeds next to pager-basic's. Explain the gap from what pager-basic refuses to do (Step 3), then describe your victim choice and your local or global decision, with the evidence from Step 5.
  3. Is 100:1 honest? Compute the real ratio from the question's two numbers yourself, and compare it with 100. Then convert: how many instructions could the CPU have run during one fault?
  4. Where LRU is exactly wrong. Pick a loop from the five program shapes, or make one up. Give LRU fewer frames than the loop has pages, and simulate by hand, tick by tick, which page LRU evicts and which page the loop needs next.
  5. MemFree or MemAvailable? In the VM, read both lines of /proc/meminfo. Then read a lot of file data, for example with find /usr -type f -exec cat {} + > /dev/null, and read both lines again. Which one dropped, and which one barely moved? The kernel's documentation for /proc, at docs.kernel.org/filesystems/proc.html, explains each line. L15 §3.1 says which victim frames cost no disk write.

Stretch, ungraded

LRU only reacts. However, you know the five program shapes from Step 3: a doubly nested loop will come back, and a straight line never will. Copy your pager to pager-predict.c and prefetch: track each process's branch behavior, and during idle paging capacity, page in what the structure says comes next. Build it the same way you built test-lru in Step 5, and let the simulator score it. Getting meaningfully under a good LRU is hard, which is the point. Start from your LRU, and first measure how often a process blocks on a page it has used before. That number bounds how much any predictor can win.

Watch the kernel page, then be the pager

This page walks you through Lab04 step by step. In this lab, you first watch how the kernel hands memory to a program, and then you decide yourself what stays in memory. In Part 1, touch.c measures how much memory a program really holds before and after it uses a 64 MiB region. In Part 2, you write the eviction policy of a simulator, and the simulator measures how long 20 processes wait for the disk. This page, the header comment of each file in labs/04-virtual-memory/submit/, and check/sim/simulator.h are the specification for this lab.

Step 1

touch.c, watching pages arrive

The goal of this step is to see how much memory a program really holds after malloc returns, and when that amount changes. touch.c allocates a 64 MiB region, measures itself, writes one byte into every page of the region, and measures itself again. It prints exactly three lines, RSS_KB_BEFORE=, RSS_KB_AFTER=, and FAULT_DELTA=, each followed by a whole number.

  1. On your laptop, read the header of touch.c.

    There are three TODOs, namely two readers, rss_kb() and faults(), and the loop in main. main already allocates the region and prints the three lines, so you write only the parts marked TODO.

  2. In the VM, look at the two values that the readers parse.

    grep VmRSS /proc/self/statusVmRSS: 1792 kBawk '{print $10 + $12}' /proc/self/stat119

    /proc/self is the /proc directory of whichever process reads it. Here that is grep or awk, and inside touch.c it is touch itself. The VmRSS: line gives the size of the resident setThe resident set of a process is the part of its memory that is in RAM right now. Its size is the resident set size, RSS. A process can own pages that are not in RAM, and Lecture 15 explains why. in kB. Fields 10 and 12 of the stat file together count the process's page faultsA page fault is a trap that the MMU raises when a program touches a page whose page-table entry is invalid. The kernel handles it in six steps, and then it restarts the instruction, which now finds the page. since the process started. Your numbers differ.

  3. Write rss_kb().

    Open /proc/self/status, find the line that starts with VmRSS:, and return its number. The number is already in kB. Return -1 if the file does not open or no line matches, and close the file before you return. Read fopen(3), fgets(3), and sscanf(3) first. fgets reads one line at a time. sscanf parses a string with a format, and its return value says how many values it parsed. proc_pid_status(5) describes every line of the file.

  4. Write faults().

    Open /proc/self/stat, and return field 10 plus field 12. Return -1 on failure. The stat file is one line of fields separated by spaces, and the header explains why splitting on spaces is safe for this program. Read fscanf(3), which reads from a file with the same formats as sscanf. The formats are described in sscanf(3), including how a conversion can read a field without storing it.

  1. Recompile, and run touch before you write the loop.

    gcc -Wall -Werror -O2 -o /tmp/touch submit/touch.c/tmp/touchRSS_KB_BEFORE=1024RSS_KB_AFTER=1280FAULT_DELTA=2

    Both readers now return positive numbers. However, nothing writes into the region yet, so AFTER is close to BEFORE, and FAULT_DELTA is small.

  2. Write the loop, recompile, and run touch again.

    Write one byte into every PAGE-sized chunk of region. That is 64 MiB / 4096 B = 16,384 writes. Your output should now look like Fig. 1.1.

What the symptom tells you

A value of -1. That reader failed to open the file or to parse it. Print the line it found. AFTER is close to BEFORE. The loop does not write into the region. RSS_KB_BEFORE is already about 65,000. Something touched the region before the first measurement.

Look deeper (ungraded). Transparent huge pages.

L14 §2.1 mentions that pages larger than 4 KB, called huge pages, also exist. Real Linux can back a large region like yours with huge pages of 2 MB on its own, which it calls transparent huge pages. The course VM turns them off when it boots, so that one page fault brings in one 4 KiB page, as in Lecture 15. Nothing in make check or the report uses this fold.

  1. In the VM, turn huge pages on, and run touch.

    echo always > /sys/kernel/mm/transparent_hugepage/enabled/tmp/touchRSS_KB_BEFORE=1024RSS_KB_AFTER=66740FAULT_DELTA=543

    The file under /sys/kernel/mm/ is a kernel setting, and you are root in the VM, so the write is allowed.

  2. Turn them off again, and run touch.

    echo never > /sys/kernel/mm/transparent_hugepage/enabled/tmp/touchRSS_KB_BEFORE=1024RSS_KB_AFTER=66816FAULT_DELTA=16384

    The same 64 MiB became resident in both runs, with about 30 times fewer faults when huge pages are on. A 64 MiB region holds only 32 pieces of 2 MB. The count is larger because the region that malloc returns does not start on a 2 MB boundary, so its two ends still fault in 4 KiB at a time.

Step 2

Meet the simulator

The goal of this step is to learn what the simulator models, what your pageit() can see and do, and how badly a simple policy scores. You build and run the baseline pager that comes with the simulator. There is no code to write in this step.

In Part 2, you play the part of the kernel's page-fault handler. The simulator runs 20 processes at the same time. Each process has an address space of 20 pages, and each page holds 128 instructions. The programs use between 4 and 15 of those pages, and all 20 processes share only 100 physical frames. Therefore, the processes together need about twice as many pages as fit in memory. On every tick, each process whose current page is in memory runs one instruction, and each process whose page is not in memory is blocked. Then the simulator calls your pageit(). To page inA page that is not in RAM lives in swap space, a disk area reserved as backing store. Paging in reads a page from there into a free frame. In this simulator every page out is a write to swap that takes 100 ticks, as if every victim were dirty (L15 §3.2). or page out one page takes 100 ticks. The score is the total number of blocked ticks divided by the total number of compute ticks. Lower is better.

  1. In the VM, build the simulator with the baseline pager.

    cd /sharegcc -Wall -Werror -O2 -Icheck/sim -o /tmp/test-basic \ check/sim/simulator.c check/sim/programs.c check/sim/pager-basic.c

    gcc compiles the three files and links them into one program. simulator.c is the simulator, programs.c holds the programs that the processes run, and pager-basic.c holds a pageit(). -Icheck/sim tells gcc to look for header files in check/sim as well, so that #include "simulator.h" finds the header. The backslash at the end of the first line continues the command on the next line.

  1. Run it with seed 1, and keep only the score.

    /tmp/test-basic -seed 1 2>&1 | grep ratio01713657: ratio blocked/compute=15.2964

    A run takes about 5 seconds. The simulator writes everything to stderr, not to stdout. 2>&1 sends stderr to the same place as stdout, so that the pipe hands it to grep. Each line starts with the tick at which it was written. The seed fixes every random choice in the run. Therefore, the same seed gives exactly the same run and the same ratio, every time.

  2. Run seeds 2 and 3, and look at a whole run once.

    /tmp/test-basic -seed 2 2>&1 | grep ratio/tmp/test-basic -seed 3 2>&1 | grep ratio/tmp/test-basic -seed 1

    The baseline scores about 15 on all three seeds, as Fig. 2.1 shows. Write the three ratios down, because report question 2 compares your pager with them. The flag -help lists the other flags, and Step 4 uses two of them.

  1. On your laptop, read check/sim/simulator.h, and check the interface below against it.

    pageit(Pentry q[MAXPROCESSES]) receives one entry per process slot, as the table below shows.

fieldmeaning
active1 if a process runs in this slot, 0 if the slot is empty
pcthe program counter. The page that the process needs now is pc / PAGESIZE.
npagesthe number of pages in the process's address space, 20 while it is active
pages[]1 if the page is in memory, 0 if it is not. A 0 covers three situations, namely out, going out, and coming in. The map alone cannot tell them apart.

You act through two functions, pagein(proc, page) and pageout(proc, page). Both return 1 if the operation starts, is already underway, or is already done. Both return 0 if it cannot start. pagein cannot start when no frame is free, or when the page is still going out. pageout cannot start when the page is still coming in. An operation completes 100 ticks after it starts, and a frame that a pageout frees is free only then. When pagein returns 0 because memory is full, your pager must choose a victimWhen no frame is free, a page fault needs page replacement. The kernel picks a victim page, writes it out if needed, marks it not present, and reads the wanted page into the freed frame. to page out.

  1. Read check/sim/pager-basic.c, and find out why it scores so badly.

    Read its loop. For one tick, count how many processes it can serve. Then check whether it ever frees a frame. The flag -page logs every pagein and pageout that a run starts, so grep on its output counts them. Report question 2 asks for this explanation.

  2. Read the five program shapes below.

    The simulator runs 40 processes in total, at most 20 at a time. It gives them the five shapes in turn, so each shape runs 8 times. A run n executes n instructions in a row.

1: loop w/ branch 2: one loop 3: doubly nested for 10 30 for 20 50 for 10 20 run 500 run 1129 run 1166 if .4 end for 10 20 run 900 exit run 516 else end run 131 4: linear end endif run 1911 exit end exit exit 5: probabilistic backward branch for 10 20 label: run 500 if .5 goto label end exit

Which branches fire, and how many iterations run, depend on the seed. Therefore, you can never predict one execution, only its shape. The shapes matter mostly for report question 3. For LRU, you need only one assumption, namely localityMost programs reuse the pages they referenced recently. Loops run through the same instructions again and again, and execution is mostly linear. Therefore, the recent past is a good guess about the near future, most of the time..

Step 3

Design your LRU

The goal of this step is to turn the LRULeast-recently-used replacement evicts the page that has gone unused for the longest time. It uses the past as a guess about the future, so it needs the time of last use of every page. policy into code. Your pageit() keeps the page that each active process needs in memory as often as it can. When it must evict, it evicts the least recently used page.

  1. On your laptop, open submit/pager-lru.c, and delete the placeholder.

    Delete the fprintf and exit lines, which only make the empty skeleton compile. Keep tick++ as the last thing the function does on every path. A return in the middle that skips it freezes your clock. The skeleton declares initialized, tick, and timestamps as static. A static variable inside a function keeps its value from one call to the next, so your pager remembers what it saw on earlier ticks.

  2. Decide how pageit() does each of the four jobs below, before you write it.

    Each call is one tick. On every tick, your function has four jobs.

jobthe question you must answer
1 · record useWhich (process, page) pairs are in use on this tick? The skeleton's timestamps array and tick counter store when each page was last usedOne way to implement exact LRU is to store the time of last use with every page. At replacement time, the page with the oldest time is the victim. A real kernel cannot afford this on every memory reference. Your pager runs once per tick, so it can..
2 · requestFor each active process whose needed page is not in memory, ask for it.
3 · make roomIf the request cannot start, choose a victim. It is the page in memory with the oldest timestamp (L16 §1.1). Never choose a page that some process needs right now.
4 · in flightA swap takes 100 ticks, and the page map cannot tell "going out" from "coming in" from "out". What stops your function from choosing the same victim again on the next tick? Does it matter?

  1. Write the four jobs, then go on to Step 4 to build and run your pager.

Step 4

Measure and iterate

The goal of this step is to score your pager the way make check does, and to improve it until it passes with margin. make check averages the ratios of seeds 1, 2, and 3, and the average must be below 1.28.

  1. In the VM, build the simulator with your pager.

    gcc -Wall -Werror -O2 -Icheck/sim -o /tmp/test-lru \ check/sim/simulator.c check/sim/programs.c submit/pager-lru.c

    Run it in /share. This is the build from Step 2, with your file in place of pager-basic.c. make check builds it with the same flags.

  2. Score seeds 1, 2, and 3.

    for s in 1 2 3; do /tmp/test-lru -seed $s 2>&1 | grep ratio; done

    The for loop runs the command once for each value of s, so it prints three ratio lines. A working LRU finishes each run in well under a second. Compute the average of the three ratios, and compare it with the table below.

  3. Run seed 1 twice, and check that the two ratios are identical.

    for i in 1 2; do /tmp/test-lru -seed 1 2>&1 | grep ratio; done

    The simulator is deterministic. Therefore, if the two lines differ, your pager is the cause.

The course that this lab comes from graded this ratio, averaged over several seeds, in the bands below.

What the symptom tells you

"pager-lru not yet implemented". The placeholder lines are still there. The run never ends. Stop it with Ctrl-C, namely press Control and c together. The simulator then prints the state of every page and exits. Rerun it with -dead. If it prints "All needed pages swapped out!" on every tick, then every process is waiting for a page that nobody brings in, and the simulator waits forever. Your function evicted without requesting, or requested nothing. Two runs with the same seed differ. The policy uses something that is not repeatable, such as rand(), the time, or an uninitialized variable. A score around 5 or more. Eviction barely works. Check that job 1 really updates the timestamps, and that job 3 picks the smallest one. It is merely slow. make check gives each run 120 seconds. Look for a loop inside pageit that keeps searching when no victim exists.

Look deeper (ungraded). Watch your policy think.

-block logs every time a process blocks and unblocks, and -page logs every pagein and pageout, each with its tick. Follow one process, for example the process in slot 3.

/tmp/test-lru -seed 1 -block -page 2>&1 | grep 'process= 3 ' | head -40

How long does it wait for each page? Does it wait for the same page over and over? The second pattern means that your policy evicts pages that come back soon. -csv writes the same events to output.csv and pages.csv in the current directory, for plotting. Run it from /tmp, so that the files stay out of your lab directory.

Stretch (ungraded). Replace LRU with clock.

Copy your pager to /tmp/pager-clock.c and replace LRU with the clock algorithm of L16 §3.2, treating the page each process needs on a tick as referenced. Build it the same way as test-lru, and compare its ratio with your LRU.

Step 6

The report

submit/report.md already holds three questions. Your answer replaces each (your answer) placeholder. Each item below tells you how to investigate, not what the answer is.

  1. Question 1. "Paste your touch.c numbers. malloc(64 MiB) returned success, so why was RSS_KB_BEFORE so small? Go through the six steps of a page fault in Lecture 15 and say what each of your ~16,000 page faults did and which step it did not need. If the kernel later evicted one of these pages and your program touched it again, where would its contents come from?"

    Paste your three numbers from Step 1, item 6. For "why so small", compare RSS just before and just after the loop, and read in L15 §0.3 when a page first gets a frame. Then follow one of your pages through the six steps in L15 §1.1. At each step, ask what the kernel had to do for a heap page that your program had never written before. The second checkpoint at the end of L15 Chapter 1 asks about the same kind of page. For the last part, L15 §1.2 says where an evicted page is written, and which kinds of pages go there.

  2. Question 2. "pager-basic scores ~15, and your LRU should score well under 1.28. Explain where the orders of magnitude come from, and how you chose your eviction victim."

    Put your three seeds and their average next to the baseline's three ratios from Step 2. Explain the gap from what pager-basic does with its processes and its frames, which you found in Step 2 item 5. Then describe how your pager chooses its victim.

  3. Question 3. "LRU bets that the recent past predicts the near future. Using one of the five simulated program structures (or a pattern of your own construction), show an access pattern where LRU's bet loses, namely where the page it evicts is precisely the one needed next."

    Pick a loop from the five program shapes in Step 2, or make one up. Write down the pages it references in order, and give LRU fewer frames than the loop has pages. Then simulate by hand, step by step, which page LRU evicts and which page the loop needs next. The simulator in L16 §1.2 accepts your own reference string and frame count, so you can check your hand simulation there.

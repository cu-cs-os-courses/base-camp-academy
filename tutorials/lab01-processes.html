Birth, family, death, and afterlife

Three small programs, one process life cycle. It never shows code for the lab files. Keep labs/01-processes/README.md and the header comment of each file open beside it: those are the specification.

Step 0

Set up the loop

Same loop as Lab00, now with a compiler in it. Edit on the laptop; compile and run in the VM.

# laptop, repository rootSHARE=$PWD/labs/01-processes/submit env/run.sh# VMcd /sharegcc -Wall -Werror -O2 -o /tmp/spawn spawn.c # the exact flags make check usesgcc -Wall -Werror -O2 -o /tmp/undead undead.cbash ptree.sh $$
  • Put binaries in /tmp, not in /share. They are build products, not something to commit.
  • Compile with -O2 as well as -Wall -Werror. Some warnings (an uninitialized variable, for example) appear only when optimizing, and the checker optimizes.
  • Before you have written anything, both C programs compile and print nothing, and ptree.sh prints nothing. That is the starting point, not a bug.
Step 1

Read a status file by hand

Before scripting anything, find with your own eyes the three values ptree.sh has to print.

echo $$ # your shell's PIDhead -8 /proc/$$/status # your shell's status file

Find three lines, Name:, State: and PPid:, and note exactly what ptree.sh has to print from each:

linewhat the file showswhat ptree.sh prints
Name:the command nameit, unchanged (COMM)
State:a letter and a word in parenthesesonly the capital letter (STATE)
PPid:the parent's PIDit, unchanged (PPID); it is also the next PID to visit

Now follow the chain by hand: take the PPid: value, open that process's status file, and repeat until you reach PID 1. Write the chain down. That is exactly what ptree.sh automates, and your hand-written chain is what you will check it against.

A technique you already have

Lab00 Step 3 showed how to print one field of the line that begins with a given key. The same technique works here. Look at the State line: which field is the letter?

Step 2

ptree.sh: the family tree

Goal: given a PID, print one line for it and one for each ancestor, up to and including PID 1, each exactly <PID> <COMM> <STATE> <PPID>.

Plan it in words before you write it. The loop keeps a "current PID", and each pass does three things:

  1. read the three values for the current PID from its status file;
  2. print the line;
  3. decide: if the current PID is 1, stop; otherwise the parent becomes the current PID.

Get one pass right first: make the script print only the first line, run it on $$, and compare with your notes from Step 1. Then add the loop.

How to check it yourself

trywhat must be true
bash ptree.sh $$It matches the chain you wrote by hand in Step 1.
the last lineIt is PID 1's line, its PPID is 0, and nothing is printed after it.
every lineExactly four fields, and the 4th field of each line equals the 1st field of the next.
sleep 60 &
bash ptree.sh $!		The first line is the sleep, in state S, with your shell as its parent. make check runs exactly this test.
the README's nested bash -cRun it, find the innermost sleep's PID, and walk its chain. Which ancestors did you not expect?
What the symptom tells you

An error mentioning /proc/0: the loop did not stop after PID 1; there is no process 0 to visit. STATE shows S (sleeping) or (sleeping): you printed the wrong part of the line. no-ps fails though you never ran ps: the check looks for the word ps anywhere outside comments, so a variable named ps trips it too.

Step 3

spawn.c: fork, exec, wait

Goal: spawn <program> [args…] runs the program in a child, then prints exactly CHILD <pid> EXITED <status>.

The file has three TODOs, one per system call. What each must do, and what to read first:

TODOwhat it must doread first
1 · forkCreate the child. After the call, two processes run the same code; the return value is how each one knows which it is.man 2 fork, section RETURN VALUE: three cases.
2 · exec (child)Replace the child with the program argv[1], handing it &argv[1] as its argument vector. If exec returns at all, it failed: leave with status 127.man 3 execv: what the second argument must look like, and why &argv[1] already has that shape.
3 · wait (parent)Wait for that child, decode the status, print the line.man 2 waitpid: WIFEXITED, WEXITSTATUS.

How to check it yourself. These four runs are the contract, and they are exactly what make check runs:

/tmp/spawn /bin/true # CHILD <pid> EXITED 0/tmp/spawn /bin/false # CHILD <pid> EXITED 1/tmp/spawn /bin/echo hello # hello, and only then the CHILD line/tmp/spawn /no/such/program # CHILD <pid> EXITED 127/nonexistent; echo $? # the shell's own convention, for comparison
What the symptom tells you

Status 256 instead of 1: you printed the raw status word without decoding it. Two CHILD lines for a missing program: after exec failed, the child kept going and ran the parent's code too. Some status other than 127 for a missing program: the failure path is not exiting with 127. hello is missing: look again at what you passed as the argument vector.

Why does the TODO say _exit, not exit?

Think about what fork copies, including any unwritten output sitting in the parent's stdio buffer. Then read what exit(3) does that _exit(2) does not. It is the same buffering problem you will meet in Step 4.

Step 4

undead zombie

Goal: a child that is dead for 10 seconds but not yet gone, and is then reaped.

The required timeline, from the file header:

whodoes what, in order
childexits at once with status 42
parentprints CHILD <the child's pid> → flushes stdout → sleeps 10 s without waiting → waits → prints REAPED <pid> STATUS <decoded status>

How to check it yourself. Send stdout to a file: that is what the checker does, and it is the case where a missing flush shows up.

/tmp/undead zombie > /tmp/z.out &cat /tmp/z.out # right away: the CHILD line must already be therecat /proc/<that pid>/stat # during the 10 s, the third field is Zps -o pid,ppid,stat,comm -p <that pid> # ps is fine here, in the terminalsleep 10; cat /tmp/z.out # now also REAPED <pid> STATUS 42ls /proc/<that pid> # after reaping: No such file or directory
What the symptom tells you

/tmp/z.out stays empty for 10 seconds, then everything appears at once: the output sat in the stdio buffer; the flush must come before the sleep. The state is never Z: either the parent waits before it sleeps, or the child does not exit at once. STATUS 10752: the raw status word again, as in Step 3.

Step 5

undead orphan

Goal: the parent dies first; the child lives on and gets a new parent.

whodoes what
parentexits immediately, without waiting
childprints CHILD <its own pid> → flushes stdout → sleeps 10 s

Note who prints this time: the child, and it prints its own PID, so the number comes from a different place than in the zombie act. Where? man 2 getpid.

/tmp/undead orphan > /tmp/o.out # returns at once: the parent is gonecat /tmp/o.outgrep PPid /proc/<that pid>/status # within 10 s: who is the parent now?bash /share/ptree.sh <that pid> # your own tool, on your own orphan
What make check expects

orphan-ppid1 reads the sleeping child's PPid: and expects it to become 1. If yours shows something else, first check that the parent really exits at once, and that you read the PPid within the 10 seconds.

Step 7

Report and submit

submit/report.md already holds three questions. Each asks what your code made observable, so answer from an experiment you ran. How to investigate, not the answers:

  1. The zombie's purpose. During the 10 seconds, compare the zombie's /proc/<pid>/status with a live process's: what is still there, and what is missing? Then ask what the parent gets from wait that it could get no other way.
  2. What exec throws away. Pick properties to test: the PID, the parent, the current directory, the open files, the command line, the program's memory. For each, design a probe with spawn, such as /tmp/spawn /bin/cat /proc/self/<some file>, and compare with what the process had before exec. Report only what you actually showed.
  3. The adoption. Your Step 5 output answers the first half. For the second half, find out what the kernel does with an orphan: man 2 prctl, and search for "orphan".

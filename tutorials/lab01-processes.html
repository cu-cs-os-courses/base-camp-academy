Birth, family, death, and afterlife

This page walks you through Lab01 step by step. In this lab, you follow one process through its whole life. It is born with fork and exec. It has a family, namely its parent and the process tree. Finally, it dies, and its parent collects its exit status, which brings in zombies and orphans. This page and the header comment of each file in labs/01-processes/submit/ are the specification for this lab.

Step 1

Read a status file by hand

The goal of this step is to learn to read a process's status file, /proc/<pid>/status. This file is where the kernel shows a process's name, state, and parent. Before you write any script, you find the three values that ptree.sh has to print, by hand. Work in the VM.

  1. Print your shell's PID.

    echo $$

    The shell replaces $$ with its own PID. The shell is a process like any other, so it has a directory under /proc.

  2. Read the first lines of your shell's status file.

    head -8 /proc/$$/status

    Find three lines in the output, and note what ptree.sh has to print from each.

    linewhat the file showswhat ptree.sh prints
    Name:the command name, here bashthe name, unchanged (COMM)
    State:a letter and a word in parentheses, here S (sleeping)only the capital letter (STATE)
    PPid:the PID of the parentEvery process except PID 1 is created by another process, its parent. The new process is the parent's child. Each child has exactly one parent. As such, following parents from any process leads up the process tree to PID 1, its root.the number, unchanged (PPID), which is also the next PID to visit

    Your shell is in stateThe lecture names five states, namely new, ready, running, waiting, and terminated. Linux shows a state as a letter. S (sleeping) is the waiting state, for example waiting for a timer or a key press. Z (zombie) is a process that has terminated, but whose parent has not yet called wait() (Step 4). S, because it is waiting for head to finish.

  3. Follow the chain by hand up to PID 1.

    grep PPid /proc/$$/statushead -8 /proc/<that PPid>/status # the parent; repeat with its PPid

    Repeat until you reach PID 1, and write down each PID, Name, State, and PPid. The last process is systemd, the PID1_COMM you found in Lab00. ptree.sh automates exactly this walk, and you will check it against your notes.

A technique you already have

Lab00 Step 3 showed how to print one field of the line that begins with a given key. The same technique works here. Look at the State line, and find which field is the letter.

Step 2

ptree.sh, the family tree

The goal of this step is to print the process tree from one process up to its root. The tree starts with the process itself, then the process that started it, then the process that started that one, and so on up to PID 1. ptree.sh automates the walk you did by hand in Step 1. Given a PID, it prints one line for the process and one for each ancestor, each exactly <PID> <COMM> <STATE> <PPID>.

  1. On your laptop, read the header of ptree.sh.

    It gives the output format, which the checks compare exactly. It also gives the one rule. Read only /proc/<pid>/status, and do not call ps or pstree.

  2. Plan the loop in words.

    The loop keeps a "current PID", which starts as the argument. Each pass does three things. First, it reads the three values for the current PID from its status file. Second, it prints the line. Third, it stops if the current PID is 1. Otherwise, the parent becomes the current PID.

  3. On your laptop, write one pass only, without the loop. In the VM, run it on your shell.

    bash /share/ptree.sh $$

    It prints one line. Compare it with the first line of your notes from Step 1. Getting one line exactly right first is easier than debugging the whole loop.

  4. On your laptop, add the loop. In the VM, run the same command again.

    Now the output matches the whole chain from Step 1. The last line is 1 systemd S 0, and nothing is printed after it. In every line, the 4th field equals the 1st field of the next line.

  5. In the VM, run ptree.sh on a process you started.

    sleep 60 &bash /share/ptree.sh $!

    The & starts sleep in the background, so the prompt returns at once. The shell replaces $! with the PID of the process it last started in the background. Therefore, the first line is the sleep, <its PID> sleep S <your shell's PID>. It is in state S because it is waiting for a timer. make check runs exactly this test.

What the symptom tells you

An error that mentions /proc/0. The loop did not stop after PID 1, and there is no process 0. STATE shows S (sleeping) or (sleeping). You printed the wrong field of the State line. no-ps fails although you never ran ps. The check looks for the word ps anywhere outside comments, so a variable named ps also fails it.

Step 3

spawn.c, with fork, exec, and wait

The goal of this step is to learn how a new process is created and starts a new program, which is what a shell does for every command you type. spawn <program> [args…] runs the program in a child, then prints exactly CHILD <pid> EXITED <status>.

A shell runs every command you type with three system callsA system call is how a program asks the kernel to do something it cannot do itself, such as create a process. In C, you call it like an ordinary function, and the C library passes the request to the kernel.. spawn.c is a shell that runs one command. Each of its three TODOs is one of these calls.

  1. On your laptop, read the header of spawn.c.

    It gives the one line that spawn prints. It also gives one more rule. If the program cannot be run, the child exits with status 127.

  2. In the VM, see where 127 comes from. Ask the shell to run a program that does not exist.

    /nonexistent; echo $?-bash: /nonexistent: No such file or directory127

    The ; separates two commands, which run one after the other. First, the shell tries to run /nonexistent. It cannot, so it prints an error, and it gives the command the exit status 127. Second, echo $? prints that status, because the shell replaces $? with the exit status of the last command. As such, 127 is the shell's convention for "command not found". spawn follows the same convention.

  3. TODO 1. Create the child with forkfork() creates a new process that is a copy of the caller. Both processes continue from the same point, just after fork() returns. However, the return value differs. The child gets 0, and the parent gets the child's PID. A return value of −1 means the call failed..

    Read fork(2), section RETURN VALUE. It lists three cases, and your code needs a branch for each. To see the two returns, temporarily add printf("pid %d\n", getpid()); right after the call, then compile and run /tmp/spawn /bin/true. The line appears twice, with two different PIDs. Delete the line before you go on.

  4. TODO 2. In the child, replace the program with execThe exec family loads a new program into the calling process. The old program's code is gone, so a successful exec never returns. If it returns at all, it failed..

    Read exec(3), and find what the second argument of execv must look like. Then work out why &argv[1] already has that shape. If execv returns, the child must leave with status 127, as the header says.

  5. TODO 3. In the parent, waitA process ends with exit(), and its exit status goes to its parent. The parent collects it with wait(), or with waitpid() for one particular child. Until the parent collects it, the kernel keeps the status. for the child, and print the line.

    Read wait(2), which also documents waitpid. Note that the status that waitpid fills in is not the exit status itself. It packs the exit status together with other information, and the macros WIFEXITED and WEXITSTATUS unpack it.

  6. In the VM, compile, and run the four contract runs.

    gcc -Wall -Werror -O2 -o /tmp/spawn spawn.c/tmp/spawn /bin/true # CHILD <pid> EXITED 0/tmp/spawn /bin/false # CHILD <pid> EXITED 1/tmp/spawn /bin/echo hello # hello, and only then the CHILD line/tmp/spawn /no/such/program # CHILD <pid> EXITED 127

    make check runs exactly these four. Note that hello must appear before the CHILD line. Ask yourself why that order is guaranteed, given that the parent waits.

What the symptom tells you

Status 256 instead of 1. You printed the packed status without unpacking it. Two CHILD lines for a missing program. After exec failed, the child kept going and ran the parent's code too. A status other than 127 for a missing program. The failure path does not exit with 127. hello is missing. Look again at what you passed as the argument vector.

Step 4

undead zombie

The goal of this step is to see what remains of a process after it dies, and why. undead zombie makes a child that has died but stays visible for 10 seconds, until its parent collects it.

  1. On your laptop, read the zombie part of the header of undead.c.

    It gives the timeline below.

    whodoes what, in order
    childexits at once with status 42
    parentprints CHILD <the child's pid> → flushes stdout → sleeps 10 s without waiting → waits → prints REAPED <pid> STATUS <decoded status>

    During the 10 seconds, the child is a zombieA zombie is a child that has terminated, but whose parent has not yet called wait(). The kernel has freed most of it. However, it keeps an entry for it, so that the parent can still collect the exit status. Its state is Z.. Waiting and decoding work as in Step 3.

  2. Write the zombie part, and flush before you sleep.

Buffering

printf does not write to the output right away. It puts the text into a buffer in your process's memory. The C library writes the buffer out when it is full, when the process exits, or when you call fflush(stdout). On a terminal, a newline also writes it out. In a file, which is where the checker sends your output, a newline does not. Therefore, without fflush, the CHILD line reaches the file only when the process exits, 10 seconds too late for anyone watching. Recitation 03, Part 1, shows the same buffer copied by fork.

  1. In the VM, compile, and run the zombie act in the background, with its output in a file.

    gcc -Wall -Werror -O2 -o /tmp/undead undead.c/tmp/undead zombie > /tmp/z.out &cat /tmp/z.out # CHILD <pid>, right away

    The output goes to a file because that is what the checker does, and it is the case in which a missing flush shows up. The CHILD line must be there at once. If the file is still empty, go back to the Buffering note.

  2. Within the 10 seconds, look at the child from outside.

    grep State /proc/<that pid>/status # State: Z (zombie)ps -o pid,ppid,stat,comm -p <that pid> # STAT is Z

    The child has exited. However, its directory under /proc still exists, because the parent has not collected it yet. You may use ps here at the prompt. Only ptree.sh must not use it.

  3. Wait for the program to finish, and look again.

    wait # returns when the 10 s are overcat /tmp/z.out # now also REAPED <pid> STATUS 42ls /proc/<that pid> # No such file or directory

    The shell's wait waits for your background job, as your C code waits for its child. After the parent collected the status, the kernel removed the child for good, and its directory is gone.

What the symptom tells you

/tmp/z.out stays empty for 10 seconds, then everything appears at once. The output sat in the buffer, so the flush must come before the sleep. The state is never Z. Either the parent waits before it sleeps, or the child does not exit at once. STATUS 10752. The packed status again, as in Step 3.

Step 5

undead orphan

The goal of this step is to see what happens to a child when its parent dies first. undead orphan makes such a child, and you find its new parent with ptree.sh.

  1. On your laptop, read the orphan part of the header of undead.c.

    whodoes what
    parentexits at once, without waiting
    childprints CHILD <its own pid> → flushes stdout → sleeps 10 s

    Note that the child prints this time, and it prints its own PID. Therefore, the number comes from a different place than in the zombie act. See getpid(2). The flush rule from Step 4 applies here too.

  2. In the VM, compile, and run the orphan act.

    gcc -Wall -Werror -O2 -o /tmp/undead undead.c/tmp/undead orphan > /tmp/o.out # the prompt returns at oncecat /tmp/o.out # CHILD <pid>

    The prompt returns at once, because the shell waits only for the parent, and the parent is already gone. The child is still sleeping. It is now an orphanAn orphan is a child whose parent terminated without waiting for it. The kernel gives it a new parent, so that someone will still collect its exit status when it ends..

  3. Within the 10 seconds, find out who the parent is now.

    grep PPid /proc/<that pid>/statusbash /share/ptree.sh <that pid> # your own tool, on your own orphan

    The parent that started the child no longer exists. Compare the new PPid with your chain from Step 1. make check expects this PPid to be 1.

If the PPid is not 1

First, check that the parent really exits at once. Second, check that you read the PPid within the 10 seconds, while the child is still alive.

Step 7

The report

submit/report.md already holds three questions. Each asks what your programs made observable, so answer each one from an experiment you ran. Each item below tells you how to investigate, not what the answer is.

  1. Question 1. "In undead zombie, the child is dead for 10 seconds but still has an entry in /proc. What is the kernel keeping alive, and for whom? What single line of parent code makes it disappear?"

    Run the zombie act as in Step 4. During the 10 seconds, compare the zombie's status file with a live process's status file.

    cat /proc/<zombie pid>/statuscat /proc/$$/status # a live process, your shell

    Ask what is still there and what is missing. Then reread the zombie card in Step 4, and ask what the parent gets from wait that it could get no other way.

  2. Question 2. "Run /tmp/spawn /bin/sleep 20 in the background, read /proc/<pid>/status of the sleeping child from your shell, and compare its Name, Pid and PPid lines with the CHILD line that spawn prints when the sleep ends. Using L03 §1.4, say what exec replaced and which values it kept, and why."

    spawn waits for its child, so start it in the background with &. Then $! is spawn's PID, and ps --ppid lists spawn's children, as in Recitation 03, Part 3.

    /tmp/spawn /bin/sleep 20 &ps -o pid,ppid,stat,comm --ppid $! # the sleeping child, with its PIDhead -8 /proc/<that pid>/statuswait # the CHILD line, when the sleep ends

    Right after fork, the child was a copy of spawn. For each of the three lines, ask whether it would have looked the same before exec. Then reread L03 §1.4 and the exec card in Step 3.

  3. Question 3. "Who adopted your orphan, and which two observations from your own run show it? According to L03 §2.2, would the adopter change if PID 1 ran a program other than systemd?"

    Step 5, item 3, looked at the orphan in two ways. Write down what each one printed. For the second part, reread the orphan rule in L03 §2.2, and decide whether it names a program or a PID.

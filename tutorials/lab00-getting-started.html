From zero to a running kernel

This page walks you through Lab00 step by step. For each step, it describes what to do, how to tell whether it worked, and what usually goes wrong. Note that this page does not do the lab for you. It never shows code for observe.sh, and it never names the file that holds an answer. Instead, it shows you how to search and how to check your own work. Keep labs/00-getting-started/README.md from your repository open alongside this page. The README is the specification, and this page is the map.

Step 0

Get your repository

You work in your own private copy of the course repository. That copy is what we grade.

  1. On GitHub, create a new private repository named 3753-27-spring-<identikey>, where <identikey> is your CU IdentiKey. Leave it empty: no README, no .gitignore, and no license.
  2. Clone the course repository, and make your private repository the place you push to:
git clone https://github.com/cu-cs-os-courses/3753-27-springcd 3753-27-springgit remote rename origin upstreamgit remote add origin https://github.com/<your-username>/3753-27-spring-<identikey>.gitgit push -u origin maingit remote -v # check: origin = your repository, upstream = the course
  1. In your repository, open Settings → Collaborators → Add people, and add chenyueqi, the instructor. Grading clones your repository with this account. Without it, your work cannot be graded.

When a new lab is released, run git pull upstream main and then git push. A release adds files under labs/ and never touches your submit/ directories.

Common mistakes

Forking the course repository instead of creating a new one. A fork of a public repository cannot be private, and a public repository exposes your graded work to everyone. Pushing to upstream instead of origin also fails, because you cannot write to the course repository. If git remote -v does not show your own repository as origin, fix the remotes before you continue.

Step 1

Build and boot the VM

Start this step on the day the lab opens. The first build takes 30–60 minutes.

cd envmake setup # once; macOS (on Ubuntu: scripts/host-setup-ubuntu.sh)make images # 30–60 min the first timemake smoke # should end with every check passingmake run # boots to a root prompt; leave with Ctrl-a x

How to tell that it worked: Inside the VM, cat /proc/version prints a line that starts with Linux version 6.6.87.

Step 2

The edit–run loop

Edit on your laptop with your usual editor, and run inside the VM. Every lab follows this loop.

# laptop, repository rootSHARE=$PWD/labs/00-getting-started/submit env/run.sh# VMls /share # your submit/ directory, livebash /share/observe.sh
  • The share is live. Save the file on your laptop and rerun it in the VM. No reboot is needed.
  • At first, every line prints an empty value, because each $( : TODO ) does nothing. This is expected. Fill in one TODO at a time, and rerun the script after each one.
Step 3

Tools for reading /proc

Every fact is text in a file. First, find the file. Second, cut out exactly one value.

Finding the file. man 5 proc documents /proc. In the man page, press / to search for a word, and press n to jump to the next match. To find which files mention a word, run grep -l over a set of files. For example:

grep -l -i swap /proc/* 2>/dev/null # which top-level files mention "swap"?man 5 proc # then /swap, n, n, ...

Cutting out a value. The examples below use files that the lab does not ask about. However, the same patterns apply to the lab's files:

cat /proc/sys/vm/swappiness # a whole file that is one valueawk '{print $1}' /proc/loadavg # field 1 of a one-line fileawk '/^Threads:/ {print $2}' /proc/self/status # field 2 of the line starting "Threads:"grep -c '^Vm' /proc/self/status # count the lines that matchls /proc | wc -l # count directory entriesreadlink /proc/1/exe # where a symbolic link points
The output contract

Each line must be exactly KEY=VALUE, with no spaces, no units, and no trailing text. Note that echo "KEY=$(command)" prints whatever the command prints. Therefore, make sure the command prints only the value.

Step 4

The eight facts, one at a time

For each fact, the table below lists exactly what you are looking for, how to search for it, and how to check your answer. Some checks use tools that are not allowed in the script, but you can still type them in the terminal.

factwhat you are afterhow to look for itcheck it with
KERNEL_RELEASEThe release string of the running kernel, like 6.6.87.This is one system-wide value. Search man 5 proc for "release," and read which file it names.uname -r
NPROCThe number of CPUs the kernel is using, as a single number.Find the /proc file that describes the CPUs, with one entry per CPU. Then turn the entries into a count.nproc
PID1_COMMThe command name of process 1, the first process the kernel starts.man 5 proc lists the files inside each process's directory. Find the file that holds only the command name.ps -p 1 -o comm=
MEM_TOTAL_KBTotal usable RAM in kB, as a bare number.Find the /proc file that reports memory, then the line for the total.free -k, "total" column
BOOT_CMDLINEThe parameters the kernel was booted with, exactly as passed.Search man 5 proc for "command line." Make sure you pick the kernel's command line, not a process's.The -append line in env/run.sh
SELF_PIDThe PID of the process that reads /proc/self./proc/self is a symbolic link. Work out what it points to, and extract the PID from the target.Run the script twice. The value changes between runs, and it is never 1.
CTXTThe total number of context switches since boot, as one number.The header names the file. man 5 proc explains each of its lines. Find the line for context switches.Read it twice, a few seconds apart. The value only grows.
NUM_PROCSThe number of processes that exist right now.Every process is a directory whose name is all digits, and no other entry in /proc has such a name. Count only those names.ps aux | wc -l (this includes one header line, so a roughly equal count is correct)
Rules the checks enforce

The script must not contain uname or nproc anywhere, even inside a command substitution, because a check searches for those words. Further, SELF_PID must come from /proc/self, not from the shell's $$, because a check searches your script for /proc/self.

Step 5

make check, and reading a failure

# laptop, repository rootmake check LAB=00-getting-started
  • make check boots a fresh VM without a console and runs your script there. It prints one PASS or FAIL per check, followed by a RESULT line. Grading runs the same checks.
  • Each check name maps to a fact: kernel-release, nproc, pid1-comm, mem-total, boot-cmdline, self-pid, ctxt, num-procs, plus the rule checks no-uname, no-nproc, and uses-proc-self.
  • A FAIL names the check but does not show your output. To debug, go back to Step 2, run the script in a live VM, and compare the failing line with the format in the file header.
  • A failed run prints (artifacts kept at …). In that directory, result.txt holds the raw check output, and console.log holds the VM's boot log. If the VM never came up, look at console.log.
Step 6

The report

Create submit/report.md, and answer the two questions in the README in your own words. The hints below describe how to investigate, not the answers:

  1. What changed between two runs, and what is /proc/self? Run the script twice, and compare the output line by line. Then run ls -l /proc/self twice. Ask yourself which process reads /proc/self each time.
  2. MemFree vs MemAvailable. Read both lines of /proc/meminfo, and then read what man 5 proc says about each. Consider what the kernel keeps in memory that it could give back.

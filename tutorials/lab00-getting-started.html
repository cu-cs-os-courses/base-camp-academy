From zero to a running kernel

This page walks you through Lab00 step by step. For each step, it describes what to do, how to tell whether it worked, and what usually goes wrong. Note that this page does not do the lab for you. It never shows code for observe.sh, and it never names the file that holds an answer. Instead, it shows you how to search and how to check your own work. This page and the header of submit/observe.sh are the specification for this lab.

Step 0

Get your repository

You work in your own private copy of the course repository. That copy is what we grade.

  1. On GitHub, create a new private repository named 3753-27-spring-<identikey>, where <identikey> is your CU IdentiKey. Leave it empty: no README, no .gitignore, and no license.
  2. Clone the course repository, and make your private repository the place you push to:
git clone https://github.com/cu-cs-os-courses/3753-27-springcd 3753-27-springgit remote rename origin upstreamgit remote add origin https://github.com/<your-username>/3753-27-spring-<identikey>.gitgit push -u origin maingit remote -v # check: origin = your repository, upstream = the course
  1. In your repository, open Settings → Collaborators → Add people, and add chenyueqi, the instructor. Grading clones your repository with this account. Without it, your work cannot be graded.

Do all three before the Lab00 deadline.

When a new lab is released, run git pull upstream main and then git push. A release adds files under labs/ and never touches your submit/ directories.

Common mistakes

Forking the course repository instead of creating a new one. A fork of a public repository cannot be private, and a public repository exposes your graded work to everyone. Pushing to upstream instead of origin also fails, because you cannot write to the course repository. If git remote -v does not show your own repository as origin, fix the remotes before you continue.

Step 1

Build and boot the VM

Start this step on the day the lab opens. The first build takes 30–60 minutes.

The whole environment builds and runs on your laptop. There is no VDI and no shared server. Before you start, you need:

  • a laptop running macOS (Apple Silicon or Intel) or Linux, with about 20 GB of free disk (kernel build cache, a 4 GB disk image, and Docker images) and 8 GB of RAM;
  • on macOS, Homebrew, which make setup uses to install QEMU and Docker;
  • a GitHub account (Step 0).

Then run, from the repository root (env/README.md explains each target):

cd envmake setup # once; macOS (on Ubuntu: scripts/host-setup-ubuntu.sh)make images # 30–60 min the first timemake smoke # should end with every check passingmake run # boots to a root prompt; leave with Ctrl-a x

How to tell that it worked: Inside the VM, cat /proc/version prints a line that starts with Linux version 6.6.87.

How to leave the VM: Press Control and a together, release both, and then press x. On a Mac, this is the Control key, not Command. Alternatively, type poweroff inside the VM.

Step 2

The edit–run loop

You edit files on your laptop and run them inside the VM. Follow these steps once now. Every later lab uses the same loop.

  1. On your laptop, open a terminal and go to the root of your repository.

    cd 3753-27-spring # wherever you cloned it in Step 0

    The next command builds a path from $PWD, the directory you are in. Therefore, it only works from the repository root.

  2. Boot the VM, and share your lab's submit/ directory with it.

    SHARE=$PWD/labs/00-getting-started/submit env/run.sh

    This is the same VM that make run booted in Step 1. The only difference is SHARE: it names a directory on your laptop, and the VM mounts that directory at /share. When the boot finishes, you are at a root prompt inside the VM. Note that this terminal now belongs to the VM, so keep it open.

  3. In the VM, list the shared directory.

    ls /share # prints: observe.sh

    /share is not a copy. It is the same directory as labs/00-getting-started/submit on your laptop, seen from inside the VM.

  4. In the VM, run the script.

    bash /share/observe.sh

    You see eight lines, from KERNEL_RELEASE= to NUM_PROCS=, and every value is empty. This is expected. Each value comes from $(: TODO), and : is the shell's do-nothing command, so the substitution produces nothing.

  5. On your laptop, open labs/00-getting-started/submit/observe.sh in your editor, add echo hello as the last line, and save.

    Use your usual editor, or a second terminal. The first terminal still belongs to the VM.

  6. In the VM, run the script again.

    bash /share/observe.sh # the last line is now: hello

    You did not reboot the VM or copy any file. The VM reads the file directly from your laptop, so every save is visible immediately.

  7. On your laptop, delete the echo hello line, and save.

    The script must print only the eight lines in the format given in the header of observe.sh.

This is the loop for the rest of the lab: fill in one TODO on your laptop, save, and rerun the script in the VM. Step 3 and Step 4 tell you how to find each value. When you are done, leave the VM with Control-a, then x (Step 1).

Step 3

Tools for reading /proc

Every fact is text in a file. In this step, you practice the two skills the lab needs: finding the file, and cutting out exactly one value. Work in the VM from Step 2.

  1. In the VM, look around /proc.

    ls /proc # files, and one directory per processcat /proc/versionls /proc/1/cat /proc/meminfo | headgrep . /proc/sys/kernel/* # everything here greps like an ordinary file

    /proc is the kernel's window onto itself. Each numbered directory is one running processA process is a program in execution. The program is a file on disk. Each time you run it, the kernel creates a new process for it. Therefore, every program you start, such as cat or ls, runs as a new process., named by its PIDThe kernel gives each new process a number, its process identifier (PID). Two processes that exist at the same time never share a PID. Therefore, if you run the same program twice, you get two different PIDs.. The eight facts in observe.sh make you look at four different faces of /proc. First, system-wide constants: the kernel release, the CPUs, and memory. Second, the boot command line, which you can compare with env/run.sh. Third, per-process views: /proc/<pid>/, and /proc/self, which answers "who is asking?" Fourth, live counters that change every time you look (/proc/stat).

  2. Find which files mention a word.

    grep -l -i swap /proc/* 2>/dev/null

    -l prints only the names of the files that match, and -i ignores case. 2>/dev/null hides the error messages for directories and for files you are not allowed to read.

  3. Practice cutting out one value.

    Run each command below. Then run cat on the same file, and compare. These files are not ones the lab asks about. However, the same patterns apply to the lab's files.

    cat /proc/sys/vm/swappiness # a whole file that is one valueawk '{print $1}' /proc/loadavg # field 1 of a one-line fileawk '/^Threads:/ {print $2}' /proc/self/status # field 2 of the line that starts with "Threads:"grep -c '^Vm' /proc/self/status # count the lines that matchls /proc | wc -l # count directory entriesreadlink /proc/1/exe # where a symbolic link points

    awk splits each line into fields at spaces, and $1 is the first field. A pattern between slashes, such as /^Threads:/, keeps only the lines that match it.

  4. On your laptop, read the header of observe.sh.

    It gives the output format, which the checks compare exactly. Each line must be KEY=VALUE, with no spaces, no units, and no trailing text. Note that echo "KEY=$(command)" prints whatever the command prints. Therefore, make sure each command prints only the value.

Step 4

The eight facts, one at a time

Fill in the eight TODOs in order. For each fact, repeat the five steps below. The table after them says what each fact is, where to start looking, and how to check it.

  1. Read the fact's row in the table below.

    The second column says exactly what value you are after. The third column says how to search for it, not where it is.

  2. In the VM, find the file, and try commands at the prompt until one prints exactly the value.

    Use the search tools and the patterns from Step 3. Trying commands at the prompt is faster than editing the script for every attempt.

  3. In the VM, check the value with the tool in the last column.

    These tools, such as uname and nproc, compute the same value in another way. You may type them at the prompt. However, you may not use them in the script (step 6 below).

  4. On your laptop, put the command into the fact's TODO, and save.

    Replace only : TODO inside $( ), so that the line keeps the form echo "KEY=$(command)".

  5. In the VM, rerun the script, and check that line.

    bash /share/observe.sh

    The line for this fact now shows its value. Then go to the next fact.

When all eight lines show values, do one last check on your laptop:

  1. Make sure that the script never uses uname or nproc, and that SELF_PID comes from /proc/self.

    A check searches your script for the words uname and nproc, even inside a command substitution. It ignores comments. Another check searches for /proc/self, so SELF_PID cannot come from the shell's $$. The point of the lab is to read each fact where the kernel itself exposes it.

Step 5

make check, and reading a failure

make check runs the same checks that grading runs. Therefore, a pass on your laptop is a pass in grading.

  1. On your laptop, at the repository root, run the checks.

    make check LAB=00-getting-started

    It boots a fresh VM without a console, runs your script inside it, and powers the VM off. This takes a few minutes, especially on Apple Silicon. Then it prints one PASS or FAIL line per check, and a last line that starts with RESULT.

  2. Read the result.

    If every check passes, the last line ends with status=pass passes=14 fails=0. The 14 checks fall into three groups:

    • boot, proc-mounted, and tracefs check the VM, not your script. If one of them fails, the environment is broken: go back to the table in Step 1.
    • no-uname, no-nproc, and uses-proc-self check the rules from Step 4.
    • kernel-release, nproc, pid1-comm, mem-total, boot-cmdline, self-pid, ctxt, and num-procs check one fact each.

  3. If a check fails, look at your output in a live VM.

    A FAIL line names the check, but it does not show what your script printed. Therefore, boot the VM as in Step 2, run bash /share/observe.sh, and compare the failing line with the format in the header of observe.sh. Fix the script, leave the VM, and run make check again.

    A failed run also prints (artifacts kept at …). In that directory, result.txt holds the raw check output, and console.log holds the VM's boot log. If the VM never came up, look at console.log.

Step 6

The report

The report answers three questions in your own words. Each step below tells you how to investigate, not what the answer is.

  1. On your laptop, create labs/00-getting-started/submit/report.md.

    It goes in submit/, next to observe.sh, because everything in submit/ is your submission. Keep it short.

  2. Question 1: “Run observe.sh twice. Which values changed, and why? (SELF_PID deserves a sentence of its own: what exactly is /proc/self?)”

    Boot the VM as in Step 2, and investigate:

    bash /share/observe.shbash /share/observe.sh # compare the two outputs line by linels -l /proc/selfls -l /proc/self # compare the two link targets

    Ask yourself which process reads /proc/self each time. Then write your answer in report.md.

  3. Question 2: “Even while you type nothing, CTXT keeps growing. Which processes run while you wait, and why does the kernel keep switching between them?”

    bash /share/observe.sh | grep CTXTsleep 10 # type nothingbash /share/observe.sh | grep CTXTps -e # every process that exists right now

    First, subtract the two values. Then look at the list from ps -e: you started only a few of these processes. Reread the card on context switches in Step 4, and L01 §4.2 on the timer. Then write your answer.

  4. Question 3: “One thing you found in /proc that surprised you.”

    Anything you met in Steps 3 and 4 counts. Say what it is, and why it surprised you.

Step 7

Submit

We grade what is on GitHub at the deadline.

  1. On your laptop, at the repository root, commit your two files.

    git add labs/00-getting-started/submit/observe.sh labs/00-getting-started/submit/report.mdgit commit -m "Lab00"

    Add only these two files. They are your Lab00 submission.

  2. Push the commit.

    git push

    This pushes to origin, your private repository from Step 0. You cannot push to upstream, the course repository.

  3. Open your repository on GitHub, and check the files.

    Go to labs/00-getting-started/submit/, and check that both files are there with your latest changes. If they are not, the push did not reach your repository: run git remote -v, and compare its output with Step 0.

  4. Before the deadline, go through this list.

    • make check LAB=00-getting-started shows no FAIL.
    • The script contains no uname or nproc, and it reads /proc/self.
    • report.md answers all three questions.
    • Both files are visible on GitHub in your private repository, and chenyueqi is a collaborator.

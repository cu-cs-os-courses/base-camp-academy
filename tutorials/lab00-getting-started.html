Step 0

Get your repository

The goal of this step is to make your own private copy of the course repository. You work in that copy, and it is what we grade.

  1. On GitHub, create a new private repository named 3753-27-spring-<identikey>, where <identikey> is your CU IdentiKey. Leave it empty, with no README, no .gitignore, and no license.
  2. Clone the course repository, and make your private repository the place you push to, as below.
git clone https://github.com/cu-cs-os-courses/3753-27-springcd 3753-27-springgit remote rename origin upstreamgit remote add origin https://github.com/<your-username>/3753-27-spring-<identikey>.gitgit push -u origin maingit remote -v # check: origin = your repository, upstream = the course
  1. In your repository, open Settings → Collaborators → Add people, and add chenyueqi, the instructor. Grading clones your repository with this account. Without it, your work cannot be graded.

Do all three before the Lab00 deadline.

When a new lab is released, run git pull upstream main and then git push. A release adds files under labs/ and never touches your submit/ directories.

Common mistakes

Forking the course repository instead of creating a new one. A fork of a public repository cannot be private, and a public repository exposes your graded work to everyone. Pushing to upstream instead of origin also fails, because you cannot write to the course repository. If git remote -v does not show your own repository as origin, fix the remotes before you continue.

Step 1

Build and boot the VM

The goal of this step is to build the course VM and boot it once. Start this step on the day the lab opens, because the first build takes 30–60 minutes.

The whole environment builds and runs on your laptop. There is no VDI and no shared server. Before you start, you need the three things below.

  • You need a laptop running macOS (Apple Silicon or Intel) or Linux, with about 20 GB of free disk (kernel build cache, a 4 GB disk image, and Docker images) and 8 GB of RAM.
  • On macOS, you need Homebrew, which make setup uses to install QEMU and Docker.
  • You need a GitHub account (Step 0).

Then run, from the repository root (env/README.md explains each target).

cd envmake setup # once; macOS (on Ubuntu: scripts/host-setup-ubuntu.sh)make images # 30–60 min the first timemake smoke # should end with every check passingmake run # boots to a root prompt; leave with Ctrl-a x

How to tell that it worked. Inside the VM, cat /proc/version prints a line that starts with Linux version 6.6.87.

How to leave the VM. Press Control and a together, release both, and then press x. On a Mac, this is the Control key, not Command. Alternatively, type poweroff inside the VM.

Step 2

The edit–run loop

The goal of this step is to learn the loop that every lab uses. You edit files on your laptop and run them inside the VM. Follow these steps once now.

  1. On your laptop, open a terminal and go to the root of your repository.

    cd 3753-27-spring # wherever you cloned it in Step 0

    The next command builds a path from $PWD, the directory you are in. Therefore, it only works from the repository root.

  2. Boot the VM, and share your lab's submit/ directory with it.

    SHARE=$PWD/labs/00-getting-started/submit env/run.sh

    This is the same VM that make run booted in Step 1. The only difference is SHARE. It names a directory on your laptop, and the VM mounts that directory at /share. When the boot finishes, you are at a root prompt inside the VM. Note that this terminal now belongs to the VM, so keep it open.

  3. In the VM, list the shared directory.

    ls /share # prints: observe.sh

    /share is not a copy. It is the same directory as labs/00-getting-started/submit on your laptop, seen from inside the VM.

  4. In the VM, run the script.

    bash /share/observe.sh

    You see eight lines, from KERNEL_RELEASE= to NUM_PROCS=, and every value is empty. This is expected. Each value comes from $(: TODO), and : is the shell's do-nothing command, so the substitution produces nothing.

  5. On your laptop, open labs/00-getting-started/submit/observe.sh in your editor, add echo hello as the last line, and save.

    Use your usual editor, or a second terminal. The first terminal still belongs to the VM.

  6. In the VM, run the script again.

    bash /share/observe.sh # the last line is now: hello

    You did not reboot the VM or copy any file. The VM reads the file directly from your laptop, so every save is visible immediately.

  7. On your laptop, delete the echo hello line, and save.

    The script must print only the eight lines in the format given in the header of observe.sh.

This is the loop for the rest of the lab. Fill in one TODO on your laptop, save, and rerun the script in the VM. Step 3 and Step 4 tell you how to find each value. When you are done, leave the VM with Control-a, then x (Step 1).

Step 3

Tools for reading /proc

The goal of this step is to practice the two skills the lab needs, namely finding the file that holds a fact and cutting out exactly one value. Every fact is text in a file. Work in the VM from Step 2.

  1. In the VM, look around /proc.

    ls /proc # files, and one directory per processcat /proc/versionls /proc/1/cat /proc/meminfo | head

    /proc is the kernel's window onto itself. Each numbered directory is one processA process is a program in execution. The program is a file on disk. Each time you run it, the kernel creates a new process for it. Therefore, every program you start, such as cat or ls, runs as a new process., named by its PIDThe kernel gives each new process a number, its process identifier (PID). Two processes that exist at the same time never share a PID. Therefore, if you run the same program twice, you get two different PIDs.. The eight facts in observe.sh make you look at four different faces of /proc. First, there are system-wide constants, such as the kernel release, the CPUs, and memory. Second, there is a clock, namely /proc/uptime, whose first number is the seconds since boot. Third, there are per-process views, namely /proc/<pid>/. The shell replaces $$ with its own PID, so /proc/$$/ is the directory of the shell that reads it. Fourth, there are live counters that change every time you look, such as the ones in /proc/stat.

  2. Find which files mention a word.

    grep -l -i MemFree /proc/*info 2>/dev/null # prints /proc/meminfo

    /proc/*info stands for every name in /proc that ends in info, such as cpuinfo and meminfo. -l prints only the names of the files that match, and -i ignores case. 2>/dev/null hides the error messages for files you are not allowed to read. The search finds /proc/meminfo, the file that Recitation 01 read with grep MemFree.

    Note that a search over all of /proc/* never finishes, because a few files in /proc never end. Therefore, narrow the names with a pattern such as *info, or search one directory such as /proc/sys/kernel. If a command hangs, press Control and c together to stop it.

  3. Practice cutting out one value.

    Run each command below. Then run cat on the same file, and compare. Some of these files hold a fact that you need in Step 4. However, the values cut out here are not the facts, and the same patterns work on every file.

    cat /proc/sys/kernel/pid_max # PIDs stay below this numberawk '{print $1}' /proc/uptime # field 1 of a one-line fileawk '/^Threads:/ {print $2}' /proc/$$/status # field 2 of the "Threads:" linegrep -c '^Mem' /proc/meminfo # count the lines that matchls /proc | wc -l # count directory entries

    The first file is one value, the number that every PID stays below. A system that keeps too many processes can run out of PIDs, as L03 §2.2 warns. In the second line, awk splits each line into fields at spaces, and $1 is the first field, here the seconds since boot. In the third line, a pattern between slashes, such as /^Threads:/, keeps only the lines that match it, and $2 is the second field of that line. The fourth line counts the lines of /proc/meminfo that start with Mem, because -c prints a count instead of the lines. The last line counts every entry in /proc, files and directories alike.

  4. On your laptop, read the header of observe.sh.

    It gives the output format, which the checks compare exactly. Each line must be KEY=VALUE, with no spaces, no units, and no trailing text. Note that echo "KEY=$(command)" prints whatever the command prints. Therefore, make sure each command prints only the value.

Step 4

The eight facts, one at a time

The goal of this step is to find each of the eight facts where the kernel exposes it, and to check each value a second way. Fill in the eight TODOs in order. For each fact, repeat the five steps below. The table after them says what each fact is, where to start looking, and how to check it.

  1. Read the fact's row in the table below.

    The second column says exactly what value you are after. The third column says how to search for it, not where it is.

  2. In the VM, find the file, and try commands at the prompt until one prints exactly the value.

    Use the search tools and the patterns from Step 3. Trying commands at the prompt is faster than editing the script for every attempt.

  3. In the VM, check the value with the tool in the last column.

    These tools, such as uname and nproc, compute the same value in another way. You may type them at the prompt. However, you may not use them in the script (step 6 below).

  4. On your laptop, put the command into the fact's TODO, and save.

    Replace only : TODO inside $( ), so that the line keeps the form echo "KEY=$(command)".

  5. In the VM, rerun the script, and check that line.

    bash /share/observe.sh

    The line for this fact now shows its value. Then go to the next fact.

Step 5

make check, and reading a failure

make check runs the same checks that grading runs. Therefore, a pass on your laptop is a pass in grading.

  1. On your laptop, at the repository root, run the checks.

    make check LAB=00-getting-started

    It boots a fresh VM without a console, runs your script inside it, and powers the VM off. This takes a few minutes, especially on Apple Silicon. Then it prints one PASS or FAIL line per check, and a last line that starts with RESULT.

  2. Read the result.

    If every check passes, the last line ends with status=pass passes=12 fails=0. The 12 checks fall into three groups.

    • boot and proc-mounted check the VM, not your script. If one of them fails, the environment is broken. Go back to the table in Step 1.
    • no-uname and no-nproc check the rule from Step 4.
    • kernel-release, nproc, pid1-comm, mem-total, uptime, shell-ppid, ctxt, and num-procs check one fact each.

  3. If a check fails, look at your output in a live VM.

    A FAIL line names the check, but it does not show what your script printed. Therefore, boot the VM as in Step 2, run bash /share/observe.sh, and compare the failing line with the format in the header of observe.sh. Fix the script, leave the VM, and run make check again.

    A failed run also prints (artifacts kept at …). In that directory, result.txt holds the raw check output, and console.log holds the VM's boot log. If the VM never came up, look at console.log.

Step 6

The report

The report answers three questions in your own words. Each step below tells you how to investigate, not what the answer is.

  1. On your laptop, create labs/00-getting-started/submit/report.md.

    It goes in submit/, next to observe.sh, because everything in submit/ is your submission. Keep it short.

  2. Question 1. “Run observe.sh twice from the same shell. Which values changed and which stayed the same? Using L01 §5.1 and L03 §1.1, explain why SHELL_PPID stayed the same while CTXT grew.”

    Boot the VM as in Step 2, and investigate with the commands below.

    bash /share/observe.shbash /share/observe.sh # compare the two outputs line by lineecho $$ # the shell you ran both from

    For each value that changed, ask what it counts or measures. For SHELL_PPID, ask which process it names, and whether each run of the script is the same process or a new one. Then write your answer in report.md.

  3. Question 2. “While you type nothing for ten seconds, CTXT still grows. Report your two readings and their difference. Using the five process states of L03 §3.1 and the context switch of L03 §4.3, explain how processes that spend almost all their time waiting can still cause context switches.”

    bash /share/observe.sh | grep CTXTsleep 10 # type nothingbash /share/observe.sh | grep CTXT

    First, subtract the two values. Then follow one process that waits, such as sleep during those ten seconds, through the five states. Ask what the kernel does with the CPU each time a process moves into or out of the running state. Then write your answer.

  4. Question 3. “Pick one of the eight facts other than CTXT. Name the lecture section that explains what it measures, and describe the second way you checked its value in Step 4.”

    The cards in Steps 3 and 4 link the lecture sections behind several facts. Repeat that fact's check from the last column of the table in Step 4, and write down what you ran and what it printed.

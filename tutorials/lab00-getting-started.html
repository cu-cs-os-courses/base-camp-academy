From zero to a running kernel

This page walks you through Lab00 one step at a time: what to do, how to tell that it worked, and what usually goes wrong. It does not do the lab for you. It never shows code for observe.sh and never names the file that holds an answer. It shows you how to search and how to check yourself. Keep labs/00-getting-started/README.md from your repository open beside it: the README is the specification, and this page is the map.

Step 0

Get your repository

  1. Accept the GitHub Classroom invitation posted on Canvas. It creates a private repository that belongs to you.
  2. Clone that repository, not the course's:
git clone <the URL on your repository's green "Code" button>cd <your-repo>git remote -v # check: the URL contains your GitHub username
Common mistake

Cloning the course repository instead. Everything seems fine until you push, and then grading cannot see your work. If git remote -v does not show your own repository, clone again.

Step 1

Build and boot the VM

Start this the day the lab opens. The first build takes 30–60 minutes.

cd envmake setup # once; macOS (on Ubuntu: scripts/host-setup-ubuntu.sh)make images # 30–60 min the first timemake smoke # should end with every check passingmake run # boots to a root prompt; leave with Ctrl-a x

How you know it worked: inside the VM, cat /proc/version prints a line starting Linux version 6.6.87.

Step 2

The edit–run loop

Edit on your laptop with your usual editor; run inside the VM. Every lab works this way.

# laptop, repository rootSHARE=$PWD/labs/00-getting-started/submit env/run.sh# VMls /share # your submit/ directory, livebash /share/observe.sh
  • The share is live: save the file on the laptop and rerun it in the VM, with no reboot.
  • At first every line prints an empty value, because each $( : TODO ) does nothing. That is expected. Fill them in one at a time and rerun after each.
Step 3

Tools for reading /proc

Every fact is text in a file. You need to find the file, then cut out exactly one value.

Finding. /proc is documented in man 5 proc. Press / to search for a word, and n for the next match. To find which files mention a word, use grep -l over a set of files, for example:

grep -l -i swap /proc/* 2>/dev/null # which top-level files mention "swap"?man 5 proc # then /swap, n, n, ...

Cutting out a value. These are practice examples on files the lab does not ask about. The same patterns carry over:

cat /proc/sys/vm/swappiness # a whole file that is one valueawk '{print $1}' /proc/loadavg # field 1 of a one-line fileawk '/^Threads:/ {print $2}' /proc/self/status # field 2 of the line starting "Threads:"grep -c '^Vm' /proc/self/status # count the lines that matchls /proc | wc -l # count directory entriesreadlink /proc/1/exe # where a symbolic link points
The output contract

Each line must be exactly KEY=VALUE: no spaces, no units, no trailing text. echo "KEY=$(command)" prints whatever the command prints, so make sure the command prints only the value.

Step 4

The eight facts, one at a time

For each fact: exactly what you are after, how to go looking for it, and how to check your answer with a tool that is off-limits in the script but fine to type in the terminal.

factwhat you are afterhow to look for itcheck it with
KERNEL_RELEASEThe release string of the running kernel, like 6.6.87.One system-wide value. Search man 5 proc for "release" and read which file it names.uname -r
NPROCHow many CPUs the kernel is using: a single number.Find the /proc file that describes the CPUs, one entry per CPU. Then turn "entries" into a count.nproc
PID1_COMMThe command name of process 1, the first process the kernel starts.man 5 proc lists the files inside each process's directory. Find the one that holds only the command name.ps -p 1 -o comm=
MEM_TOTAL_KBTotal usable RAM in kB, as a bare number.Find the /proc file that reports memory, then the line for the total.free -k, "total" column
BOOT_CMDLINEThe parameters the kernel was booted with, exactly as passed.Search man 5 proc for "command line"; make sure you pick the kernel's, not a process's.The -append line in env/run.sh
SELF_PIDThe PID of whichever process reads /proc/self./proc/self is a symbolic link. Work out what it points to, and extract the PID from that.Run the script twice: the value changes, and it is never 1.
CTXTTotal context switches since boot: one number.The header tells you the file. man 5 proc explains each of its lines; find the one for context switches.Read it twice, a few seconds apart: it only grows.
NUM_PROCSHow many processes exist right now.Every process is a directory whose name is all digits, and nothing else in /proc is. Count those names only.ps aux | wc -l (one header line; roughly equal is right)
Rules the checks enforce

No uname and no nproc anywhere in the script, even inside a command substitution: a check looks for those words. SELF_PID must come from /proc/self, not from the shell's $$: a check looks for /proc/self in your script.

Step 5

make check, and reading a failure

# laptop, repository rootmake check LAB=00-getting-started
  • It boots a fresh VM without a console, runs your script there, and prints one PASS or FAIL per check, then a RESULT line. Grading runs the same checks.
  • Check names map to facts: kernel-release, nproc, pid1-comm, mem-total, boot-cmdline, self-pid, ctxt, num-procs, plus the rule checks no-uname, no-nproc and uses-proc-self.
  • A FAIL names the check, not your output. Go back to Step 2, run the script in a live VM, and compare that one line with the format in the file header.
  • A failed run prints (artifacts kept at …). In that directory, result.txt is the raw check output, and console.log is the VM's boot log, which is where to look if the VM never came up.
Step 6

The report

Create submit/report.md and answer the README's two questions in your own words. How to investigate, not the answers:

  1. What changed between two runs, and what is /proc/self? Run the script twice and compare line by line. Then run ls -l /proc/self twice. Ask yourself: which process is doing the looking each time?
  2. MemFree vs MemAvailable. Read both lines of /proc/meminfo, then read what man 5 proc says about each. Think about what the kernel keeps in memory that it could give back.
Step 7

Submit

git add labs/00-getting-started/submit/observe.sh labs/00-getting-started/submit/report.mdgit commit -m "Lab00"git push

Then open your repository on GitHub and check that both files are there with your latest changes. What is on GitHub at the deadline is what gets graded.

  • make check LAB=00-getting-started shows no FAIL.
  • The script contains no uname or nproc and reads /proc/self.
  • report.md answers both questions.
  • Both files are visible on GitHub in your repository.
